ConteúdoAula 05 · Atividade 02

sys.getsizeof e o que ele não conta

06 min

É a primeira ferramenta que todo mundo encontra, e a que mais produz conclusão errada. Vale entender exatamente o que ela mede antes de confiar nela.

python
import sys
print(sys.getsizeof([1, 2, 3]))
print(sys.getsizeof(list(range(1_000_000))))
Saída real88 8000056

8 MB para um milhão de inteiros. Oito bytes por item mais um cabeçalho — parece exato. E é, para este caso, porque os inteiros pequenos são objetos compartilhados que o Python já tinha na memória.

Onde ele deixa de dizer a verdade

Troque os inteiros por registros — que é o que existe em ETL:

python
row  = {"id": 1, "name": "Alice Johnson", "city": "New York"}
rows = [dict(row) for _ in range(10_000)]

shallow = sys.getsizeof(rows)
deep = shallow + sum(
    sys.getsizeof(d) + sum(sys.getsizeof(k) + sys.getsizeof(v) for k, v in d.items())
    for d in rows
)
print(f"getsizeof   : {shallow:,} bytes")
print(f"soma real   : {deep:,} bytes")
Saída realgetsizeof : 85,176 bytes soma real : 4,565,176 bytes

Errou por 54 vezes. Não é um bug: getsizeof mede o objeto e só o objeto. Uma lista é um vetor de ponteiros, então ela reporta 8 bytes por elemento — e os dicts de verdade, com suas chaves e strings, ficam de fora da conta.

Como isso vira uma decisão errada

Você mede um lote de 10 mil registros, vê 85 KB, conclui que cabem 100 lotes na memória e configura o pipeline assim. O consumo real é 4,5 MB por lote. O processo morre com MemoryError em produção, com uma medição no seu caderno dizendo que não deveria.

Para que ele serve, então

Para responder "quanto pesa esta caixa", não "quanto pesa tudo que está dentro dela". É útil em objetos rasos e de tipo fixo — um array, um bytes, um buffer. E é útil para uma coisa específica que a próxima atividade usa:

python
g = (x for x in range(10))
print(sys.getsizeof(g), "bytes")
Saída real200 bytes

200 bytes, e esse número não muda se você trocar o range(10) por range(10**12). Aqui getsizeof é honesto porque não há nada dentro: o generator guarda um frame suspenso, não os valores. É a mesma constatação dos 56 bytes do Countdown na aula 01, agora com o nome certo.

A regra

Use getsizeof para inspecionar um objeto. Para responder "quanto o meu programa está consumindo", use tracemalloc — que é a próxima atividade e é a ferramenta que você vai usar no resto do curso.

A medição de verdade

O mesmo trabalho — somar o campo amount de um milhão de registros — das duas formas:

python
def source(n):
    for i in range(n):
        yield {"id": i, "amount": i * 1.5}

# lazy
tracemalloc.start()
total = sum(r["amount"] for r in source(1_000_000))
_, peak = tracemalloc.get_traced_memory(); tracemalloc.stop()

# materializado
tracemalloc.start()
rows = [r for r in source(1_000_000)]
total = sum(r["amount"] for r in rows)
_, peak = tracemalloc.get_traced_memory(); tracemalloc.stop()
Saída realgenerator : current 0.000 MB peak 0.001 MB list : current 236.9 MB peak 236.9 MB

1 KB contra 237 MB, para o mesmo resultado numérico. Esse é o valor que as quatro aulas anteriores vinham prometendo — agora medido.

Duas armadilhas do tracemalloc

Ele só conta alocações feitas pelo interpretador Python. Um DataFrame do pandas ou um ndarray do NumPy alocam em C, e boa parte do consumo deles não aparece — para esses, o número honesto vem do RSS do processo (psutil) ou do df.memory_usage(deep=True).

E ele custa caro: ligado, o programa fica visivelmente mais lento. É ferramenta de investigação, não de produção.

Mão na massaAula 05 · Atividade 04

Prever o pico

05 min

Três trechos que fazem o mesmo trabalho sobre 200 mil registros de um arquivo de 8,4 MB. Ordene do menor para o maior pico antes de ver a resposta.

python
# A — três agregações, relendo o arquivo em cada uma
n     = sum(1 for _ in read_jsonl(path))
total = sum(r["amount"] for r in read_jsonl(path))
mx    = max(r["amount"] for r in read_jsonl(path))

# B — materializa uma vez, agrega três vezes sobre a lista
rows  = list(read_jsonl(path))
n, total, mx = len(rows), sum(r["amount"] for r in rows), max(r["amount"] for r in rows)

# C — uma passada, três acumuladores
n = 0; total = 0; mx = float("-inf")
for r in read_jsonl(path):
    n += 1; total += r["amount"]; mx = max(mx, r["amount"])
Prever antes de rodar
Sua resposta fica salva neste navegador.
tracemalloc + perf_counter — 200.000 registros
A  3 passadas lazy    : 2.86 s    pico   0.14 MB
B  materializa 1 vez  : 2.05 s    pico  80.19 MB
C  1 passada, 3 acum. : 0.93 s    pico   0.14 MB

A ordem de memória é A = C < B, e a de tempo é C < B < A. Elas não coincidem — e é por isso que a pergunta tinha duas partes.

A economiza memória e paga com tempo: relê e reparseia o arquivo três vezes. B paga 80 MB para parsear uma vez só, e ainda assim é mais lento que C. C ganha nos dois: uma passada, e nada guardado.

O que a opção C revela

C é 3× mais rápido que A e usa 559× menos memória que B. Ela não é um meio-termo — é melhor que as duas nas duas dimensões. Quando existe uma opção assim, é sinal de que a pergunta "lazy ou eager?" era a pergunta errada desde o começo. A atividade 08 volta a isso.

ConteúdoAula 05 · Atividade 05

Provando O(1): a mesma medição em três escalas

06 min

Uma medição isolada diz "usou pouco". Só uma série de medições diz "usa a mesma coisa independente do tamanho" — e é essa a afirmação que interessa.

A diferença importa. "Usou 40 MB" é um fato sobre a entrada que você testou. "É O(1)" é uma previsão sobre todas as entradas que você não testou — e é por isso que só se prova variando a escala:

python
for n in (10_000, 100_000, 1_000_000):
    tracemalloc.start()
    sum(r["amount"] for r in source(n))
    _, pico_lazy = tracemalloc.get_traced_memory(); tracemalloc.stop()

    tracemalloc.start()
    rows = list(source(n)); sum(r["amount"] for r in rows)
    _, pico_eager = tracemalloc.get_traced_memory(); del rows; tracemalloc.stop()

    print(f"{n:>10,} | {pico_lazy/1024:>9.1f} KB | {pico_eager/1024**2:>9.1f} MB")
Saída real n | generator | lista 10,000 | 0.6 KB | 2.4 MB 100,000 | 0.6 KB | 23.6 MB 1,000,000 | 0.6 KB | 236.9 MB

Leia a tabela por coluna, não por linha. A coluna do generator é uma reta horizontal: 0,6 KB, 0,6 KB, 0,6 KB. A da lista multiplica por dez toda vez que a entrada multiplica por dez. Isso é O(1) contra O(n), demonstrado — não afirmado.

O protocolo mínimo para provar uma complexidade

Três escalas, separadas por 10×

Duas escalas não distinguem O(1) de O(log n) nem O(n) de O(n log n). Três pontos separados por uma ordem de grandeza mostram a forma. Se o número dobra quando a entrada decuplica, você tem algo logarítmico; se decuplica, linear; se fica parado, constante.

Meça o pico, não o final

Um pipeline que aloca 2 GB e libera antes de terminar tem current pequeno e peak fatal. É o peak que precisa ser plano.

Desconfie de plano demais

Se o número não muda nada entre escalas, confirme que o trabalho está mesmo acontecendo. Um generator que ninguém consome custa 200 bytes e faz zero — e o gráfico fica lindo.

O mesmo raciocínio na fase 2

É assim que se lê o plano de execução de uma query ou de um job Spark: não "quantos MB este estágio usou", mas "como este estágio cresce quando a partição cresce". Um estágio O(1) por partição escala horizontalmente; um O(n) tem um teto, e você vai encontrá-lo.

Quando lazy é a escolha errada

09 min · o núcleo da aula

Quatro situações em que insistir em generator produz código mais lento, mais complicado ou simplesmente errado. Todas comuns.

1. Você precisa de mais de uma passada

É o caso medido na atividade 04. Três agregações relendo o arquivo custaram 2,86 s contra 2,05 s materializando — lazy foi 1,4× mais lento, porque parsear JSON três vezes custa mais do que guardar o resultado.

Se o dado cabe na memória e você precisa de N passadas, materializar é a decisão certa. O erro é fazê-la por reflexo: a pergunta é se cabe, e "cabe" tem que ser um número, não uma esperança.

2. Você precisa de acesso aleatório, tamanho ou ordem

python — nada disso funciona em iterador
len(records)          # TypeError: object of type 'generator' has no len()
records[42]           # TypeError: 'generator' object is not subscriptable
records[-1]           # idem — e "o último" exige chegar ao fim
sorted(records)       # funciona, mas materializa tudo por dentro

O sorted é o mais traiçoeiro dos quatro, porque funciona. Ele aceita o generator, roda, devolve a lista certa — e por dentro construiu a lista completa, porque não existe como ordenar sem ver todos os elementos. Você escreveu código lazy e obteve consumo eager, sem nenhum aviso.

A mesma coisa vale para mediana e percentis:

python
tracemalloc.start()
med = statistics.median(r["amount"] for r in read_jsonl(path))
_, peak = tracemalloc.get_traced_memory(); tracemalloc.stop()
print(f"mediana {med}  pico {peak/1024**2:.1f} MB")
Saída realmediana 499.5 pico 6.3 MB

Passar um generator para median() não economizou nada: ele materializa internamente porque precisa ordenar. Os 6,3 MB são os 200 mil valores — menos que os 80 MB dos dicts completos, mas O(n) do mesmo jeito. Média é O(1); mediana é O(n). Não há truque que mude isso.

3. O dado é pequeno

Laziness tem custo fixo por item: cada next() é uma retomada de frame, e isso não é de graça.

timeit — 100 itens, média de 10.000 execuções
sum(lista)               0.59 µs
sum(x for x in lista)    2.41 µs

4× mais lento, para economizar uma lista de 100 itens que ocupa menos de 1 KB. Numa função chamada milhões de vezes, esse fator 4 é a diferença entre um job de 10 minutos e um de 40.

4. A complexidade não paga

Um pipeline de generators exige cuidado com esgotamento, com arquivos que ficam abertos, com tee e seu buffer, com iteradores consumidos por engano. Toda a aula 01 e metade da 04 são sobre esses riscos.

Se a entrada é um CSV de 3 MB que sempre vai ser um CSV de 3 MB, rows = list(read_csv(path)) é uma linha, não tem nenhuma dessas armadilhas, e o revisor entende em dois segundos. Escolher generator ali é pagar risco por uma economia que ninguém vai notar.

A pergunta que decide

"O tamanho da entrada é controlado por mim ou por outra pessoa?"

Um arquivo de configuração que você mesmo escreve: materialize à vontade. Um upload de cliente, um dump de tabela que cresce, um tópico Kafka, o resultado de uma query sem LIMIT: streaming, sempre — porque o dia em que a entrada decuplicar não vai ser avisado.

Resumo em uma tabela
SituaçãoEscolha
Entrada de tamanho desconhecido ou crescentestreaming
Uma passada, uma agregação O(1)streaming
N passadas e o dado cabematerializar
Precisa de len, índice, ordem, medianamaterializar (o Python vai fazer isso de qualquer jeito)
Dado pequeno e fixomaterializar — é mais simples e mais rápido

O preço de tempo do lazy

05 min

A memória a gente já mediu. Vale medir o outro eixo, porque a conversa sobre generators quase sempre ignora que existe um preço.

timeit — somar 1.000.000 de inteiros, melhor de 5
sum(xs)                        5.9 ms
sum([x for x in xs])          18.7 ms
sum(x for x in xs)            22.8 ms
sum(map(lambda v: v, xs))     41.6 ms

Quatro formas de somar a mesma lista, com um fator 7 entre a primeira e a última. Três coisas para tirar daí:

A camada mais rápida é não ter camada

sum(xs) percorre a lista em C. Qualquer coisa que você coloque no meio — genexp, list comp, map — devolve o controle ao interpretador Python a cada item, e é aí que o tempo vai.

A list comp é mais rápida que a genexp

18,7 contra 22,8 ms, apesar de alocar uma lista de um milhão de itens. Materializar tem um custo uma vez; suspender e retomar um frame tem um custo por item. Em volumes pequenos, o segundo perde.

map com lambda é o pior dos mundos

41,6 ms: você paga a laziness e uma chamada de função Python por item. map só compensa quando a função é builtin em C — map(int, linhas) é rápido, map(lambda x: int(x), linhas) não.

Como isso muda a decisão — e como não muda

Não muda nada quando a entrada é grande e desconhecida: 22,8 ms contra 5,9 ms é irrelevante se a alternativa é o processo morrer. Muda tudo em código quente sobre dado pequeno.

E repare no que a atividade 04 já tinha mostrado: a opção C, com uma passada e três acumuladores, foi ao mesmo tempo a mais rápida e a de menor pico. O trade-off entre tempo e memória é real, mas nem sempre você está de fato nele — às vezes está só numa implementação ruim.

A pergunta certa não é "lazy ou eager"

07 min

É quantas passadas o seu pipeline faz sobre os dados. Quase todo problema de memória em ETL é, no fundo, um problema de contagem de passadas.

Volte à medição da atividade 04. Três agregações sobre 200 mil registros:

PassadasTempoPico
A — relê a cada agregação32,86 s0,14 MB
B — materializa e agrega1 + 3 em memória2,05 s80,19 MB
C — uma passada, três acumuladores10,93 s0,14 MB

A e B são as duas respostas que a discussão "lazy ou eager" produz, e as duas são piores que C. C não é um meio-termo entre elas — é uma implementação diferente, que sai da discussão.

python — o padrão do acumulador único
def summarize(records: Iterable[dict]) -> dict:
    """Compute every statistic in a single pass over `records`."""
    count = 0
    total = 0.0
    largest = float("-inf")
    by_city: defaultdict[str, float] = defaultdict(float)

    for record in records:
        amount = record["amount"]
        count += 1
        total += amount
        largest = max(largest, amount)
        by_city[record["city"]] += amount

    return {"count": count, "total": total, "max": largest,
            "mean": total / count if count else 0.0, "by_city": dict(by_city)}

Cinco estatísticas, uma passada, e o consumo é O(1) em tudo menos o by_city — que é O(cidades distintas), não O(registros). Saber apontar exatamente qual termo é que cresce, e com o quê, é a diferença entre dizer "usa pouca memória" e saber onde está o teto.

Quando você realmente precisa de duas passadas

Existe o caso legítimo: normalizar por um valor que só se conhece no fim (dividir pelo total, calcular z-score, deduplicar mantendo o último). Aí a resposta não é escolher entre A e B — é escolher onde a materialização acontece:

EstratégiaCustoQuando
Materializar em RAMO(n) de memóriao dado cabe, e você mediu que cabe
Duas passadas no arquivo2× de I/Oa fonte é relegível e barata (disco local)
Passada 1 grava intermediáriodisco temporárioa fonte é cara ou não relegível (API, socket)
Acumulador aproximadoerro controladoHyperLogLog para distinct, t-digest para percentil
A fonte é relegível?

Um arquivo local, sim. Um stdin, um socket, um cursor de banco já consumido, uma resposta HTTP: não. Essa propriedade decide entre a linha 2 e a linha 3 da tabela, e é a primeira coisa a perguntar quando alguém propõe "é só ler de novo".

Medindo em produção

05 min

tracemalloc é caro demais para ficar ligado. O que se instrumenta num job de verdade é outra coisa.

Um teste que falha quando o pipeline deixa de ser O(1)

É a forma mais barata de não regredir, e cabe na sua suíte:

python
def test_pipeline_memory_is_flat():
    """The peak must not grow with the input size."""
    peaks = []
    for n in (10_000, 100_000):
        tracemalloc.start()
        consume(pipeline(source(n)))
        peaks.append(tracemalloc.get_traced_memory()[1])
        tracemalloc.stop()

    # 10x a entrada nao pode dobrar o pico
    assert peaks[1] < peaks[0] * 2, f"memoria cresceu com a entrada: {peaks}"

Repare na folga do * 2: o teste não exige igualdade, porque ruído de alocação existe. Ele exige que a curva seja plana o bastante — e falha alto no dia em que alguém acrescentar um list() no meio do pipeline.

O que realmente monitorar no job

MétricaComoDiz o quê
RSS do processopsutil.Process().memory_info().rsso número que o contêiner usa para te matar
Registros por lotelog a cada N lotesse o batching está do tamanho que você configurou
Registros processadoscontadordetecta o iterador consumido por engano da aula 01
Duração por estágioperf_counter por etapaonde o tempo vai, antes de otimizar no lugar errado
RSS não é o mesmo que tracemalloc

O tracemalloc conta o que o Python alocou; o RSS conta o que o sistema operacional entregou ao processo — e o Python não devolve tudo ao SO quando libera. É normal ver RSS alto e current baixo. Para "cabe no contêiner?", o RSS é a fonte da verdade; para "quem alocou isso?", o tracemalloc.

Achando o culpado

Quando o pico está alto e você não sabe por quê, tracemalloc.take_snapshot().statistics("lineno") devolve as alocações agrupadas por linha de código, ordenadas. Costuma resolver em um minuto o que meia hora de leitura não resolve.

medição

5.4

Ache o vazamento

depuração

Este pipeline deveria ser O(1) e não é. Meça, descubra por quê, conserte, e meça de novo para provar:

python
def process(records):
    """Normalize records and report how many were rejected."""
    seen_ids = set()
    rejected = []

    for record in records:
        if record["id"] in seen_ids:
            rejected.append(record)
            continue
        seen_ids.add(record["id"])
        yield {**record, "amount": round(record["amount"], 2)}

    log.info("rejected %d duplicates", len(rejected))

Há dois termos que crescem com a entrada aqui, e eles não são igualmente evitáveis. Diga qual dá para eliminar sem mudar o comportamento observável, qual não dá, e o que você faria com o que não dá.

O termo que você não consegue eliminar

O agrupamento por cidade é O(cidades distintas), e isso é irredutível se a fonte não vier ordenada — é exatamente a conclusão do exercício 4.4. Declare esse termo no comentário em vez de fingir que o pipeline é O(1): "O(1) nos registros, O(k) nas cidades distintas" é a descrição honesta.

Como entregar

Mande o lesson05.py com as tabelas de medição nos comentários. Toda afirmação sobre memória neste arquivo precisa ter um número ao lado — é o assunto da aula.

Checklist antes de commitar
  • Toda função definida é chamada em algum lugar do main()?
  • Você leu cada saída e conferiu contra o que esperava?
  • Toda afirmação de complexidade tem três escalas medidas por trás?
  • O tracemalloc.stop() está num finally?
  • Sobrou algum import não usado?
