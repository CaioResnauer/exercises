Apresentação

03 min · última aula da fase 1

Você já usa git. Faz add, commit, push, e funciona. Esta aula não é sobre os comandos — é sobre o modelo de dados por baixo deles, que é surpreendentemente simples e que transforma o git de sequência de rituais em ferramenta previsível.

A estrutura é a mesma da aula 01: em vez de decorar o que git reset --hard faz, você vai entender as três áreas que ele mexe, e a partir daí deduzir o comportamento de qualquer comando — inclusive os que você ainda não conhece.

O que você vai entender

  • Que o git guarda conteúdo endereçado por hash, não arquivos nem diffs — e o que isso implica;
  • Por que a área de staging existe, e por que ela é a causa do "commitei e faltou um arquivo";
  • Como escrever um histórico que serve de documentação, com Conventional Commits;
  • Por que aquele CSV que você commitou continua no repositório depois de apagado — medido.
Por que esta aula fecha a fase 1

As cinco aulas anteriores produziram código. Esta é sobre o que faz esse código sobreviver: um repositório que outra pessoa — inclusive você daqui a seis meses — consegue abrir e entender. Um pipeline brilhante num repo ilegível é um pipeline que vai ser reescrito.

ConteúdoAula 06 · Atividade 02

O que o git realmente guarda

08 min

A intuição comum é que o git guarda uma sequência de diffs: o commit 2 é "o commit 1 mais estas mudanças". Está errada, e o erro atrapalha.

O git guarda snapshots completos, endereçados pelo hash do próprio conteúdo. Um objeto no git é o par (sha1 do conteúdo, conteúdo) — e é só isso.

O hash é do conteúdo, não do arquivo

bash
printf 'def take(it, n):\n    return islice(it, n)\n' > pipeline.py
cp pipeline.py outro_nome.py

git hash-object pipeline.py
git hash-object outro_nome.py
Saída real634d1a045449cef3bd36baaac640f329f7204ec5 634d1a045449cef3bd36baaac640f329f7204ec5

Mesmo hash. O nome do arquivo não entra na conta — só os bytes. Três consequências que explicam comportamentos que parecem mágicos:

Renomear é de graça

O git não guarda "renomeado de X para Y". Ele guarda uma árvore nova apontando para o mesmo blob com outro nome. Quando o git log te mostra um rename, ele deduziu comparando conteúdos — não estava anotado em lugar nenhum.

Conteúdo duplicado é armazenado uma vez

Dez arquivos idênticos em dez pastas viram um blob e dez entradas de árvore. Um arquivo que não mudou entre dois commits é literalmente o mesmo objeto, referenciado duas vezes.

O histórico é imutável por construção

Mudar qualquer byte de um commit antigo muda o hash dele, o que muda o hash de todos os commits seguintes. É por isso que rebase "reescreve" o histórico em vez de editá-lo: ele cria commits novos e abandona os antigos.

Os três tipos de objeto

Depois de um add e um commit, o banco tem exatamente três objetos:

bash
git add pipeline.py && git commit -m "feat(pipeline): add take"
git cat-file --batch-all-objects --batch-check
Saída real634d1a04... blob 42 206f3a6f... tree 39 92262120... commit 175
ObjetoGuardaAponta para
blobo conteúdo de um arquivo, sem nomenada
treenomes, permissões e um diretórioblobs e outras trees
commitautor, data, mensagemuma tree e o(s) commit(s) pai

Abra o commit e a árvore e veja que não há nada de misterioso:

bash
git cat-file -p HEAD
git cat-file -p HEAD^{tree}
Saída realtree 206f3a6f4a7dc708fe630a6068cc7301caada49f author Caio <caio3322@gmail.com> 1788655520 -0300 committer Caio <caio3322@gmail.com> 1788655520 -0300 feat(pipeline): add take 100644 blob 634d1a04... pipeline.py

O commit é um arquivo de texto de 175 bytes apontando para uma árvore. A árvore é uma lista de nomes apontando para blobs. Não existe diff guardado em lugar nenhum — o git diff calcula a diferença entre duas árvores na hora em que você pede.

E o blob que não mudou?

bash
printf 'def drop(it, n):\n    return islice(it, n, None)\n' > helpers.py
git add helpers.py && git commit -m "feat(pipeline): add drop"
git cat-file -p HEAD^{tree}
Saída real100644 blob fde93444... helpers.py 100644 blob 634d1a04... pipeline.py

O blob do pipeline.py é o mesmo 634d1a04 do primeiro commit. A árvore nova aponta para o objeto velho. É por isso que um repositório com mil commits de um projeto pequeno continua pequeno — cada commit é um snapshot completo, mas quase todos os objetos são compartilhados.

Mão na massaAula 06 · Atividade 03

Encontre o blob

05 min

Um teste rápido do modelo. O comando abaixo roda num repositório recém-criado, antes de qualquer git add:

bash
printf 'def take(it, n):\n    return islice(it, n)\n' > pipeline.py

git hash-object pipeline.py
git cat-file -t $(git hash-object pipeline.py)
Prever antes de rodar
Sua resposta fica salva neste navegador.
saída real
634d1a045449cef3bd36baaac640f329f7204ec5
fatal: git cat-file: could not get object info

A primeira funciona, a segunda falha. E a diferença entre elas é a definição de git add.

git hash-object calcula o hash — é uma função pura sobre os bytes, não precisa que nada exista. git cat-file lê do banco de objetos, e ali ainda não há nada.

Depois de git add pipeline.py, a mesma linha funciona:

bash
git add pipeline.py
git cat-file -t $(git hash-object pipeline.py)
git cat-file -p $(git hash-object pipeline.py)
Saída realblob def take(it, n): return islice(it, n)

É isso que git add faz: grava um blob permanente no banco de objetos e anota o hash no index. Não é "marcar para commitar depois" — o conteúdo já está salvo, agora, antes de qualquer commit.

Uma consequência prática

Se você fez git add e depois estragou o arquivo, o conteúdo bom ainda existe no banco de objetos. git checkout -- arquivo traz de volta a versão do index. E mesmo depois de um reset, o blob continua lá até o gc passar — git fsck --lost-found acha.

As três áreas e por que o staging existe

07 min

Quase todo comando de git é uma movimentação entre três lugares. Quem tem esse mapa na cabeça deduz o comportamento de qualquer comando; quem não tem, decora receitas.

ÁreaOnde viveO que é
working treeseus arquivoso que o editor mostra
index (staging).git/indexa foto do próximo commit
HEAD.git/objectso último commit

O index é o que confunde — parece burocracia entre você e o commit. Ele existe para permitir uma coisa específica: commitar parte do que você mudou. Você mexeu em cinco arquivos resolvendo duas coisas diferentes; o index deixa você fazer dois commits coerentes em vez de um commit bagunçado.

E ele tem uma propriedade que morde. Percorra o passo a passo:

Execução passo a passo — o que o commit realmente grava

working tree—
index—
HEAD—
Passo 1 de 6 · clique em “Próximo passo”.

O mapa dos comandos

Com as três áreas na cabeça, os comandos param de precisar de decoreba:

ComandoMove o quê
git add <f>working tree → index
git commitindex → HEAD
git restore --staged <f>HEAD → index (desfaz o add)
git restore <f>index → working tree (perde sua edição)
git reset --soft <c>move só o HEAD; index e arquivos intactos
git reset --mixed <c>HEAD e index; arquivos intactos (padrão)
git reset --hard <c>as três — o único que apaga trabalho
git diffcompara working tree com index
git diff --stagedcompara index com HEAD — o que você está prestes a commitar
As duas linhas que evitam quase todo acidente

git diff --staged antes de todo commit: mostra exatamente o que vai entrar, que é a informação que o trace acima mostrou faltar. E git status antes de todo push.

Dos comandos da tabela, só o --hard e o git restore <f> destroem trabalho não commitado. Todo o resto é reversível — inclusive commits "perdidos", que o git reflog acha.

ConteúdoAula 06 · Atividade 05

Commits que contam uma história

07 min

O histórico é a única documentação que nunca fica desatualizada — porque é gerada pelo próprio ato de mudar o código. Vale escrevê-lo como se alguém fosse ler, porque alguém vai.

Comece pelo caso real. O histórico deste repositório, antes desta aula:

bash — o que estava lá
012e669 updating lesson04
69cbce6 udpdating lesson04
ff39593 adding lesson04.py
f0fd420 Adding lesson03.py
81c7ae3 updating lesson01, assing lesson02
a05e45e add README

Três problemas, e o terceiro é o que dói. As mensagens dizem o que foi tocado, nunca o que mudou. Há um typo (udpdating) e uma mensagem com duas coisas (updating lesson01, assing lesson02). E 012e669 contra 69cbce6: se um bug aparecer, nada distingue esses dois commits — você vai ter que abrir os dois.

Conventional Commits

texto — o formato
<tipo>(<escopo>): <resumo no imperativo, minúsculo, sem ponto>

<corpo: POR QUE, não o quê. O diff já mostra o quê.>
TipoQuando
featcapacidade nova, visível para quem usa
fixcorrige comportamento errado
refactormuda a forma, não o comportamento
perfrefactor cujo objetivo é desempenho — traga o número
testsó testes
docssó documentação
choretooling, configuração, dependências

O mesmo trabalho, escrito assim:

bash — o que dá para ler daqui a seis meses
fix(lesson04): stop manual_batched from looping forever

The while guard tested an islice object, which is always truthy, so the
loop kept yielding empty tuples after the source was exhausted. Move the
tuple() inside the condition and add the assertions that catch it.

O resumo cabe num --oneline e já diz o suficiente para alguém decidir se este é o commit que procura. O corpo explica por que — a causa, não a mudança. O diff mostra a mudança melhor do que qualquer prosa.

Um commit, uma ideia

É a regra que mais melhora um histórico, e a mais ignorada. Se a sua mensagem precisa de "e" ou de uma vírgula listando coisas, são dois commits.

Não é estética. Um commit atômico é o que torna possível:

  • git revert de uma mudança sem levar junto três não relacionadas;
  • git bisect apontar a linha culpada em vez de um commit com 40 arquivos;
  • um review que cabe na cabeça de quem revisa.

Se você já misturou tudo na working tree, o index resolve — é para isso que ele existe:

bash
git add -p            # escolhe HUNK por hunk o que entra neste commit
git diff --staged     # confere
git commit -m "fix(reader): close the file when the consumer breaks early"
git add -p            # o resto
git commit -m "test(reader): cover the early-break path"
Escreva a mensagem antes do código

Se você não consegue escrever o resumo de uma linha antes de começar, provavelmente você não sabe ainda o que vai fazer — ou vai fazer duas coisas. É um teste de escopo que custa dez segundos.

Para saber maisAula 06 · Atividade 06

O que não versionar

06 min

Em engenharia de dados esse assunto é mais grave que na média, porque a nossa pasta de trabalho está cheia de arquivos grandes que parecem parte do projeto.

A medição

Um CSV de 4,7 MB, commitado, regerado, e depois "removido":

bash
git add sales.csv && git commit -m "chore: add data"
du -sh .git

# regenera o csv (mesmas 300k linhas, valores diferentes) e commita
git add sales.csv && git commit -m "chore: regenerate data"
du -sh .git

# "remove" o arquivo do versionamento e limpa
git rm --cached sales.csv && echo "sales.csv" > .gitignore
git add .gitignore && git commit -m "chore: stop tracking data"
git gc --aggressive --prune=now
du -sh .git
Saída realsales.csv: 4.7M .git depois de 1 commit do csv: 2.2M .git depois de REGERAR o csv: 4.2M .git depois de "remover" + gc: 3.7M

Três coisas para tirar daí.

Compressão não salva você

4,7 MB de CSV viraram 2,2 MB no .git. Bom, mas é um fator 2 — não uma ordem de grandeza. Um dataset de 500 MB não vai virar 5 MB.

Cada versão é um objeto novo, inteiro

Regerar o CSV quase dobrou o .git. O git não guarda o diff de um arquivo binário-ish: guarda o snapshot completo. Um CSV regenerado toda semana custa o tamanho dele por semana, para sempre.

"Remover" não remove

Depois do git rm --cached, do .gitignore e de um gc --aggressive --prune=now, o .git ainda tem 3,7 MB. Os blobs continuam lá porque commits antigos ainda apontam para eles — e apagar de verdade exige reescrever o histórico inteiro (git filter-repo) e forçar todo mundo a reclonar.

O caso que não é sobre tamanho

Um .env com credencial commitado por engano tem exatamente a mesma propriedade: remover no commit seguinte não remove. O segredo continua acessível no histórico, e se o repo foi pushado, a única resposta correta é rotacionar a credencial. Reescrever o histórico ajuda, mas você não sabe quem já clonou.

Um .gitignore para pipeline de dados

.gitignore
# Python
__pycache__/
*.py[cod]
.venv/
.pytest_cache/
.ipynb_checkpoints/

# Segredos — nunca versionar
.env
*.pem
credentials.json

# Dados e saídas
data/raw/
data/processed/
out/
*.parquet
*.db

# Amostras pequenas para os testes SÃO versionadas
!data/samples/*.jsonl

A última linha é a que vale a discussão. Dados de produção ficam de fora, mas uma amostra pequena e fixa deve entrar: é ela que faz os testes rodarem em qualquer máquina, e o repositório deixar de depender de um bucket que talvez você nem tenha acesso.

A regra de bolso

Versione o que é fonte: código, configuração, schema, migração, amostra pequena. Não versione o que é derivado (saída de pipeline, cache, build) nem o que é secreto. Se um arquivo pode ser regerado pelo código do repositório, ele não pertence ao repositório.

Branches e o histórico legível

06 min

Depois do modelo de objetos, branch fica quase decepcionante de tão simples.

bash
cat .git/refs/heads/main
Saída real92262120418ccc20e6843c60a58f22b3de04d3ac

Um branch é um arquivo de texto com 40 caracteres: o hash de um commit. Criar um branch escreve um arquivo desses; trocar de branch reescreve o HEAD e ajusta os arquivos. Nada é copiado. É por isso que git branch é instantâneo mesmo num repositório enorme.

E como cada commit aponta para o pai, o "histórico do branch" é só seguir os ponteiros a partir daquele hash.

Merge ou rebase

mergerebase
O que fazcria um commit com dois paisreescreve seus commits em cima da nova base
Históricopreserva o que aconteceu de fatolinear, mais fácil de ler
Hashespreservadostodos novos
Seguro em branch compartilhadosimnão

A regra que evita 90% dos acidentes: rebase só em commits que ainda não foram pushados. Rebasear algo que outra pessoa já puxou reescreve o passado dela, e a reconciliação é feia.

O fluxo saudável para trabalho solo, que é o seu caso aqui:

bash
git switch -c feat/lesson05-memory     # branch a partir de main
# ... commits pequenos, um por ideia ...
git switch main
git pull --rebase                       # traz o remoto sem commit de merge
git merge --no-ff feat/lesson05-memory  # preserva o agrupamento do trabalho
git branch -d feat/lesson05-memory

O --no-ff força um commit de merge mesmo quando o fast-forward seria possível. Custa um commit e ganha uma coisa: fica registrado no histórico quais commits formavam uma unidade de trabalho.

Os dois comandos que salvam

git reflog lista todo lugar onde o HEAD já esteve, incluindo commits que nenhum branch alcança mais. Quase tudo que parece perdido está lá, e volta com git reset --hard <hash>. Ele guarda 90 dias por padrão.

git log --oneline --graph --all desenha a topologia real dos branches. Quando o estado do repositório não faz sentido, é a primeira coisa a rodar.

ConteúdoAula 06 · Atividade 08

O repositório de um engenheiro de dados

05 min

O que um revisor — ou um entrevistador — procura nos primeiros dois minutos.

estrutura
pipeline-de-vendas/
├── README.md              # o que é, como rodar, como testar
├── pyproject.toml         # dependências com versão travada
├── .gitignore
├── .env.example           # os NOMES das variáveis, nunca os valores
├── src/
│   └── sales_pipeline/
│       ├── extract.py
│       ├── transform.py
│       └── load.py
├── tests/
│   └── test_transform.py
└── data/
    └── samples/           # amostra pequena, versionada, para os testes
        └── sales.jsonl

Quatro coisas fazem a diferença entre um repositório que passa e um que impressiona:

Um README que responde três perguntas

O que este projeto faz, como eu rodo, como eu rodo os testes. Nessa ordem, nas primeiras vinte linhas. Um README que começa com a arquitetura antes de dizer o comando para rodar é um README que ninguém lê até o fim.

Dá para rodar sem te perguntar nada

Clonou, instalou, rodou os testes, passou. Se for preciso um bucket, uma credencial ou um arquivo que não está no repo, os testes precisam funcionar com a amostra versionada. Este é o critério que mais reprova repositório de portfólio.

Segredo nenhum, nem no histórico

Um .env.example com os nomes das variáveis e valores fictícios. Se algum dia um segredo real entrou, rotacione — a atividade 06 explicou por quê.

O histórico é legível

Um git log --oneline que conta a construção do projeto vale mais que um parágrafo de README, porque não dá para falsificar depois.

Estudo e portfólio são repositórios diferentes

Este repositório aqui é o seu caderno: exercícios, tentativas, código que existe para aprender. Um repositório de portfólio é um produto: um pipeline que resolve um problema, com README, testes e histórico limpo. Misturar os dois prejudica os dois — o caderno fica engessado e o portfólio fica cheio de exercício.

6.3

O dado que não sai

medição

Reproduza a medição da atividade 06 com um arquivo seu de alguns MB: commite, regenere, commite de novo, remova com git rm --cached, adicione ao .gitignore, rode git gc --aggressive --prune=now e meça o .git nos quatro momentos.

Depois encontre os blobs órfãos: git rev-list --objects --all | grep sales. Eles ainda estão lá?

6.4

Separando um commit bagunçado

refactor

Num arquivo, faça duas mudanças não relacionadas ao mesmo tempo — uma correção de bug e um ajuste de formatação. Depois use git add -p para transformá-las em dois commits atômicos, com mensagens em Conventional Commits.

Se os hunks estiverem grudados

s divide um hunk em pedaços menores dentro do add -p; e abre o hunk para você editar linha a linha. É a saída quando as duas mudanças estão a três linhas de distância.
