ConteúdoAula 15 · Atividade 02

SCAN contra SEARCH

06 min

Duas palavras no plano, e a diferença entre elas é a aula inteira.

sql — 400.000 linhas, sem índice
EXPLAIN QUERY PLAN
SELECT id, amount FROM orders WHERE user_id = 12345;
Saída realSCAN orders tempo: 20.03 ms
sql — depois de um índice
CREATE INDEX idx_orders_user ON orders(user_id);
EXPLAIN QUERY PLAN
SELECT id, amount FROM orders WHERE user_id = 12345;
Saída realSEARCH orders USING INDEX idx_orders_user (user_id=?) tempo: 0.01 ms

2.000 vezes. E o motivo está nas duas palavras:

SCANSEARCH
Lêtodas as linhassó as que casam
CustoO(n)O(log n)
Cresce com a tabelasim, linearmentequase nada
No plano do PostgreSQLSeq ScanIndex Scan

Um índice é uma árvore B ordenada pela coluna, apontando de volta para a linha. Procurar nela é descer a árvore — o mesmo salto de complexidade do set contra a list na aula 07, e por uma razão parecida: estrutura de busca em vez de varredura.

SCAN nem sempre é problema

Numa tabela de 200 linhas, varrer é mais rápido que descer uma árvore e depois buscar cada linha. O planejador sabe disso e escolhe SCAN de propósito. SCAN só é um alerta quando a tabela é grande e o filtro é seletivo — e "grande" e "seletivo" são medidas, não impressões.

Rode ANALYZE antes de acreditar no plano

O planejador decide com base em estatísticas sobre a distribuição dos dados. Sem ANALYZE, ele chuta. Um plano ruim que melhora depois de um ANALYZE é sinal de estatística desatualizada, não de índice faltando.

ConteúdoAula 15 · Atividade 03

Índice composto e a ordem das colunas

07 min

Um índice sobre duas colunas não é dois índices. A ordem em que você declara decide quais queries ele atende.

sql
CREATE INDEX idx_status_date ON orders(status, created_at);
Saída realWHERE status='paid' AND created_at='2026-03-05' SEARCH orders USING COVERING INDEX idx_status_date (status=? AND created_at=?) tempo: 0.00 ms WHERE status='paid' SEARCH orders USING COVERING INDEX idx_status_date (status=?) tempo: 5.28 ms WHERE created_at='2026-03-05' SEARCH orders USING COVERING INDEX idx_status_date (ANY(status) AND created_at=?) tempo: 0.00 ms

Os dois primeiros são o esperado: o índice atende o prefixo da esquerda. Pense numa lista telefônica ordenada por (sobrenome, nome) — dá para achar "todos os Silva" e "Silva, João", mas não "todos os João".

O terceiro caso contraria a regra — e vale entender por quê

Filtrar só por created_at não usa o prefixo, e mesmo assim o plano diz ANY(status) AND created_at=?. Isso é um skip-scan: como status só tem três valores distintos, o planejador percorre os três e faz uma busca dentro de cada um. Três buscas continuam sendo muito melhor que varrer 400 mil linhas.

Não conte com o skip-scan

Ele só compensa quando a coluna da esquerda tem pouquíssimos valores distintos. Se status fosse user_id, com 50 mil valores, seriam 50 mil buscas e o planejador voltaria a varrer. A regra do prefixo à esquerda continua sendo a que você usa para projetar; o skip-scan é um bônus que o banco às vezes te dá.

E nem todo banco tem: MySQL não faz skip-scan em índice B-tree comum, PostgreSQL passou a fazer só na 18.

Como escolher a ordem

Igualdade antes de intervalo

WHERE status = 'paid' AND created_at > '2026-01-01' quer (status, created_at). Com (created_at, status), o índice consegue posicionar no intervalo mas precisa filtrar status linha a linha dentro dele.

Mais seletiva primeiro, entre iguais

Se as duas são igualdade, ponha antes a que corta mais linhas. Menos entradas do índice a percorrer.

A coluna do ORDER BY por último

Um índice (status, created_at) atende WHERE status=? ORDER BY created_at sem ordenar nada — as linhas já saem na ordem. É o SORT que some do plano.

Um índice composto substitui vários

(a, b, c) atende (a), (a, b) e (a, b, c). Criar os três separados é pagar três vezes na escrita para ter o que um já dava.

ConteúdoAula 15 · Atividade 04

Índice de cobertura

05 min

A palavra COVERING apareceu nos planos da atividade anterior. Ela significa que o banco respondeu a query sem tocar na tabela.

sql
SELECT user_id, amount FROM orders WHERE user_id BETWEEN 100 AND 200;
Saída realcom idx(user_id): SEARCH orders USING INDEX idx_orders_user (user_id>? AND user_id<?) tempo: 0.61 ms com idx(user_id, amount): SEARCH orders USING COVERING INDEX idx_cover (user_id>? AND user_id<?) tempo: 0.32 ms

Metade do tempo, e a razão é o que não aconteceu. No primeiro caso o banco encontra as entradas no índice e depois vai buscar cada linha na tabela para pegar o amount — um salto por linha encontrada. No segundo, o amount já está no índice, e a tabela nunca é lida.

Onde isso vale muito mais que 2x

Aqui a tabela está em memória. Num banco real, cada salto é uma leitura de página que pode ir ao disco. Uma query que devolve 10 mil linhas faz 10 mil saltos aleatórios — e é a diferença entre milissegundos e minutos. Índice de cobertura é uma das otimizações de maior retorno em relatório.

Como projetar um

sql
-- a query que você quer cobrir
SELECT user_id, status, SUM(amount)
FROM orders
WHERE created_at >= '2026-01-01'
GROUP BY user_id, status;

-- o índice: filtro primeiro, depois agrupamento, depois o que é só lido
CREATE INDEX idx_cover ON orders(created_at, user_id, status, amount);

A regra é olhar a query e listar todas as colunas que aparecem — no WHERE, no GROUP BY, no ORDER BY e no SELECT. Se todas estiverem no índice, ele cobre.

O limite: SELECT *

Nenhum índice cobre um SELECT * numa tabela com vinte colunas — você teria que indexar a tabela inteira, e o índice ficaria do tamanho dela. É mais um motivo, além dos óbvios, para listar as colunas que você realmente usa.

Em PostgreSQL há uma variante melhor: CREATE INDEX ... ON orders(created_at) INCLUDE (amount). As colunas do INCLUDE ficam só nas folhas, não na estrutura de busca — cobre igual, e o índice fica menor.

Mão na massaAula 15 · Atividade 05

O índice que sumiu

06 min

Duas queries que fazem a mesma pergunta — quantos pedidos em março — sobre a mesma tabela, com o mesmo índice em created_at.

sql
-- A
SELECT COUNT(*) FROM orders
 WHERE created_at >= '2026-03-01' AND created_at < '2026-04-01';

-- B
SELECT COUNT(*) FROM orders
 WHERE substr(created_at, 1, 7) = '2026-03';
Prever antes de rodar
Sua resposta fica salva neste navegador.
EXPLAIN QUERY PLAN + tempo
A  intervalo (sargable)
     SEARCH orders USING COVERING INDEX idx_status_date (... created_at>? AND created_at<?)
     tempo:  1.97 ms

B  substr() na coluna
     SCAN orders USING COVERING INDEX idx_status_date
     tempo: 31.96 ms

16 vezes, e repare na palavra que mudou: SEARCH virou SCAN.

O índice guarda os valores de created_at, ordenados. Ele não guarda substr(created_at, 1, 7) — e o banco não tem como saber que essa função preserva a ordem. Então ele faz a única coisa possível: percorre tudo, aplicando a função linha a linha.

A palavra é sargable

De Search ARGument ABLE: um predicado é sargable quando o banco consegue traduzi-lo numa busca no índice. A regra é uma só — deixe a coluna sozinha de um lado da comparação.

Não sargableReescreva como
substr(d,1,7) = '2026-03'd >= '2026-03-01' AND d < '2026-04-01'
YEAR(d) = 2026d >= '2026-01-01' AND d < '2027-01-01'
UPPER(city) = 'SP'guarde normalizado, ou índice sobre UPPER(city)
amount * 1.1 > 100amount > 100 / 1.1
city LIKE '%paulo'nada resolve — LIKE com curinga à esquerda nunca usa índice B-tree
d::text = '2026-03-05'compare no tipo da coluna, sem conversão
A conversão implícita é a pior delas

Comparar uma coluna varchar com um número, ou timestamp com string, faz o banco converter a coluna — e o índice morre sem que nada apareça na query. Você olha e vê uma comparação simples; o plano diz SCAN. Confira o tipo dos dois lados sempre que um índice "não estiver sendo usado".

ConteúdoAula 15 · Atividade 06

O que um índice custa

06 min

A conversa sobre índices costuma parar na leitura. O custo aparece do outro lado — e em ETL, que é escrita em volume, ele domina.

python — 200.000 inserts
sem índice     :  112.6 ms
com 2 índices  :  312.9 ms   -> 2.8x

Cada INSERT passou a fazer três trabalhos: escrever a linha e atualizar duas árvores. Cada UPDATE numa coluna indexada é uma remoção mais uma inserção na árvore. Cada DELETE mexe em todas.

CustoImpacto
Escrita mais lentaproporcional ao número de índices
Espaço em discoum índice grande pode passar da metade da tabela
Memória de cacheíndice compete com dados pelo buffer pool
Manutençãofragmentação, REINDEX, estatísticas
O padrão de carga em massa
sql
DROP INDEX idx_orders_user;
-- carga em lotes, como no batched da aula 04
CREATE INDEX idx_orders_user ON orders(user_id);
ANALYZE;

Construir o índice de uma vez no fim é mais rápido que mantê-lo atualizado linha a linha — o banco ordena tudo e monta a árvore em uma passada. Vale quando a carga é grande em relação à tabela; não vale numa carga incremental de mil linhas.

Índice parcial: pague só pela fatia que interessa

sql
CREATE INDEX idx_pending ON orders(created_at) WHERE status = 'pending';

Ele indexa 133.385 das 400.000 linhas — um terço do tamanho, um terço do custo de escrita, e atende as queries que filtram por status = 'pending'.

E ele não foi usado

Criei esse índice e rodei a query que ele deveria atender. O plano escolheu outro:

Saída realSEARCH orders USING COVERING INDEX idx_status_date (status=? AND created_at>?) tempo: 3.53 ms

O idx_status_date já existente cobria a query — respondia sem tocar na tabela — enquanto o parcial exigiria um salto por linha. O planejador escolheu certo, e o índice novo virou custo puro.

A lição: criar um índice não significa que ele será usado. Sempre confira com EXPLAIN depois de criar, e apague o que o planejador ignora.

ConteúdoAula 15 · Atividade 07

Particionamento

06 min

Índice acelera achar a agulha. Particionamento serve para quando você quer o palheiro inteiro de um mês — e não quer nem tocar nos outros.

Uma tabela particionada é logicamente uma só, e fisicamente várias. O critério mais comum em dados é a data:

sql — PostgreSQL
CREATE TABLE orders (
    id bigint, user_id int, status text, created_at date, amount numeric
) PARTITION BY RANGE (created_at);

CREATE TABLE orders_2026_03 PARTITION OF orders
    FOR VALUES FROM ('2026-03-01') TO ('2026-04-01');

O ganho tem nome: partition pruning. Um WHERE created_at >= '2026-03-01' faz o planejador descartar as outras partições antes de ler qualquer coisa — e isso aparece no EXPLAIN como partições que simplesmente não estão no plano.

GanhoPor quê
Leitura de um períodoas outras partições nem são abertas
Apagar dados antigosDROP TABLE da partição: instantâneo, contra um DELETE de horas
Índices menoresuma árvore por partição, cada uma cabe no cache
ManutençãoVACUUM e REINDEX por partição
Quando ele atrapalha

Se a query não filtra pela chave de partição, o banco lê todas — e agora com o overhead de coordenar cem tabelas. Particionar por created_at uma tabela cujas consultas filtram por user_id deixa tudo mais lento. A chave de partição tem que ser a coluna que o filtro usa.

E cuidado com o excesso: mil partições diárias fazem o planejamento da query custar mais que a execução. Mensal costuma ser o ponto certo.

Em arquivos, é a mesma ideia

estrutura
warehouse/orders/
├── year=2026/month=01/part-00000.parquet
├── year=2026/month=02/part-00000.parquet
└── year=2026/month=03/part-00000.parquet

É a saída particionada que você escreveu no exercício 8.4, com o nome do diretório carregando o valor da chave. Spark, DuckDB e Athena leem essa convenção e fazem o mesmo pruning — um WHERE month = 3 abre um arquivo em vez de doze.

A ponte com a fase 2

Este é o conceito de maior transferência da fase 1 para a 2. Partição em Spark, arquivo Parquet particionado, predicate pushdown e partition pruning são todos a mesma ideia: organizar os dados de forma que a maior parte deles nunca precise ser lida.

Para saber maisAula 15 · Atividade 08

Lendo um plano de verdade

05 min

O EXPLAIN QUERY PLAN do sqlite é minimalista de propósito. Num banco de produção você tem muito mais — e mais chance de se enganar.

sql — PostgreSQL
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT ...;

EXPLAIN estima; EXPLAIN ANALYZE executa

Sem ANALYZE, os números são previsão do planejador. Com, são medição — e a query roda de verdade, inclusive se for um DELETE. Envolva em transação e faça rollback quando for query de escrita.

Compare rows estimado com actual rows

É a informação mais útil do plano inteiro. Uma estimativa de 100 linhas contra 100 mil reais significa estatística desatualizada — e explica por que ele escolheu um plano ruim. A correção é ANALYZE, não um índice novo.

BUFFERS mostra o que veio do disco

shared read alto contra shared hit é I/O de verdade. Uma query "lenta" com tudo em hit não tem problema de I/O — tem problema de CPU ou de estar processando linhas demais.

O custo é acumulado, e os filhos vêm primeiro

Leia de dentro para fora. O tempo de um nó inclui o dos filhos, então o gargalo é onde o tempo aumenta muito em relação ao nó de baixo.

Os três sinais que valem procurar primeiro

Seq Scan em tabela grande com filtro seletivo. Nested Loop com muitas linhas no lado de fora — cada uma dispara uma busca. E Sort com Sort Method: external merge, que significa que a ordenação não coube na memória e foi para o disco.

Meça a query, não só o plano

Plano bonito e query lenta acontece. E o contrário também: um Seq Scan numa tabela de 500 linhas é o plano certo. O plano explica o porquê do tempo; quem decide se há problema é o cronômetro — do mesmo jeito que na aula 05.

MétodoAula 15 · Atividade 09

Um método para otimizar

04 min

Otimizar por palpite é caro: cada índice criado "por precaução" custa escrita para sempre. Vale ter uma ordem.

  1. Meça primeiro. Qual query, quantas vezes por dia, quanto tempo cada uma. Uma query de 2 s que roda uma vez por noite não é problema; uma de 50 ms que roda 100 mil vezes é.
  2. Leia o plano. SCAN em tabela grande? SORT que não precisava? Estimativa muito longe do real?
  3. Conserte a query antes do esquema. Predicado não sargable, SELECT *, subquery correlacionada que vira JOIN. Não custa nada e frequentemente resolve.
  4. Rode ANALYZE. Antes de criar índice, garanta que o planejador tem estatística boa.
  5. Aí sim, o índice — um, o mais específico que atenda o padrão de filtro. Confirme com EXPLAIN que ele está sendo usado.
  6. Meça de novo, e meça também a escrita.
  7. Se ainda não bastar, aí é particionamento, materialização, ou repensar o modelo.
Os três atalhos que dão errado

Indexar toda coluna do WHERE. Dez índices numa tabela de escrita intensa, e o planejador escolhe um só. Você pagou dez.

Copiar índice de outro ambiente. O que serve para o banco de relatório não serve para o transacional — as queries são outras.

Otimizar antes de medir. A intuição sobre o que é lento erra na maioria das vezes; foi o que a aula 05 mostrou quatro vezes seguidas.

Índices que ninguém usa

PostgreSQL tem pg_stat_user_indexes, com idx_scan por índice. Um índice com idx_scan = 0 depois de um mês é custo puro de escrita — apague. É a limpeza de maior retorno e a que ninguém faz.
