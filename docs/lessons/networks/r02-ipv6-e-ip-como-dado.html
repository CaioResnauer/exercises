128 bits e as muitas formas de escrever um endereço

07 min

Um IPv6 é um inteiro de 128 bits, escrito em oito grupos de 16 bits em hexadecimal. A ideia é a mesma do IPv4; o que muda é que a escrita tem regras de abreviação, e cada sistema aplica as regras de um jeito.

python
import ipaddress

forms = ["2001:0DB8:0010:0020:0000:0000:0000:0025", "2001:db8:10:20:0:0:0:25",
         "2001:db8:10:20::25", "2001:DB8:10:20::0025"]
addresses = {ipaddress.ip_address(f) for f in forms}
print(len(forms), "textos,", len(addresses), "endereço")

ip = ipaddress.ip_address("2001:db8:10:20::25")
print(ip.compressed)
print(ip.exploded)
print(int(ip))
Saída real4 textos, 1 endereço 2001:db8:10:20::25 2001:0db8:0010:0020:0000:0000:0000:0025 42540766411301936260313629377154777125

Quatro textos diferentes, um endereço só. As duas abreviações permitidas são:

  • Zeros à esquerda de cada grupo podem sumir: 0db8 vira db8, 0025 vira 25;
  • Uma sequência de grupos inteiros de zero vira ::, uma única vez por endereço. Duas vezes seria ambíguo: não daria para saber quantos zeros vão em cada lado.

E como hexadecimal não liga para maiúscula, DB8 e db8 também são iguais. Para não depender de cada ferramenta, existe uma forma canônica (RFC 5952): minúsculas, sem zero à esquerda, e o :: na maior sequência de zeros, a primeira se houver empate, nunca para um grupo só.

python
for text in ("2001:db8:0:0:1:0:0:1", "2001:db8:0:1:0:0:0:1", "2001:db8:0:1:1:1:1:1"):
    print(f"{text:<24} -> {ipaddress.ip_address(text)}")
Saída real2001:db8:0:0:1:0:0:1 -> 2001:db8::1:0:0:1 2001:db8:0:1:0:0:0:1 -> 2001:db8:0:1::1 2001:db8:0:1:1:1:1:1 -> 2001:db8:0:1:1:1:1:1

É isso que o compressed do ipaddress produz, e o exploded faz o contrário: os 32 dígitos, sem abreviação nenhuma.

Como isso vira número errado

O CMDB grava o que o discovery leu do Windows (2001:DB8:10:20::25), o DHCPv6 exporta outra forma, o firewall outra. Um COUNT(DISTINCT ip) sobre a coluna de texto conta o mesmo servidor três vezes, e um join entre as fontes não acha nada. Nenhum erro, só um inventário com o triplo de endereços e zero reconciliação. É o exercício N2.1.

A regra, de novo

Mesma regra da R01, com mais motivo: converta na entrada. Se a coluna precisa ser texto (um CSV, uma chave de cache), grave compressed e nunca outra coisa.

ConteúdoAula R02 · Atividade 03

O /64 e a sub-rede que nunca enche

06 min

Em IPv4 você escolhe o tamanho da sub-rede pela quantidade de hosts. Em IPv6, uma rede de usuários é /64 sempre, tenha ela três máquinas ou três mil.

python
import ipaddress

lan = ipaddress.ip_network("2001:db8:10:20::/64")
site = lan.supernet(new_prefix=48)
print("site      ", site)
print("lan       ", lan)
print("endereços ", f"{lan.num_addresses:,}")
print("/64 por /48", f"{2 ** (64 - 48):,}")

host = ipaddress.ip_address("2001:db8:10:20:21a:2bff:fe3c:4d5e")
groups = host.exploded.split(":")
print("prefixo global", ":".join(groups[:3]), "| sub-rede", groups[3], "| interface", ":".join(groups[4:]))
Saída realsite 2001:db8:10::/48 lan 2001:db8:10:20::/64 endereços 18,446,744,073,709,551,616 /64 por /48 65,536 prefixo global 2001:0db8:0010 | sub-rede 0020 | interface 021a:2bff:fe3c:4d5e

O desenho típico de uma empresa: o provedor ou o registro entrega um /48 por site; os 16 bits seguintes numeram as sub-redes (65.536 por site); os 64 bits finais são o identificador de interface, a parte do host. O endereço se lê em três pedaços fixos, sem número mágico: os três primeiros grupos são o site, o quarto é a sub-rede, os quatro últimos são o host.

Por que sempre /64

Porque a autoconfiguração (SLAAC, atividade 05) precisa de exatamente 64 bits para o host montar o próprio endereço. Uma LAN com prefixo diferente de /64 quebra esse mecanismo. Prefixos mais longos aparecem em casos específicos, como /127 em link entre roteadores e /128 em loopback, que são o equivalente do /31 e do /32 da aula anterior.

Quando a métrica de utilização NÃO ajuda

Uma /64 tem 18 quintilhões de endereços. Com 3.000 máquinas a utilização é 0,000000000000016%, e com 30 mil continua zero para qualquer arredondamento. Copiar o mart_subnet_utilization de IPv4 para IPv6 produz uma coluna de zeros. Em IPv6 o que se acompanha é outra coisa: quantas /64 de cada /48 já foram alocadas, quantos hosts ativos por /64 (para dimensionar tabela de vizinhos no switch) e quantos endereços cada host usa.

Em IPv4 o tipo do endereço é exceção. Em IPv6 toda interface tem pelo menos dois tipos ao mesmo tempo, e confundir um com o outro estraga a reconciliação.

IPv6 não tem broadcast. O que fazia esse papel agora é multicast, e por isso não existe "endereço de broadcast" a descontar da sub-rede.

python
seen = ["2001:db8:10:20::25", "fe80::21a:2bff:fe3c:4d5e", "fd12:3456:789a:1::10",
        "ff02::1", "::1", "::ffff:10.20.1.7", "2606:4700:4700::1111"]

for text in seen:
    ip = ipaddress.ip_address(text)
    flags = [name for name in ("is_global", "is_private", "is_link_local", "is_multicast",
                               "is_loopback") if getattr(ip, name)]
    print(f"{text:<26} {' '.join(flags):<26} mapped={ip.ipv4_mapped}")
Saída real2001:db8:10:20::25 is_private mapped=None fe80::21a:2bff:fe3c:4d5e is_private is_link_local mapped=None fd12:3456:789a:1::10 is_private mapped=None ff02::1 is_global is_multicast mapped=None ::1 is_private is_loopback mapped=None ::ffff:10.20.1.7 is_private mapped=10.20.1.7 2606:4700:4700::1111 is_global mapped=None

Duas leituras desta saída. A primeira: o fe80::... é a forma link-local do mesmo host do primeiro exemplo da atividade 03 (repare no final 21a:2bff:fe3c:4d5e); o discovery costuma trazer os dois, e só o global serve para reconciliar. A segunda: ff02::1, que é multicast de escopo de enlace, sai com is_global=True. As propriedades do ipaddress seguem o registro da IANA, e o registro não foi feito para classificar inventário.

A regra, igual à da R01

Para classificar, use uma lista ordenada de (tipo, bloco) e teste pertinência. As flags servem como conferência, não como classificador. É o exercício N2.3.

SLAAC, EUI-64 e o host com cinco endereços

08 min

Em IPv4 quem dá o endereço é o DHCP, e o lease fica registrado. Em IPv6 o host pode montar o próprio endereço sozinho, e aí não existe lease nenhum para o seu relatório ler.

Como o host se configura

O roteador anuncia periodicamente o prefixo da rede (Router Advertisement). O host pega o /64 anunciado e completa os 64 bits do identificador de interface por conta própria. Isso é a SLAAC, autoconfiguração sem estado (RFC 4862). Existem três jeitos de completar esses 64 bits:

MétodoIdentificador vem deConsequência para os dados
EUI-64o MAC da placaestável; dá para recuperar o MAC a partir do IPv6
Estável e opacohash de prefixo e segredo do hostestável na rede, mas não revela o MAC
Temporário (privacidade)aleatório, troca periodicamenteo mesmo notebook aparece com endereços novos ao longo do dia

Servidores e equipamentos de rede costumam usar endereço fixo ou DHCPv6 com reserva. Notebooks e celulares, com Windows, macOS, iOS e Android modernos, usam endereços temporários por padrão. É isso que faz um único host ter cinco IPv6 numa tabela de vizinhos.

O EUI-64, montado à mão

O método é mecânico: parte o MAC de 48 bits ao meio, enfia ff:fe no meio para chegar a 64 bits, e inverte o sétimo bit do primeiro byte (o bit universal/local).

python
def slaac_eui64(prefix: str, mac: str) -> ipaddress.IPv6Address:
    """Build the SLAAC address a host derives from its MAC (modified EUI-64)."""
    octets = bytearray(int(part, 16) for part in mac.split(":"))
    octets[0] ^= 0x02                                  # flip the universal/local bit
    interface_id = bytes(octets[:3]) + b"\xff\xfe" + bytes(octets[3:])
    network = ipaddress.ip_network(prefix)
    return network.network_address + int.from_bytes(interface_id, "big")

print(slaac_eui64("2001:db8:10:20::/64", "a4:5e:60:d1:22:9f"))
print(slaac_eui64("fe80::/64", "a4:5e:60:d1:22:9f"))
Saída real2001:db8:10:20:a65e:60ff:fed1:229f fe80::a65e:60ff:fed1:229f

O MAC a4:5e:60:d1:22:9f virou a65e:60ff:fed1:229f: o a4 virou a6 por causa do bit invertido, e o ff:fe está no meio. O mesmo identificador aparece no global e no link-local, só o prefixo muda.

Por que isso interessa a quem reconcilia inventário

O caminho de volta também é mecânico. Se um IPv6 tem ff e fe no meio do identificador de interface (os bytes 11 e 12, contando do zero), você extrai o MAC, e o MAC é a chave que liga o endereço ao CMDB e à porta do switch. É uma reconciliação de graça que pouca gente conhece; o exercício N2.2 pede a função inversa.

Quando NÃO funciona

Endereço temporário e endereço estável-opaco não carregam MAC: o ff:fe não está lá e não há o que extrair. E mesmo quando está, o MAC pode ser aleatório: celulares e notebooks modernos usam MAC privado por rede, e o bit local ligado denuncia isso. Um MAC extraído com segundo dígito hexadecimal 2, 6, A ou E é administrado localmente e provavelmente não bate com nada no CMDB.

Prever o endereço SLAAC

05 min

Uma impressora com MAC 00:1a:2b:3c:4d:5e entra na rede 2001:db8:10:20::/64 e usa EUI-64. Escreva o endereço global dela na forma canônica.

Dois cuidados: o bit invertido muda o primeiro byte, e a forma canônica tira os zeros à esquerda de cada grupo.

Prever antes de rodar
Sua resposta fica salva neste navegador.
saída real — slaac_eui64("2001:db8:10:20::/64", "00:1a:2b:3c:4d:5e")
2001:db8:10:20:21a:2bff:fe3c:4d5e

O primeiro byte 00 com o bit universal/local invertido vira 02, e o grupo 021a perde o zero à esquerda: 21a. O resto é o MAC com ff:fe no meio: 2bff, fe3c, 4d5e.

Os dois erros mais comuns são esquecer o bit (e escrever 1a:2bff:..., que é outro endereço) e colocar o fffe no lugar errado, depois dos três primeiros grupos em vez dos três primeiros bytes do MAC. É o mesmo endereço do primeiro host da atividade 03: agora você sabe de onde ele veio.

ConteúdoAula R02 · Atividade 07

Dual-stack e o IPv4 disfarçado de IPv6

06 min

Quase nenhuma rede corporativa é só IPv6. O normal é dual-stack: cada equipamento tem IPv4 e IPv6 ao mesmo tempo, o DNS responde os dois, e o cliente prefere IPv6 quando consegue.

O que muda no modelo de dados

Um dispositivo deixa de ter "um IP". Tem zero ou um IPv4, zero a vários IPv6 globais, um link-local por interface e, num notebook, uma coleção de temporários que muda ao longo do dia. Duas colunas ipv4 e ipv6 no cadastro do equipamento não comportam isso. O modelo que comporta é uma tabela de endereços com uma linha por (dispositivo, interface, endereço), a família, a origem (DHCP, SLAAC, estático, temporário) e o período em que foi visto. É o exercício N2.4, que é de modelagem e por escrito.

O IPv4 que chega escrito como IPv6

Um servidor dual-stack que escuta num socket IPv6 recebe as conexões IPv4 como endereços mapeados, ::ffff: seguido do IPv4. Muita aplicação grava isso no log assim mesmo:

python
inventory = {ipaddress.ip_address("10.20.1.7"), ipaddress.ip_address("10.20.1.8")}
log = ["::ffff:10.20.1.7", "::ffff:10.20.1.8", "2001:db8:10:20::25"]   # dual-stack web server

raw = [ipaddress.ip_address(x) for x in log]
print("casam sem normalizar:", sum(ip in inventory for ip in raw))

normal = [ip.ipv4_mapped or ip for ip in raw]
print("casam normalizando  :", sum(ip in inventory for ip in normal))
Saída realcasam sem normalizar: 0 casam normalizando : 2

O log do servidor web tinha dois clientes do inventário, e o join achou zero. O ipv4_mapped devolve o IPv4 de dentro, ou None se o endereço não é mapeado, e o or ip mantém os IPv6 de verdade como estão.

O mesmo erro, em SQL

No Postgres, '::ffff:10.20.1.7'::inet << '10.20.0.0/16'::cidr é falso (atividade 09): são famílias diferentes, e o banco não converte sozinho. Quem conta "acessos vindos da rede do site" sobre o log cru conta zero para os clientes IPv4 e não percebe, porque os clientes IPv6 continuam aparecendo.

Guardar IP num banco: inteiro, bytes ou texto

07 min

Se o banco tem um tipo de rede, use. Se não tem, as alternativas são inteiro, bytes ou texto canônico, e cada uma quebra num lugar diferente.

python
for text in ("10.20.1.7", "192.168.1.1", "255.255.255.255"):
    ip = ipaddress.ip_address(text)
    as_signed = struct.unpack("!i", ip.packed)[0]      # what a signed 32-bit INT column holds
    print(f"{text:<16} {int(ip):>13,}   int32 com sinal: {as_signed:>14,}")

v6 = ipaddress.ip_address("2001:db8:10:20::25")
print(f"\nIPv6: {int(v6).bit_length()} bits, BIGINT vai até {2**63 - 1:,}")
print("packed:", len(ipaddress.ip_address("10.20.1.7").packed), "bytes e", len(v6.packed), "bytes")
Saída real10.20.1.7 169,083,143 int32 com sinal: 169,083,143 192.168.1.1 3,232,235,777 int32 com sinal: -1,062,731,519 255.255.255.255 4,294,967,295 int32 com sinal: -1 IPv6: 126 bits, BIGINT vai até 9,223,372,036,854,775,807 packed: 4 bytes e 16 bytes

Três fatos saem daqui. Um IPv4 cabe em 32 bits, mas sem sinal: de 128.0.0.0 para cima ele passa de 2.147.483.647, o limite de um INTEGER com sinal. O Postgres recusa o insert, o que é bom. Pior é a ferramenta que converte em silêncio: o 192.168.1.1 vira um número negativo, e a ordenação quebra.

python
ips = ["10.20.1.7", "127.0.0.1", "172.16.0.5", "192.168.1.1"]
as_int32 = {ip: struct.unpack("!i", ipaddress.ip_address(ip).packed)[0] for ip in ips}
print(sorted(ips, key=as_int32.get))
Saída real['172.16.0.5', '192.168.1.1', '10.20.1.7', '127.0.0.1']

Ordenado pelo inteiro com sinal, 172.16.0.5 e 192.168.1.1 vêm antes de 10.20.1.7. O segundo fato: um IPv6 tem 128 bits e não cabe em BIGINT nenhum. O terceiro: em bytes, os dois têm tamanho fixo (4 e 16), o que torna BINARY(16) uma coluna única para as duas famílias.

A linha que mais rende

A terceira. Como toda LAN IPv6 é /64, todos os endereços de uma sub-rede têm os mesmos 64 bits altos. "Este IPv6 está em qual /64?" deixa de ser range join e vira join de igualdade na parte alta, que qualquer motor executa com hash. O exercício N2.7 mede isso.

E o DuckDB?

Ela não rodou aqui: o ambiente desta aula não baixa extensões, e o INSTALL falhou com erro de rede. Na sua máquina, com internet, é uma linha. Por isso a próxima atividade mostra o DuckDB com a técnica que funciona em qualquer banco: inteiros.

db.executemany("INSERT INTO subnet VALUES (?, ?, ?)",
               [(str(n), int(n.network_address), int(n.broadcast_address)) for n in subnets])
db.executemany("INSERT INTO lease VALUES (?)", [(ip,) for ip in leases])
db.execute("CREATE INDEX ix_subnet_start ON subnet (net_start)")

between = """SELECT count(*) FROM lease l
             JOIN subnet s ON l.ip BETWEEN s.net_start AND s.net_end"""
t0 = time.perf_counter()
print("BETWEEN  :", db.execute(between).fetchone()[0], f"{time.perf_counter() - t0:.2f} s")
for row in db.execute("EXPLAIN QUERY PLAN " + between):
    print("   plano:", row[-1])
Saída realBETWEEN : 50000 1.98 s plano: SCAN l plano: SEARCH s USING INDEX ix_subnet_start (net_start<?)

O plano usa o índice, mas só para net_start < ?: para cada lease ele percorre todas as sub-redes que começam antes do IP, metade da tabela em média, e testa o fim de cada uma. Um índice B-tree resolve uma desigualdade, não duas. A saída é reescrever a pergunta: "qual é a última sub-rede que começa antes deste IP?" é uma busca de uma linha só, e depois basta conferir se o IP não passou do fim dela.

python — a mesma contagem, como busca do piso
floor = """SELECT count(*) FROM (
             SELECT l.ip,
                    (SELECT s.rowid FROM subnet s WHERE s.net_start <= l.ip
                     ORDER BY s.net_start DESC LIMIT 1) AS candidate
             FROM lease l) c
           JOIN subnet s ON s.rowid = c.candidate AND c.ip <= s.net_end"""
t0 = time.perf_counter()
print("floor    :", db.execute(floor).fetchone()[0], f"{time.perf_counter() - t0:.2f} s")
Saída realfloor : 50000 0.02 s

Mesmo resultado, quase cem vezes mais rápido. É a busca binária da R01 escrita em SQL: ORDER BY net_start DESC LIMIT 1 sobre um índice é o bisect.

DuckDB: o motor que já sabe

python — IP como UBIGINT, sem índice nenhum
query = """SELECT count(*) FROM lease l
           JOIN subnet s ON l.ip BETWEEN s.net_start AND s.net_end"""
t0 = time.perf_counter()
print("DuckDB BETWEEN:", con.execute(query).fetchone()[0], f"{time.perf_counter() - t0:.3f} s")

plan = con.execute("EXPLAIN " + query).fetchall()[0][1]
print("operador:", [line.strip("╭─ ┴┬╮") for line in plan.splitlines() if "Join ─" in line])
Saída realDuckDB BETWEEN: 50000 0.021 s operador: ['IE Join']

O DuckDB reconhece duas desigualdades no join e escolhe um IE Join, um algoritmo de join por desigualdade baseado em ordenação. Você escreve o BETWEEN ingênuo e ele faz o trabalho do piso sozinho.

Quando a técnica do piso NÃO serve

Ela supõe sub-redes que não se sobrepõem, exatamente como o bisect. Com a hierarquia do IPAM (bloco do site contendo as sub-redes), a última que começa antes do IP pode ser uma /24 vizinha, e o LEFT JOIN devolve "sem sub-rede" para um IP que estava no /16. Filtre a hierarquia antes (só as folhas) ou use o GiST, que entende contenção.

Na fase 2

No Spark não existe IE Join nem GiST. Um BETWEEN entre dois DataFrames grandes vira BroadcastNestedLoopJoin ou produto cartesiano. As saídas são as mesmas ideias desta atividade: transmitir a tabela de sub-redes se ela é pequena, ou criar uma chave de igualdade grosseira (o /16 em IPv4, os 64 bits altos em IPv6) para o join e filtrar o intervalo depois.

Link-local tratado como endereço do equipamento

É o caso acima, e o mesmo vale para reconciliação: um fe80:: no CMDB não liga o equipamento a nada fora do enlace. Filtre antes de deduplicar e antes de reconciliar.

Texto não canônico

COUNT(DISTINCT), GROUP BY e join sobre IPv6 em texto multiplicam o mesmo endereço por cada forma de escrita (atividade 02). Os números sobem, nenhum erro aparece.

IPv4 mapeado no log

O cliente IPv4 de um servidor dual-stack chega como ::ffff:10.20.1.7 e não casa com o inventário IPv4 (atividade 07). Normalize com ipv4_mapped antes do join.

IPv4 num inteiro de 32 bits com sinal

De 128.0.0.0 para cima vira negativo, e a ordenação e o BETWEEN quebram para metade do espaço de endereços (atividade 08). Use BIGINT ou inteiro sem sinal.

A zona do link-local

Um link-local pode vir com o nome da interface, fe80::1%eth0. Para o ipaddress ele é diferente de fe80::1:

Num set ou num GROUP BY, as duas formas viram dois endereços. Decida se a zona importa para a pergunta e normalize antes.

Dá zero para sempre (atividade 03). Um painel que mostra isso ao lado das sub-redes IPv4 sugere que o IPv6 não está sendo usado, quando a métrica é que não se aplica.
