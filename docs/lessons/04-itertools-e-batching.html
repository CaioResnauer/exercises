ConteúdoAula 04 · Atividade 02

islice — fatiar sem materializar

05 min

É o [a:b] para iteradores. A diferença com o fatiamento de lista é que nada é copiado e nada é materializado.

python
from itertools import islice

first_10    = islice(records, 10)         # primeiros 10
skip_5      = islice(records, 5, None)    # pula os 5 primeiros
window      = islice(records, 100, 200)   # do 100º ao 199º
every_other = islice(records, 0, None, 2)

Casos de uso diários: inspecionar as primeiras linhas de um arquivo gigante (list(islice(read_lines(path), 5))) e pular cabeçalhos.

Duas restrições que mordem

Não aceita índices negativos

islice(records, -5, None) levanta ValueError. E faz sentido: não dá para saber onde é o fim de um iterador sem consumi-lo inteiro. Um índice negativo exigiria bufferizar tudo — exatamente o que islice existe para evitar.

Pular consome de verdade

islice(gen, 1000, 1010) não teleporta para o item 1000: ele chama next() mil vezes e joga os resultados fora. Se a fonte é uma API paginada, isso são todas as requisições até a página do item 1010 — pagas, contadas no rate limit, e descartadas.

O que ele devolve

islice devolve um iterator, não uma lista. Isso é o ponto todo — mas guarde bem, porque no exercício 4.2 essa propriedade tem uma consequência que derruba muita gente.

ConteúdoAula 04 · Atividade 03

chain — concatenar fontes

04 min

Trata N fontes como se fossem uma só, sem juntar nada na memória.

python
from itertools import chain

all_records = chain(read_jsonl("jan.jsonl"), read_jsonl("feb.jsonl"))

E a variante que interessa mais, porque também é lazy na lista de fontes:

python
paths = (p for p in Path("data").glob("*.jsonl"))
all_records = chain.from_iterable(read_jsonl(p) for p in paths)

chain.from_iterable é o padrão para "processar N arquivos como se fossem um só" — extremamente comum em ingestão de dados particionados por data.

Repare no gerador dentro do from_iterable

O argumento é (read_jsonl(p) for p in paths), uma generator expression — não uma lista. Se fosse [read_jsonl(p) for p in paths], todos os read_jsonl seriam construídos de uma vez. Como read_jsonl é generator, construir não abre o arquivo ainda — mas o hábito de manter a lista de fontes lazy é o que faz a diferença quando a fonte é uma conexão, e não um arquivo.

ConteúdoAula 04 · Atividade 04

batched — o mais importante para DE

07 min · Python 3.12+

Se você levar uma única função desta aula para o resto da carreira, leve esta.

python
from itertools import batched

for batch in batched(records, 1_000):
    conn.execute_many(INSERT, batch)     # 1 round-trip a cada 1000 registros

Por que isso importa tanto

Inserir linha a linha no banco é o gargalo clássico de pipeline Python. Cada INSERT individual paga latência de rede mais overhead de transação. Agrupar em lotes de 500 a 5000 costuma dar ganhos de uma a duas ordens de grandeza — e continua sendo lazy: você nunca tem mais que um lote na memória.

O batching é o equilíbrio entre os dois extremos. Nem tudo na memória, nem um round-trip por registro.

EstratégiaMemóriaRound-trips
list(records) e um insert sóO(n)1
um insert por registroO(1)n
batched(records, k)O(k)n/k

Se você está em Python < 3.12

A receita equivalente, que é a que aparece na própria documentação do módulo:

python — a receita
def batched(iterable: Iterable[T], n: int) -> Iterator[tuple[T, ...]]:
    """Batch data into tuples of length n. The last batch may be shorter."""
    if n < 1:
        raise ValueError("n must be at least one")
    it = iter(iterable)
    while batch := tuple(islice(it, n)):
        yield batch

Vale ler essa implementação linha a linha — são cinco linhas com Python idiomático concentrado. Percorra o passo a passo abaixo antes de seguir; cada clique é uma linha executada, com [1, 2, 3, 4, 5] e n = 2.

Mão na massaAula 04 · Atividade 05

Por que o tuple() é obrigatório

05 min

A receita da atividade anterior tem uma peça que parece decoração e não é. Tire o tuple() e veja o que você acha que acontece.

python — o tuple() saiu
def batched(iterable, n):
    it = iter(iterable)
    batch = islice(it, n)
    while batch:
        yield batch
        batch = islice(it, n)


print(list(batched([1, 2, 3, 4, 5], 2)))
Prever antes de rodar
Sua resposta fica salva neste navegador.

Ele nunca termina. Interrompendo depois de alguns segundos, os valores produzidos são:

saída real — primeiros 6 valores
[(1, 2), (3, 4), (5,), (), (), ()]   # ... e assim para sempre

O laço produz os três lotes corretos e depois entra em regime permanente devolvendo lotes vazios, sem parar nunca.

A causa: while batch: pergunta se o objeto batch é verdadeiro. Quando batch é uma tupla, a resposta depende do conteúdo — () é falso. Quando batch é um objeto islice, a resposta é sempre verdadeiro, esgotado ou não.

python
from itertools import islice
print(bool(islice(iter([]), 3)))     # iterador vazio, fatia vazia
print(bool(tuple(islice(iter([]), 3))))
Saída realTrue False

O tuple() não está ali para "converter para tupla". Ele está ali para forçar a avaliação — trocar uma promessa de valores por valores de verdade, que é a única coisa que se pode testar.

A regra a levar

Um objeto lazy nunca sabe, e nunca pode dizer, se ainda tem itens. Perguntar if it: ou while it: a um iterador é sempre um bug — a resposta é True por padrão e não tem relação nenhuma com o conteúdo. A atividade 07 da aula 01 já tinha avisado por outro caminho: não existe hasNext() em Python.

ConteúdoAula 04 · Atividade 06

groupby — agrupamento lazy

07 min

A função mais útil e mais mal-entendida do módulo. Duas pegadinhas, e as duas saem da mesma raiz: ele é lazy.

python
from itertools import groupby

for date, group in groupby(records, key=lambda r: r["date"]):
    print(date, sum(r["amount"] for r in group))

Pegadinha 1 — ele só agrupa elementos consecutivos

Ele não é o GROUP BY do SQL nem o groupby do pandas. Se os dados não estiverem ordenados pela chave, você recebe o mesmo grupo várias vezes:

python
data = [("a", 1), ("b", 2), ("a", 3)]
result = {k: list(g) for k, g in groupby(data, key=lambda x: x[0])}
print(result)
Saída real{'a': [('a', 3)], 'b': [('b', 2)]}

O primeiro grupo 'a' foi sobrescrito pelo segundo. Note que não houve erro: o groupby emitiu três grupos, o dict comprehension colapsou dois deles, e o resultado é silenciosamente errado.

Isso é consequência direta da laziness. Agrupar de verdade exigiria ver o dataset inteiro antes de emitir o primeiro grupo — o oposto do que um iterador faz. Se você precisa disso, ou ordena antes (sorted, que é eager) ou acumula num defaultdict — e aceita o custo de memória nos dois casos.

Pegadinha 2 — o grupo é um iterador compartilhado

O objeto group é válido só até você avançar para o próximo grupo. Isto não funciona:

python — não faça isso
data = [("a", 1), ("a", 2), ("b", 3)]
groups = list(groupby(data, key=lambda x: x[0]))
print([(k, list(g)) for k, g in groups])
Saída real[('a', []), ('b', [])]

Todos os grupos saem vazios. O list() externo percorreu o groupby até o fim, e cada avanço invalidou o grupo anterior. Se precisa guardar, converta na hora:

python
groups = [(k, list(g)) for k, g in groupby(data, key=lambda x: x[0])]
Quando o groupby é imbatível

Quando a fonte já chega ordenada pela chave — arquivo particionado por data, resultado de ORDER BY, log cronológico. Aí ele agrupa em memória O(1): processa um grupo, descarta, passa ao próximo. Nenhuma alternativa chega perto disso. Volte a esta frase quando fizer o exercício 4.4.

Mão na massaAula 04 · Atividade 07

Ordenar ou acumular?

04 min

Uma fonte de 300 mil registros que já vem ordenada pela chave, e você quer a soma por grupo. Duas implementações:

python
# A — groupby direto na fonte
total = 0
for k, g in groupby(sorted_stream(), key=lambda x: x[0]):
    total += sum(v for _, v in g)

# B — defaultdict acumulando
dd = defaultdict(list)
for k, v in sorted_stream():
    dd[k].append(v)
total = sum(sum(v) for v in dd.values())
Prever antes de rodar
Sua resposta fica salva neste navegador.
tracemalloc — 300.000 registros, 300 grupos
A — groupby em streaming : pico   0.00 MB
B — defaultdict          : pico  11.70 MB

Quatro ordens de grandeza. O groupby nunca segurou mais que um grupo por vez; o defaultdict teve que segurar os 300 mil valores antes de conseguir responder qualquer coisa.

A condição que faz isso valer é "já vem ordenada". Se você precisar de um sorted() antes, ele materializa a fonte inteira e a vantagem evapora — os dois viram O(n), e aí a escolha passa a ser sobre outra coisa (ordem de saída, legibilidade), não sobre memória.

A pergunta certa

Não é "groupby ou defaultdict?". É "a minha fonte já está ordenada pela chave de agrupamento?" — e, se não estiver, "consigo pedir para ela vir ordenada?". Um ORDER BY no banco, ou ler as partições em ordem, transforma uma agregação O(n) em O(1) de graça.

ConteúdoAula 04 · Atividade 08

tee — duplicar um iterador

05 min

Resolve o problema do exercício 3.5 — duas saídas a partir de uma fonte — e traz junto um custo que quase ninguém mede antes de usar.

python
from itertools import tee
stream_a, stream_b = tee(records, 2)

O buffer escondido

tee guarda internamente todos os itens que um ramo já consumiu e o outro ainda não. Ele precisa: a fonte original só passa uma vez, e o ramo atrasado tem que receber o que já passou.

A consequência: se você consumir stream_a inteiro antes de tocar em stream_b, o tee terá bufferizado o dataset completo na memória — exatamente o que você estava tentando evitar ao usar generators.

O padrão que parece certo e é o pior caso
python
branch_a, branch_b = tee(records, 2)

for r in (x for x in branch_a if x.valid):      # drena branch_a até o fim
    valid_sink(r)
for r in (x for x in branch_b if not x.valid):  # branch_b lê tudo do buffer
    rejected_sink(r)

Legível, simétrico, e o pior caso possível para o tee: no fim do primeiro laço o buffer contém o dataset inteiro. Você vai medir isso no exercício 4.7.

A regra

tee só é seguro quando os ramos avançam mais ou menos juntos — tipicamente dentro de um mesmo zip ou de um mesmo laço. Para "processar todos os válidos, depois todos os inválidos", um único laço que roteia é melhor, mais simples e O(1).

E não use o original depois

Depois de tee(records, 2), o records original não deve mais ser consumido diretamente. Se você avançar nele, os dois ramos perdem os itens — e sem erro nenhum.

Não precisa decorar. Precisa saber que existem, para reconhecer quando o problema que você tem é um destes:

takewhile não é filter

takewhile para no primeiro item que falha o teste e nunca mais olha o resto; filter examina todos e descarta os que falham. Trocar um pelo outro num arquivo com cabeçalho no meio é um bug clássico.

ConteúdoAula 04 · Atividade 10

itertools vs pandas vs Spark

04 min

Vale ter isso claro para não virar o cara que faz tudo com generator por esporte.

CenárioFerramenta
Streaming de arquivo ou API, transformação linha a linha, memória apertadagenerators + itertools
Dados cabem na memória, operações colunares, joins, estatísticapandas / polars
Dados não cabem em uma máquinaSpark
Ingestão e limpeza antes de virar DataFramegenerators + itertools

O padrão que combina os dois

Muito comum e muito bom: generators para ingerir e limpar em streaming, batched para agrupar, e um DataFrame por lote. Memória constante, e ainda com a API rica do pandas.

python
for i, batch in enumerate(batched(clean_records(read_jsonl(path)), 50_000)):
    df = pd.DataFrame(batch)
    df.to_parquet(f"out/part-{i:05d}.parquet")

Isso é, literalmente, uma versão manual do que o Spark faz com partições — e o formato de saída particionado é o que você vai consumir na fase 2 do roadmap.

ConteúdoAula 04 · Atividade 11

Agregações em uma passada

03 min

Complemento natural do batching: agregar sem materializar.

python
total      = sum(r["amount"] for r in records)          # uma passada, O(1) de memória
maximum    = max(records, key=lambda r: r["amount"])    # idem
unique_ids = {r["id"] for r in records}                 # O(n) — consciente disso?

Note o contraste. Soma e máximo são O(1) de memória: cabem num acumulador de tamanho fixo. Deduplicação é O(n): para saber se um id já apareceu, é preciso lembrar de todos os que apareceram.

AgregaçãoMemóriaPor quê
sum, min, max, len, médiaO(1)acumulador de tamanho fixo
set, distinct, group by não ordenadoO(n)precisa lembrar do que já viu
sorted, mediana, percentilO(n)precisa do dataset inteiro
group by em fonte ordenadaO(1)um grupo por vez, e descarta
Ponte com a fase 2

Saber classificar uma agregação nesses termos é o que te permite prever se um pipeline vai escalar. E é exatamente o mesmo raciocínio que decide se uma operação no Spark causa shuffle: as O(1) desta tabela são as que o Spark resolve dentro da partição; as O(n) são as que obrigam a mover dados entre executores.

Múltiplos arquivos como um só

implementação

Usando chain.from_iterable, escreva read_partitioned(directory, pattern="*.jsonl") -> Iterator[dict] que lê todos os arquivos de um diretório como um fluxo único. O take faz parte da prova

A assinatura diz Iterator[dict]: cada item é um registro, não um iterador de registros. Se o seu teste tiver dois for aninhados, o de dentro está iterando as chaves de um dict — e a prova de laziness não prova nada.
