O nulo que não vira float

04 min

Na D01, passenger_count chegou no pandas como float64 por causa dos 140.162 nulos. O arquivo guarda a coluna como int64. Que tipo você acha que o Polars vai mostrar?

Prever antes de rodar
Sua resposta fica salva neste navegador.
python
import polars as pl

PATH = "data/yellow_tripdata_2024-01.parquet"

dropoffs = pl.read_parquet(PATH, columns=["DOLocationID", "passenger_count"])
print(dropoffs.schema)
print(f"{dropoffs.estimated_size('mb'):.1f} MB")
print(dropoffs.null_count())
Saída realSchema({'DOLocationID': Int32, 'passenger_count': Int64}) 34.0 MB shape: (1, 2) ┌──────────────┬─────────────────┐ │ DOLocationID ┆ passenger_count │ │ --- ┆ --- │ │ u32 ┆ u32 │ ╞══════════════╪═════════════════╡ │ 0 ┆ 140162 │ └──────────────┴─────────────────┘

Continua inteiro. O Polars guarda os dados no formato Arrow, em que cada coluna tem, ao lado dos valores, um mapa de bits que diz quais posições são nulas. Nulo não precisa de um valor especial como o NaN, então nenhum tipo é trocado. É o que o "Int8" anulável do pandas faz, só que aqui é o padrão.

Repare também no que não aparece: índice. Um DataFrame do Polars é só colunas. Isso tira da frente uma classe inteira de problemas do pandas, como o alinhamento por índice que muda um resultado sem avisar, e o reset_index() depois de cada agregação.

Expressões: filter, group_by e agg

05 min

No pandas você escolhe colunas com colchetes e aplica funções. No Polars você descreve o resultado com expressões, como pl.col("tip_amount").mean(), e entrega a descrição a um contexto (select, filter, with_columns, agg) que decide como executar.

O mesmo exemplo da D01, sem a forma de pagamento 0:

python
by_type = pl.read_parquet(PATH, columns=["payment_type", "tip_amount"])

summary = (
    by_type
    .filter(pl.col("payment_type") != 0)
    .group_by("payment_type")
    .agg(
        pl.len().alias("trips"),
        pl.col("tip_amount").mean().round(2).alias("avg_tip"),
    )
    .sort("payment_type")
)
print(summary)
Saída realshape: (4, 3) ┌──────────────┬─────────┬─────────┐ │ payment_type ┆ trips ┆ avg_tip │ │ --- ┆ --- ┆ --- │ │ i64 ┆ u32 ┆ f64 │ ╞══════════════╪═════════╪═════════╡ │ 1 ┆ 2319046 ┆ 4.17 │ │ 2 ┆ 439191 ┆ 0.0 │ │ 3 ┆ 19597 ┆ 0.01 │ │ 4 ┆ 46628 ┆ 0.04 │ └──────────────┴─────────┴─────────┘

A tradução da D01 é quase linha a linha:

Saída real(2964624, 3) shape: (3, 3) ┌──────────────┬────────────┬────────────────────┐ │ payment_type ┆ tip_amount ┆ tip_minus_type_avg │ │ --- ┆ --- ┆ --- │ │ i64 ┆ f64 ┆ f64 │ ╞══════════════╪════════════╪════════════════════╡ │ 2 ┆ 0.0 ┆ -0.002296 │ │ 1 ┆ 3.75 ┆ -0.419671 │ │ 1 ┆ 3.0 ┆ -1.169671 │ └──────────────┴────────────┴────────────────────┘

join: validate e o N/A que o Polars não converte

04 min

O join do Polars tem o mesmo contrato do merge da D01, com outro nome: validate="m:1". A diferença está em outro lugar, na leitura do CSV.

python
dropoffs = pl.read_parquet(PATH, columns=["DOLocationID"])

for label, zones in [("default    ", pl.read_csv("data/taxi_zone_lookup.csv")),
                     ("null_values", pl.read_csv("data/taxi_zone_lookup.csv", null_values="N/A"))]:
    joined = dropoffs.join(
        zones.select("LocationID", "Borough"),
        left_on="DOLocationID",
        right_on="LocationID",
        how="left",
        validate="m:1",
    )
    print(label, "| rows:", joined.height,
          "| null Borough:", joined["Borough"].null_count(),
          "| Borough == 'N/A':", (joined["Borough"] == "N/A").sum())
Saída realdefault | rows: 2964624 | null Borough: 0 | Borough == 'N/A': 11967 null_values | rows: 2964624 | null Borough: 11967 | Borough == 'N/A': 0

Mesma tabela de zonas, mesmo join, e o número de nulos vai de 0 a 11.967 conforme a leitura. O pl.read_csv só trata como nulo o campo vazio. O texto N/A continua texto, a não ser que você peça com null_values. O pandas faz o contrário: converte por padrão.

Nenhum dos dois está errado. O que dá errado é migrar um pipeline de pandas para Polars e o relatório de "viagens sem borough" ir de 11.967 para zero sem nenhum erro. Num job migrado, compare as contagens de nulos coluna a coluna antes de desligar a versão antiga.

E os tipos da chave?

DOLocationID é Int32 no Parquet e LocationID é Int64 no CSV. O join funcionou porque o Polars converte os dois inteiros para um tipo comum. Com texto de um lado e número do outro, ele levanta SchemaError, o que é bom: esse erro aparece na hora.

ConteúdoAula D02 · Atividade 06

Lazy: scan_parquet monta um plano

05 min

Tudo até aqui foi eager: cada linha de código executa na hora. Troque read_parquet por scan_parquet e nada é lido. Você recebe um LazyFrame, que é a descrição do que fazer.

python
cash_trips = (
    pl.scan_parquet(PATH)
    .filter(pl.col("payment_type") == 2)
    .group_by("DOLocationID")
    .agg(pl.col("trip_distance").mean().alias("avg_distance"))
)
print(type(cash_trips).__name__)   # nothing was read yet
print(cash_trips)                  # printing shows the plan, not data
Saída realLazyFrame naive plan: (run LazyFrame.explain(optimized=True) to see the optimized plan) AGGREGATE[maintain_order: false] [col("trip_distance").mean().alias("avg_distance")] BY [col("DOLocationID")] FROM FILTER col("payment_type") == 2 FROM Parquet SCAN [data/yellow_tripdata_2024-01.parquet] PROJECT */19 COLUMNS ESTIMATED ROWS: 2964624

Esse é o plano ingênuo: exatamente o que você escreveu, de baixo para cima. Ler as 19 colunas (PROJECT */19), depois filtrar, depois agregar. Nada rodou ainda. Os dados só são lidos quando você pede o resultado:

python
result = cash_trips.collect()
print(type(result).__name__, result.shape)
Saída realDataFrame (259, 2)

Essa separação tem nome, e vale guardar porque é a mesma do Spark:

  • Transformação: filter, group_by, agg, join, with_columns. Recebe um plano, devolve um plano maior. Não toca nos dados;
  • Ação: collect(). Pega o plano inteiro, otimiza e executa.

Como o otimizador vê o plano inteiro antes de executar, ele pode reescrever a ordem das coisas. É o que a próxima atividade mostra.

Mão na massaAula D02 · Atividade 07

Ler o plano otimizado

05 min

O plano ingênuo lê 19 colunas e filtra depois de ler. A consulta usa três colunas: payment_type, DOLocationID e trip_distance. O que muda no plano otimizado?

Prever antes de rodar
Sua resposta fica salva neste navegador.
python
print(cash_trips.explain())
Saída realAGGREGATE[maintain_order: false] [col("trip_distance").mean().alias("avg_distance")] BY [col("DOLocationID")] FROM simple π 2/2 ["DOLocationID", ... 1 other column] Parquet SCAN [data/yellow_tripdata_2024-01.parquet] PROJECT 3/19 COLUMNS SELECTION: col("payment_type") == 2 ESTIMATED ROWS: 2964624

Duas reescritas, e cada uma tem nome:

  • Projection pushdown: PROJECT */19 virou PROJECT 3/19. O otimizador descobriu sozinho quais colunas a consulta usa e passou a lista para o leitor do Parquet. É o columns= da D01, sem você escrever;
  • Predicate pushdown: o nó FILTER sumiu e o filtro virou SELECTION dentro do SCAN. As linhas são descartadas durante a leitura, antes de ocupar memória. Com as estatísticas de mínimo e máximo do Parquet, o leitor ainda pode pular blocos inteiros que não têm nenhuma linha que passe no filtro.

Quem erra costuma prever "lê 2 colunas", esquecendo que a coluna do filtro também precisa ser lida, ainda que não apareça no resultado. O simple π 2/2 logo acima do scan é a projeção final, já sem o payment_type.

Medir memória do Polars

03 min

Se no pandas o tracemalloc via 1,9 MB, no Polars ele não vê nada.

python
import resource
import tracemalloc

tracemalloc.start()
trips = pl.read_parquet(PATH)
_, peak = tracemalloc.get_traced_memory()
tracemalloc.stop()

print(f"tracemalloc peak   : {peak / 1e6:7.1f} MB")
print(f"estimated_size     : {trips.estimated_size('mb'):7.1f} MB")
print(f"process peak (RSS) : {resource.getrusage(resource.RUSAGE_SELF).ru_maxrss * 1024 / 1e6:7.1f} MB")
Saída realtracemalloc peak : 0.0 MB estimated_size : 376.3 MB process peak (RSS) : 539.3 MB

O Polars é escrito em Rust e aloca tudo fora do Python. As duas medidas da D01 continuam valendo, com um ajuste: estimated_size() faz o papel do memory_usage(deep=True), e o ru_maxrss continua sendo o pico do processo.

Compare com a D01, lendo o mês inteiro: 376,3 MB de DataFrame e 539 MB de pico no Polars, contra 418,0 MB e 1.077 MB no pandas. Boa parte da diferença vem de não haver a conversão do Arrow para o formato do pandas: o Polars já trabalha no Arrow.

A ponte para o PySpark

04 min

O modo lazy do Polars é a melhor porta de entrada para o Spark, porque o modelo mental é o mesmo. O que muda é que o Spark distribui o plano entre várias máquinas.

Polars lazyPySparkO que é
pl.scan_parquet(path)spark.read.parquet(path)ponto de partida do plano; nada é lido
filter, group_by, joinfilter, groupBy, jointransformações: aumentam o plano
collect()collect(), count(), show(), writeações: otimizam e executam
explain()df.explain()o plano, para conferir antes de rodar
SELECTION no scanPushedFilters no FileScan parquetpredicate pushdown
PROJECT 3/19ReadSchema com só as colunas usadasprojection pushdown

Duas diferenças importam já na primeira conversa sobre Spark:

  • Shuffle. No Polars, o group_by roda numa máquina só. No Spark, as linhas de uma mesma chave podem estar em executores diferentes, e o groupBy e o join precisam redistribuir os dados pela rede. É a parte cara de quase todo job, e aparece como Exchange no plano;
  • Join com tabela pequena. A tabela de zonas tem 265 linhas. No Spark, você pede um broadcast join, que copia a tabela pequena para todos os executores, e o join deixa de precisar de shuffle.

E o pushdown é a mesma ideia que reduz a conta do Athena: o Athena cobra por bytes lidos, então Parquet com só as colunas usadas e filtro na coluna de partição custam menos. Você vai ver isso com número na aula de SQL.

Os bugs que não levantam exceção

06 min

Trocar de biblioteca traz bugs novos, e quase todos aparecem só na comparação com a versão antiga.

python
import time

import pandas as pd

trips = pl.read_parquet(PATH, columns=["PULocationID", "fare_amount", "tip_amount"])

# 1. group_by order is not stable
for run in range(3):
    print("run", run, trips.group_by("PULocationID").agg(pl.len()).head(3)["PULocationID"].to_list())

# 2. NaN and inf in a mean: same data, two answers
tip_pct = trips.select((pl.col("tip_amount") / pl.col("fare_amount") * 100).alias("tip_pct"))
print("polars mean:", tip_pct["tip_pct"].mean(), "| NaN rows:", tip_pct["tip_pct"].is_nan().sum())
print("pandas mean:", tip_pct.to_pandas()["tip_pct"].mean())

# 3. pl.len() is an unsigned integer
per_zone = trips.group_by("PULocationID").agg(pl.len().alias("trips"))
print("trips dtype:", per_zone.schema["trips"])
print(per_zone.with_columns((pl.col("trips") - 100_000).alias("trips_vs_100k"))
      .sort(["trips", "PULocationID"]).head(2))

# 4. going back to pandas has a price
start = time.perf_counter()
as_pandas = pl.read_parquet(PATH).to_pandas()
print(f"to_pandas of the full month: {time.perf_counter() - start:.2f}s")
Saída realrun 0 [114, 52, 161] run 1 [9, 161, 224] run 2 [254, 58, 165] polars mean: nan | NaN rows: 867 pandas mean: inf trips dtype: UInt32 shape: (2, 3) ┌──────────────┬───────┬───────────────┐ │ PULocationID ┆ trips ┆ trips_vs_100k │ │ --- ┆ --- ┆ --- │ │ i32 ┆ u32 ┆ u32 │ ╞══════════════╪═══════╪═══════════════╡ │ 44 ┆ 1 ┆ 4294867297 │ │ 105 ┆ 1 ┆ 4294867297 │ └──────────────┴───────┴───────────────┘ to_pandas of the full month: 0.53s

head() depois de group_by sem sort

Três execuções, três respostas. O Polars agrupa em paralelo e devolve os grupos na ordem em que as threads terminam. Um "top 5" sem sort, ou um teste que compara com uma saída gravada, falha de vez em quando, que é o pior jeito de falhar. Use sort, ou maintain_order=True se precisa da ordem de chegada.

NaN não é nulo

A mesma coluna de "% de gorjeta", com as 867 divisões 0/0 e as divisões por zero, dá nan no Polars e inf no pandas. O Polars ignora nulos no mean, mas NaN é um número de ponto flutuante e contamina a soma. O pandas pula o NaN, mas não o inf. As duas respostas estão erradas, e de jeitos diferentes. Filtre fare_amount > 0 antes de dividir, ou troque NaN por nulo com fill_nan(None).

Contagem sem sinal

pl.len() devolve UInt32, um inteiro sem sinal. Subtraia e o resultado negativo vira 4.294.867.297, sem erro. Isso morde em "variação de viagens entre dois meses" e em "viagens abaixo da meta". Converta para Int64 antes de qualquer subtração.

N/A que deixou de ser nulo

A atividade 05: mesmo CSV, 11.967 nulos no pandas e zero no Polars. O relatório migrado "melhora" sozinho.

to_pandas() no meio do caminho

Converter o mês inteiro de volta custou 0,53 s, mais que o pipeline lazy inteiro. Se uma biblioteca exige pandas, converta o resultado agregado, que tem 260 linhas, não os dados brutos.

validate esquecido

Como no pandas, o join não confere a chave se você não pedir. A linha repetida do JFK multiplica as viagens do mesmo jeito.

ConteúdoAula D02 · Atividade 11

Quando isso NÃO ajuda

03 min

O modo lazy ganha quando o otimizador tem o que cortar. Quando não tem, ele é só o Polars eager com um passo a mais.

  • Operações que precisam de todos os dados. Um sort global, um join entre duas tabelas grandes ou um unique não terminam antes de ver a última linha. O pushdown ainda corta colunas, mas não há filtro para empurrar para dentro do arquivo;
  • Dado pequeno. A tabela de zonas tem 265 linhas. Ali, qualquer ferramenta responde em microssegundos, e a pergunta certa é qual código a equipe consegue manter;
  • collect() no meio do pipeline. Cada collect() intermediário materializa tudo e corta o plano em dois. O otimizador só enxerga o pedaço depois dele. É o equivalente lazy do list() por acidente da aula 05;
  • O dado já está num banco ou num data lake. Se a pergunta é um GROUP BY sobre milhões de linhas no S3, escrever SQL no Athena leva o processamento até o dado, em vez de trazer o dado até o seu Python;
  • A biblioteca seguinte só aceita pandas. A conversão tem custo (atividade 10). Se o resto do código depende de pandas, troque só a etapa pesada, e meça se a troca pagou.

O pipeline inteiro em modo lazy

lazy e explain

Monte, com scan_parquet, um pipeline que filtra fare_amount > 0, agrega por PULocationID (trips, avg_fare, total_tip), faz o join com as zonas (null_values="N/A", validate="m:1"), ordena por trips e pega as cinco primeiras. Imprima o explain() antes do collect().

Antes de rodar, preveja num comentário: (a) quantas colunas o scan vai ler; (b) o JFK continua em primeiro depois do filtro?

Opinião do instrutor

O collect(engine="streaming"), que processa o arquivo em pedaços, deu o mesmo resultado que o lazy comum neste tamanho: 0,06 s e 167 MB. Ele faz diferença quando o arquivo não cabe na RAM.

Três diferenças, como ponto de partida para as suas:

  1. Execução: o pandas executa cada linha na hora. O Polars lazy monta um plano, otimiza com pushdown de colunas e filtros, e só então executa. Aqui, um terço do tempo e 40% do pico.
  2. Paralelismo: o pandas usa um núcleo na maior parte das operações. O Polars, escrito em Rust, divide o trabalho entre todos. Mesmo no eager, sem otimizador, foi um terço mais rápido em 2 núcleos.
  3. Modelo de dados: o Polars não tem índice, guarda nulo sem trocar o tipo e trabalha direto no Arrow. O pandas tem índice e um ecossistema muito maior de bibliotecas que o esperam.

Onde escorregam: rodar os três modos no mesmo processo (o pico do segundo herda o do primeiro); ler as 19 colunas no pandas e comparar com o lazy, que tira a vantagem do columns= e mede outra coisa; e concluir "Polars é 3 vezes mais rápido" sem dizer o tamanho do dado e o número de núcleos.

Se perguntarem na entrevista

Os pontos-chave estão em inglês. Troque os números pelos da sua máquina.

Q1

"pandas or Polars? What's the difference?"

Polars
  • Execution: pandas is eager. Polars can be lazy, so an optimizer sees the whole query and pushes column selection and filters into the file scan.
  • Polars is written in Rust and uses all cores. pandas mostly runs on one.
  • Data model: Polars has no index, keeps nulls without changing the type, and works on Arrow memory.
  • Give your measurement: same pipeline on one month of NYC taxi data, pandas 0.18 s and 409 MB, Polars lazy 0.06 s and 167 MB, on 2 cores.
  • pandas still wins on ecosystem. Many libraries expect a pandas DataFrame, so convert the small aggregated result, not the raw data.
Q2

"What is lazy evaluation, and why does it help?"

lazy
  • Transformations build a plan, and nothing runs until an action (collect in Polars, count or write in Spark).
  • Seeing the whole plan lets the optimizer reorder it: projection pushdown reads 3 of 19 columns, predicate pushdown drops rows while reading.
  • It doesn't help with operations that need all the data, like a global sort, or when you call collect in the middle of the pipeline.
Q3

"How do you check that a filter is pushed down to the scan?"

plans
  • Read the plan before running: explain() in Polars, df.explain() in Spark.
  • In Polars, the filter shows up as SELECTION inside the Parquet scan instead of a separate FILTER node. In Spark, it shows up under PushedFilters in the FileScan.
  • It matters for cost: on Athena you pay per byte scanned, so columns read and partitions skipped are money.
