Mão na massaAula D01 · Atividade 03

50 MB no disco, quanto na memória?

03 min

O arquivo tem 50 MB. Sem rodar nada, quanto você acha que o DataFrame inteiro ocupa na memória depois do pd.read_parquet?

Uma pista: são 19 colunas, quase todas numéricas, e quase 3 milhões de linhas.

Prever antes de rodar
Sua resposta fica salva neste navegador.
python
import os

import pandas as pd

PATH = "data/yellow_tripdata_2024-01.parquet"

trips = pd.read_parquet(PATH)
print(f"on disk   : {os.path.getsize(PATH) / 1e6:6.1f} MB")
print(f"in memory : {trips.memory_usage(deep=True).sum() / 1e6:6.1f} MB")
print(f"shape     : {trips.shape}")
Saída realon disk : 50.0 MB in memory : 418.0 MB shape : (2964624, 19)

Mais de oito vezes o tamanho do arquivo. O Parquet guarda cada coluna separada e comprimida: valores repetidos viram um dicionário, sequências iguais viram uma contagem, e tudo ainda passa por um compressor. Na memória não tem nada disso. Cada float64 ocupa 8 bytes, então cada coluna numérica custa 2.964.624 × 8 = 23,7 MB, comprimida ou não no disco.

Quem erra costuma chutar algo perto de 50 MB, como se ler fosse copiar o arquivo para a RAM. Essa conta de "8 bytes por valor" é a que importa quando alguém pergunta se um arquivo cabe na memória.

Para saber maisAula D01 · Atividade 04

Por que o tracemalloc diz 1,9 MB

03 min

Na aula 05 você mediu memória com tracemalloc. Aqui ele não serve, e o motivo é bom de saber.

python
import resource
import tracemalloc

import pyarrow as pa

tracemalloc.start()
trips = pd.read_parquet(PATH)
_, peak = tracemalloc.get_traced_memory()
tracemalloc.stop()

print(f"tracemalloc peak   : {peak / 1e6:7.1f} MB")
print(f"memory_usage(deep) : {trips.memory_usage(deep=True).sum() / 1e6:7.1f} MB")
print(f"Arrow memory pool  : {pa.total_allocated_bytes() / 1e6:7.1f} MB")
# ru_maxrss is in KiB on Linux (bytes on macOS)
print(f"process peak (RSS) : {resource.getrusage(resource.RUSAGE_SELF).ru_maxrss * 1024 / 1e6:7.1f} MB")
Saída realtracemalloc peak : 1.9 MB memory_usage(deep) : 418.0 MB Arrow memory pool : 418.0 MB process peak (RSS) : 1077.0 MB

O tracemalloc só enxerga o que passa pelo alocador do Python. O pd.read_parquet chama o pyarrow, que é C++ e reserva memória no próprio pool do Arrow. O pandas 3 monta o DataFrame em cima desses buffers. Os 418 MB existem, mas o tracemalloc não os vê.

Nesta trilha, a memória se mede de dois jeitos:

  • df.memory_usage(deep=True).sum(): quanto o DataFrame ocupa depois de pronto. O deep=True faz o pandas contar o conteúdo das colunas de texto, não só os ponteiros;
  • resource.getrusage(resource.RUSAGE_SELF).ru_maxrss: o pico do processo inteiro desde que ele começou, em KiB no Linux. Repare: 1.077 MB de pico para um resultado de 418 MB. Durante a leitura, os dados existem em mais de uma forma ao mesmo tempo.
O pico é do processo inteiro

Como o ru_maxrss nunca desce, duas medições no mesmo processo não se separam: a segunda herda o pico da primeira. Uma medição por processo, escolhida por argumento na linha de comando. Também não meça tempo com o tracemalloc ligado, porque ele deixa o código mais lento.

ConteúdoAula D01 · Atividade 05

Ler menos: columns= e dtypes

05 min

A economia mais barata é não ler. No Parquet, cada coluna é um bloco separado no arquivo, então pedir menos colunas significa ler menos bytes do disco, não só descartar depois.

Os exemplos desta atividade usam o lado do desembarque (DOLocationID). O do embarque fica para os seus exercícios.

python
import time

DEMO_COLUMNS = ["DOLocationID", "passenger_count"]

for label, kwargs in [("all columns", {}), ("2 columns", {"columns": DEMO_COLUMNS})]:
    start = time.perf_counter()
    df = pd.read_parquet(PATH, **kwargs)
    elapsed = time.perf_counter() - start
    print(f"{label:12} {elapsed:5.2f}s  {df.memory_usage(deep=True).sum() / 1e6:6.1f} MB")
Saída realall columns 0.36s 418.0 MB 2 columns 0.02s 35.6 MB

Duas colunas de 19 custam 35,6 MB e 0,02 s, contra 418,0 MB e 0,36 s. Depois de escolher as colunas, vale olhar o tipo de cada uma:

python
dropoffs = pd.read_parquet(PATH, columns=DEMO_COLUMNS)
print(dropoffs.dtypes.to_dict())
print("DOLocationID range:", dropoffs["DOLocationID"].min(), "to", dropoffs["DOLocationID"].max())
print("passenger_count nulls:", dropoffs["passenger_count"].isna().sum(),
      "| max:", dropoffs["passenger_count"].max())

slim = dropoffs.astype({"DOLocationID": "int16", "passenger_count": "Int8"})
before = dropoffs.memory_usage(deep=True, index=False) / 1e6
after = slim.memory_usage(deep=True, index=False) / 1e6
print(pd.DataFrame({"before_mb": before, "after_mb": after}).round(1))
Saída real{'DOLocationID': dtype('int32'), 'passenger_count': dtype('float64')} DOLocationID range: 1 to 265 passenger_count nulls: 140162 | max: 9.0 before_mb after_mb DOLocationID 11.9 5.9 passenger_count 23.7 5.9

Cada linha da saída é uma decisão diferente:

  • DOLocationID vai de 1 a 265. O int32 aguenta até 2 bilhões. O int16 vai até 32.767 e já sobra. Metade da memória.
  • passenger_count é contagem de pessoas, mas chegou como float64. O motivo são os 140.162 nulos: o int64 do NumPy não tem como representar "vazio", e o pandas converte a coluna para float para usar NaN. O "Int8", com I maiúsculo, é o inteiro anulável do pandas. Ele guarda o valor em 1 byte e uma máscara de nulos ao lado, e o vazio vira pd.NA.
  • Código com poucos valores distintos, repetidos milhões de vezes, é candidato a category: o pandas guarda cada valor uma vez e, por linha, só um índice pequeno. Você vai aplicar isso no exercício S1.2.

E dinheiro? Dinheiro fica em float64. A atividade 09 mostra por quê.

ConteúdoAula D01 · Atividade 06

groupby: named aggregations, agg e transform

05 min

Named aggregation é a sintaxe nome_da_saida=("coluna", "função"). Ela dá nome às colunas do resultado já na agregação, sem o MultiIndex de colunas que o agg({"col": ["mean", "max"]}) cria.

O exemplo agrupa por forma de pagamento. Os exercícios agrupam por zona.

python
by_type = pd.read_parquet(PATH, columns=["payment_type", "tip_amount"])

summary = by_type.groupby("payment_type").agg(
    trips=("tip_amount", "size"),
    avg_tip=("tip_amount", "mean"),
    max_tip=("tip_amount", "max"),
)
print(summary.round(2))

type_avg = by_type.groupby("payment_type")["tip_amount"].transform("mean")
print("agg      :", summary.shape)
print("transform:", type_avg.shape)
Saída real trips avg_tip max_tip payment_type 0 140162 1.55 40.00 1 2319046 4.17 428.00 2 439191 0.00 141.49 3 19597 0.01 24.41 4 46628 0.04 50.80 agg : (5, 3) transform: (2964624,)

As duas últimas linhas são a diferença inteira entre os dois:

aggtransform
Devolveuma linha por grupo (5)uma linha por linha de entrada (2.964.624)
Índiceas chaves do grupoo mesmo índice do DataFrame original
Serve pararelatório, tabela de resumocomparar cada linha com o próprio grupo: "% do total do grupo", "diferença para a média do grupo"

Como o transform volta alinhado pelo índice, você atribui o resultado direto como coluna nova, sem merge de volta.

Leia o número antes de confiar

A gorjeta média em dinheiro (payment_type 2) é 0,00. O dicionário de dados da TLC registra as formas de pagamento (0 = Flex Fare, 1 = cartão, 2 = dinheiro, 3 = sem cobrança, 4 = disputa), e avisa que a coluna de gorjeta só é preenchida para cartão: gorjeta em dinheiro não entra. Uma "gorjeta média de todas as viagens" mistura gorjeta zero de verdade com gorjeta que não foi registrada.

ConteúdoAula D01 · Atividade 07

merge: contar, validar, desconfiar

04 min

Um merge de fato com dimensão tem um contrato: cada viagem continua sendo uma viagem. Esse contrato não é verificado por padrão. Você verifica.

python
zones = pd.read_csv("data/taxi_zone_lookup.csv")
dropoffs = pd.read_parquet(PATH, columns=["DOLocationID"])

rows_before = len(dropoffs)
with_zone = dropoffs.merge(
    zones[["LocationID", "Borough"]],
    left_on="DOLocationID",
    right_on="LocationID",
    how="left",
    validate="many_to_one",
)
assert len(with_zone) == rows_before, "the merge changed the row count"

print("rows      :", rows_before, "->", len(with_zone))
print("no borough:", with_zone["Borough"].isna().sum())
print(zones[zones["LocationID"] >= 264])
Saída realrows : 2964624 -> 2964624 no borough: 11967 LocationID Borough Zone service_zone 263 264 Unknown NaN NaN 264 265 NaN Outside of NYC NaN

Três defesas, cada uma contra um problema diferente:

  • how="left": nenhuma viagem some por não achar zona. O inner, que é o padrão, descartaria em silêncio;
  • validate="many_to_one": o pandas confere que a chave é única do lado direito e levanta MergeError se não for. Sem ele, chave duplicada vira linha duplicada;
  • o assert de contagem: pega o que as outras duas não pegam e documenta a intenção no código.

Agora olhe as 11.967 viagens "sem borough". Não falta dado nenhum. No CSV, a zona 265 é 265,"N/A","Outside of NYC","N/A", e o read_csv trata o texto N/A como nulo por padrão. Para o pandas, o borough sumiu. Para a TLC, o borough é "não se aplica", porque a viagem terminou fora de Nova York. Num relatório, essa diferença muda a legenda e o número.

Para saber maisAula D01 · Atividade 08

apply e iterrows, medidos

03 min

"Evite apply" vira dogma quando ninguém mede. A mesma regra, "a viagem saiu de um aeroporto?", em quatro versões, sobre as primeiras 100 mil viagens:

python
import time

import numpy as np

sample = pd.read_parquet(PATH, columns=["PULocationID"]).head(100_000)
AIRPORTS = [132, 138]  # JFK, LaGuardia


def timed(label, fn):
    start = time.perf_counter()
    result = fn()
    print(f"{label:9} {time.perf_counter() - start:8.4f}s")
    return result


by_apply = timed("apply", lambda: sample.apply(lambda row: int(row["PULocationID"] in AIRPORTS), axis=1))
by_iter = timed("iterrows", lambda: pd.Series(
    [int(row["PULocationID"] in AIRPORTS) for _, row in sample.iterrows()], index=sample.index))
by_isin = timed("isin", lambda: sample["PULocationID"].isin(AIRPORTS).astype("int8"))
by_where = timed("np.where", lambda: np.where(sample["PULocationID"].isin(AIRPORTS), 1, 0))

print("same answer:", bool((by_apply.to_numpy() == by_isin.to_numpy()).all()
                           and (by_iter.to_numpy() == by_where).all()))
Saída realapply 0.2236s iterrows 1.0059s isin 0.0017s np.where 0.0012s same answer: True

O apply(axis=1) foi mais de 100 vezes mais lento que o isin, e o iterrows quase 600 vezes. Os dois montam uma Series por linha e chamam uma função Python para cada uma. O isin e o np.where rodam um laço em C sobre o array inteiro. No mês completo, medido na mesma máquina: 7,3 s com apply, 27 s com iterrows e 18 ms com isin.

Quando o apply é aceitável: lógica que não existe vetorizada (chamar uma biblioteca externa por valor, por exemplo), sobre poucos milhares de linhas, ou groupby().apply com poucos grupos. Escreva o motivo num comentário, como a aula 05 pedia para o list().

ArmadilhasAula D01 · Atividade 09

Os bugs que não levantam exceção

05 min

Um KeyError para o pipeline e você conserta. Os problemas abaixo devolvem um número plausível, e o relatório sai.

python
trips = pd.read_parquet(PATH, columns=["PULocationID", "passenger_count", "fare_amount"])

# 1. size counts rows, count skips nulls
per_zone = trips.groupby("PULocationID").agg(
    rows=("passenger_count", "size"), with_value=("passenger_count", "count"))
print("size :", per_zone["rows"].sum(), "| count:", per_zone["with_value"].sum())

# 2. a ratio against the group mean
zone_avg = trips.groupby("PULocationID")["fare_amount"].transform("mean")
ratio = trips["fare_amount"] / zone_avg
print("ratio mean:", ratio.mean(), "| inf rows:", int(np.isinf(ratio).sum()))
print(trips.loc[trips["PULocationID"] == 245, ["PULocationID", "fare_amount"]])

# 3. money in float32
total64 = trips["fare_amount"].sum()
total32 = trips["fare_amount"].astype("float32").sum()
print(f"float64: {total64:,.2f} | float32: {float(total32):,.2f}")
Saída realsize : 2964624 | count: 2824462 ratio mean: nan | inf rows: 2 PULocationID fare_amount 1995551 245 -4.4 1995552 245 4.4 float64: 53,882,224.76 | float32: 53,882,224.00

A segunda parte merece atenção. A zona 245 teve duas viagens no mês: uma cobrança de US$ 4,40 e o estorno dela. A média da zona é zero, a razão das duas linhas vira -inf e +inf, e a soma dos dois vira NaN. Duas linhas em 3 milhões apagaram a média geral. O único aviso foi um RuntimeWarning do NumPy no stderr, que num job agendado ninguém lê.

count no lugar de size

count ignora nulos, size conta linhas. Contando viagens por passenger_count, somem 140.162 viagens, justamente as de Flex Fare. Para "quantas viagens", use size, ou count numa coluna que você provou não ter nulos.

Razão contra a média do grupo

Estorno anula cobrança, a média vai a zero e a divisão vai a infinito. Prefira diferença à razão quando o denominador pode zerar, ou filtre os valores não positivos antes e conte quantos saíram.

Dinheiro em float32

O float32 tem cerca de 7 dígitos significativos. O total de tarifas do mês tem 10. Some em float32 e perde 76 centavos, sem erro. Reduza IDs e códigos, não valores monetários.

astype("int8") num ID que passa de 127

O cast não confere o intervalo: 265 vira um número negativo. Em PULocationID, 2.303.392 das 2.964.624 linhas mudam de valor. O merge seguinte não acha a zona, e com how="left" as viagens ficam com borough vazio. Confira min() e max() antes de escolher o tipo.

Chave duplicada na dimensão

Se a tabela de zonas tiver uma linha repetida, o merge repete cada viagem daquela zona, a soma de tarifas cresce e nenhum erro aparece. O validate não é o padrão: você pede. No S1.4 você mede o tamanho do estrago.

N/A lido como nulo

O read_csv converte N/A, NA, null e outros textos em NaN. Às vezes é o certo. Na tabela de zonas, transforma "não se aplica" em "faltando". Se o texto é um valor válido, leia com keep_default_na=False ou com uma lista própria de na_values.

ConteúdoAula D01 · Atividade 10

Quando isso NÃO ajuda

04 min

columns= e dtypes resolvem bem o caso desta aula. Fora dele, cada um tem um limite, e saber o limite é o que diferencia entender de decorar.

python
import time

CSV = "data/yellow_tripdata_2024-01.csv"   # same month, written once with trips.to_csv(CSV, index=False)
COLS = ["DOLocationID", "passenger_count"]

for label, read in [("parquet, columns=", lambda: pd.read_parquet(PATH, columns=COLS)),
                    ("csv, usecols=    ", lambda: pd.read_csv(CSV, usecols=COLS))]:
    start = time.perf_counter()
    df = read()
    print(f"{label} {time.perf_counter() - start:5.2f}s  {df.memory_usage(deep=True).sum() / 1e6:5.1f} MB")

pickup = pd.read_parquet(PATH, columns=["tpep_pickup_datetime"])["tpep_pickup_datetime"]
print("distinct pickup times:", pickup.nunique())
print(f"datetime64: {pickup.memory_usage(deep=True) / 1e6:.1f} MB"
      f" | category: {pickup.astype('category').memory_usage(deep=True) / 1e6:.1f} MB")
Saída realparquet, columns= 0.06s 35.6 MB csv, usecols= 0.46s 47.4 MB distinct pickup times: 1575706 datetime64: 23.7 MB | category: 24.5 MB
  • CSV não é colunar. O usecols= economiza memória, mas o arquivo inteiro de 311 MB ainda é lido e quebrado em linhas: 0,46 s contra 0,06 s do Parquet para as mesmas duas colunas. Se o dado chega em CSV e vai ser lido muitas vezes, converter uma vez para Parquet costuma valer mais que qualquer ajuste de leitura;
  • category em coluna de alta cardinalidade piora. Com 1,58 milhão de horários distintos, a categoria guarda quase todos os valores de novo, mais um índice por linha: 24,5 MB contra 23,7 MB. A regra é poucos valores repetidos muitas vezes.

O terceiro limite é o mais importante, e só aparece medindo o pico:

python
import resource


def peak_mb() -> float:
    return resource.getrusage(resource.RUSAGE_SELF).ru_maxrss * 1024 / 1e6   # KiB on Linux


dropoffs = pd.read_parquet(PATH, columns=["DOLocationID", "passenger_count"])
print(f"after read  : peak {peak_mb():6.1f} MB, frame {dropoffs.memory_usage(deep=True).sum() / 1e6:5.1f} MB")
dropoffs = dropoffs.astype({"DOLocationID": "int16", "passenger_count": "Int8"})
print(f"after astype: peak {peak_mb():6.1f} MB, frame {dropoffs.memory_usage(deep=True).sum() / 1e6:5.1f} MB")
Saída realafter read : peak 237.8 MB, frame 35.6 MB after astype: peak 277.5 MB, frame 11.9 MB

O DataFrame encolheu de 35,6 para 11,9 MB, mas o pico subiu: o astype monta as colunas novas antes de soltar as antigas. Ajustar o tipo depois de ler reduz o que fica na memória, não o pico da leitura. Se o problema é o pico, leia menos (colunas, filtros na leitura, um row group por vez) ou use um motor que não materializa tudo, que é o assunto da D02.

E quando nem as colunas certas cabem na RAM, o pandas sozinho para de ser a ferramenta: leitura em lotes com pyarrow.parquet.ParquetFile.iter_batches, o modo streaming do Polars, ou levar o processamento para onde o dado já está, com Spark ou Athena.

Quem mais encolhe é o payment_type, 8 vezes: chegou como int64, com 8 bytes por linha, para guardar 5 valores. Os três floats ainda são 71 MB dos 80. Essa é a resposta escrita: o ganho de memória não paga um relatório financeiro que não fecha.

Onde escorregam: int8 em PULocationID. O cast aceita sem reclamar, e 2.303.392 linhas passam a ter outro ID. Também escorrega quem converte payment_type para category e depois compara com == "1", como texto. As categorias continuam inteiras, a comparação dá falso em todas as linhas, e o filtro devolve vazio.

Q1

"How do you process a file that doesn't fit in memory?"

pandas
  • Read only the columns you need. With Parquet that skips bytes on disk. Give your number: 418 MB down to 107 MB for this month.
  • Shrink types where it is safe: IDs to int16, low-cardinality codes to category. Money stays float64.
  • Filter early, and process in batches if it still doesn't fit (iter_batches in pyarrow).
  • Past that point, change tools: Polars lazy/streaming, Spark, or query it where it lives with Athena.
Q2

"What can go wrong in a merge?"

pandas
  • A duplicated key on the dimension side multiplies rows with no error. One duplicated zone added 145,240 rows here.
  • An inner join silently drops rows with no match, and key type mismatches stop matches entirely.
  • Defense: how="left", validate="many_to_one", and an assert on the row count before and after.
  • Check what "null" means after the join. Here, "N/A" was a real value read as missing.
Q3

"What's the difference between agg and transform?"

pandas
  • agg reduces each group to one row: 260 rows, one per pickup zone.
  • transform returns one value per input row, aligned to the original index: 2.96 million rows.
  • Use transform to compare each row with its own group, like "fare minus the zone average", without merging back.
