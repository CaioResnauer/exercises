Para começarAula 14 · Atividade 01

Apresentação

03 min · pré-requisito: aula 13

SQL é declarativo e não tem laço. A CTE recursiva é a exceção — e é o que permite responder perguntas cuja profundidade você não sabe de antemão.

Três famílias de problema caem aqui, e as três aparecem em engenharia de dados:

  • Hierarquia: quem se reporta a quem, categoria e subcategoria, plano de contas;
  • Grafo: quais nós são alcançáveis, qual o caminho, há ciclo;
  • Geração: uma linha por dia do mês, mesmo nos dias sem venda.
A aula tem uma query que não termina

A atividade 06 mostra uma travessia sobre dados com ciclo. Ela ficou rodando até eu matar o processo — e é assim que ela se comporta em produção. Vale ver o mecanismo antes de escrever a primeira.

Tempo estimado

40 min de leitura, 1 h 30 de exercícios. Tudo roda em sqlite3.

ConteúdoAula 14 · Atividade 02

O algoritmo, em quatro passos

06 min

O nome assusta e o mecanismo é um laço while. Comece pelo caso mais simples possível: gerar uma sequência de datas.

sql
WITH RECURSIVE dias(d) AS (
    SELECT DATE('2026-03-01')                          -- âncora: o ponto de partida
    UNION ALL
    SELECT DATE(d, '+1 day') FROM dias WHERE d < '2026-03-07'   -- passo: usa o anterior
)
SELECT d FROM dias;
Saída reald ---------- 2026-03-01 2026-03-02 2026-03-03 2026-03-04 2026-03-05 2026-03-06 2026-03-07

O que o banco faz

1. Roda a âncora

A parte antes do UNION ALL, uma vez. O resultado vai para o conjunto final e para uma fila de trabalho.

2. Roda o passo sobre a fila

A parte depois do UNION ALL. Nela, o nome da CTE (dias) se refere apenas ao que foi produzido na iteração anterior — não ao acumulado. Esse é o detalhe que quase todo mundo entende errado.

3. Acumula e repete

O que saiu vira o novo conteúdo da fila, e o passo roda de novo.

4. Para quando o passo não produz nada

Fila vazia, fim. É a única condição de parada. Se o passo sempre produzir alguma linha, o laço é infinito — não existe limite implícito.

O WHERE do passo é o while

Em WHERE d < '2026-03-07', a comparação é a condição de continuação. Sem ela, a query gera datas até o fim dos tempos. É literalmente o mesmo papel do teste de parada do __next__ na aula 01 — e o mesmo tipo de bug quando está errado.

A palavra RECURSIVE vem logo depois de WITH e vale para o bloco inteiro, mesmo que só uma das CTEs seja recursiva. Em PostgreSQL ela é obrigatória; no SQLite e no SQL Server, opcional.

ConteúdoAula 14 · Atividade 03

Hierarquia: quem se reporta a quem

07 min

O caso clássico. Uma tabela que aponta para ela mesma, e uma pergunta cuja resposta tem profundidade desconhecida.

sql
CREATE TABLE employee(id INTEGER PRIMARY KEY, name TEXT, manager_id INTEGER);
INSERT INTO employee VALUES
 (1,'Marina',NULL),(2,'Caio',1),(3,'Ana',1),
 (4,'Bruno',2),(5,'Dora',2),(6,'Eva',4),(7,'Fabio',3);
sql
WITH RECURSIVE chain(id, name, manager_id, depth, path) AS (
    SELECT id, name, manager_id, 0, name
      FROM employee WHERE manager_id IS NULL          -- âncora: a raiz
    UNION ALL
    SELECT e.id, e.name, e.manager_id, c.depth + 1, c.path || ' > ' || e.name
      FROM employee e JOIN chain c ON e.manager_id = c.id
)
SELECT depth, name, path FROM chain ORDER BY path;
Saída realdepth | name | path ------+--------+---------------------------- 0 | Marina | Marina 1 | Ana | Marina > Ana 2 | Fabio | Marina > Ana > Fabio 1 | Caio | Marina > Caio 2 | Bruno | Marina > Caio > Bruno 3 | Eva | Marina > Caio > Bruno > Eva 2 | Dora | Marina > Caio > Dora

Duas colunas foram construídas no caminho, e as duas são o padrão que vale guardar:

depth — a distância até a raiz

Começa em 0 na âncora e soma 1 a cada nível. Serve para indentar na saída, para limitar a profundidade (WHERE depth < 10) e para responder "quantos níveis tem a organização".

path — o caminho concatenado

c.path || ' > ' || e.name acumula o trajeto. Além de legível, ele resolve dois problemas: dá uma ordenação que agrupa a árvore corretamente (o ORDER BY path acima), e é a base da guarda de ciclo da atividade 07.

Só uma subárvore

Trocar a âncora troca a pergunta. Mesma estrutura, agora partindo de um nó qualquer:

sql
WITH RECURSIVE sub(id, name, depth) AS (
    SELECT id, name, 0 FROM employee WHERE name = 'Caio'
    UNION ALL
    SELECT e.id, e.name, s.depth + 1 FROM employee e JOIN sub s ON e.manager_id = s.id
)
SELECT depth, name FROM sub ORDER BY depth, name;
Saída realdepth | name ------+------ 0 | Caio 1 | Bruno 1 | Dora 2 | Eva

"O time do Caio, em qualquer nível" — quatro pessoas, incluindo ele. Um COUNT(*) - 1 nisso é o tamanho da equipe indireta, que é uma métrica que gente de RH pede e que nenhum JOIN de profundidade fixa responde.

Subir em vez de descer

Inverta o JOIN e você percorre para cima: JOIN chain c ON e.id = c.manager_id, partindo do funcionário. É como se responde "quem são todos os gestores acima desta pessoa" — a cadeia de aprovação.

Mão na massaAula 14 · Atividade 04

Onde a recursão para

05 min

Duas CTEs recursivas. Uma termina, a outra não — e a diferença não está em nenhum WHERE.

sql
-- A
WITH RECURSIVE t(n) AS (
    SELECT 1
    UNION ALL
    SELECT n + 1 FROM t WHERE n < 5
) SELECT * FROM t;

-- B
WITH RECURSIVE t(n) AS (
    SELECT 1
    UNION ALL
    SELECT n + 1 FROM t
) SELECT * FROM t LIMIT 5;
Prever antes de rodar
Sua resposta fica salva neste navegador.

As duas terminam — e por motivos completamente diferentes.

A para porque o passo deixa de produzir linhas: quando n chega a 5, o WHERE n < 5 não seleciona nada, a fila esvazia, fim. É a condição de parada de verdade.

B para porque o SQLite avalia a recursão preguiçosamente e o LIMIT 5 fecha a torneira depois de cinco linhas. A CTE em si é infinita — o que a segurou foi o consumidor.

Por que B é uma armadilha

Depender do LIMIT só funciona enquanto ele estiver diretamente sobre a CTE recursiva. Acrescente um ORDER BY, um GROUP BY, um JOIN ou um COUNT(*) e o banco precisa materializar tudo antes de aplicar o limite — e aí a query nunca termina.

sql — o mesmo B, com uma ordenação
... SELECT * FROM t ORDER BY n LIMIT 5;   -- nunca termina

E nem todo banco é preguiçoso aqui. Em PostgreSQL, a CTE recursiva é materializada por completo antes do LIMIT — o B trava lá mesmo sem ORDER BY.

A regra

A condição de parada mora dentro do passo recursivo, no WHERE. O LIMIT lá fora é para o resultado, não para a recursão — tratá-lo como freio é confiar num detalhe de implementação que muda entre bancos e entre versões.

ConteúdoAula 14 · Atividade 05

Séries e calendários

05 min

O uso menos glamouroso e o mais frequente: preencher os dias em que não aconteceu nada.

O problema aparece em todo relatório. GROUP BY sale_date devolve só os dias com venda; o gráfico fica com buracos, a média móvel da aula 13 conta linhas em vez de dias, e o dia zerado — que é exatamente o que interessa — some.

sql — calendário à esquerda, dados à direita
WITH RECURSIVE calendario(d) AS (
    SELECT DATE('2026-03-01')
    UNION ALL
    SELECT DATE(d, '+1 day') FROM calendario WHERE d < DATE('2026-03-31')
)
SELECT c.d AS dia,
       COALESCE(SUM(s.amount), 0) AS total,
       COUNT(s.id)                AS vendas
FROM calendario c
LEFT JOIN sales s ON s.sale_date = c.d
GROUP BY c.d
ORDER BY c.d;

Três peças fazem isso funcionar, e errar qualquer uma devolve o buraco:

PeçaSe errar
LEFT JOIN, com o calendário à esquerdaum JOIN comum descarta os dias vazios de novo
COALESCE(SUM(...), 0)o dia vazio aparece com NULL em vez de zero
COUNT(s.id), não COUNT(*)COUNT(*) conta a linha do calendário e devolve 1 num dia sem venda
O COUNT(*) que conta o nada

Esse terceiro item é sutil e passa em revisão. Num LEFT JOIN sem correspondência, a linha existe com as colunas da direita nulas — então COUNT(*) vê uma linha. COUNT(s.id) ignora nulos e devolve 0, que é a resposta certa.

Em PostgreSQL, use generate_series

SELECT generate_series('2026-03-01'::date, '2026-03-31', '1 day') faz o mesmo em uma linha, e o planejador entende melhor. A CTE recursiva é o jeito portátil — e no sqlite, o único. Vale conhecer os dois.

O mesmo padrão serve para gerar faixas numéricas (histogramas com baldes vazios), horas do dia, meses do ano. Sempre que o relatório precisa mostrar o que não aconteceu, é isso.

ConteúdoAula 14 · Atividade 06

O ciclo que trava a query

06 min

Dados de hierarquia vêm de sistemas onde alguém, um dia, apontou um nó para o próprio ancestral. A query não avisa: ela roda.

sql
CREATE TABLE loopy(id INTEGER, next_id INTEGER);
INSERT INTO loopy VALUES (1,2),(2,3),(3,1);      -- 1 -> 2 -> 3 -> 1

WITH RECURSIVE walk(id) AS (
    SELECT 1
    UNION ALL
    SELECT l.next_id FROM loopy l JOIN walk w ON l.id = w.id
)
SELECT COUNT(*) FROM walk;
saída real
sem guarda de ciclo: ainda rodando depois de 3 s? True   <- nunca termina

O passo sempre encontra uma linha, então a fila nunca esvazia. Não há limite de profundidade, não há timeout, não há aviso. Em produção isso é uma conexão presa, uma tabela temporária crescendo e um disco enchendo.

A guarda: carregue o caminho

sql
WITH RECURSIVE walk(id, path) AS (
    SELECT 1, ',1,'
    UNION ALL
    SELECT l.next_id, w.path || l.next_id || ','
      FROM loopy l JOIN walk w ON l.id = w.id
     WHERE w.path NOT LIKE '%,' || l.next_id || ',%'      -- já visitei?
)
SELECT id, path FROM walk;
Saída realid | path ---+-------- 1 | ,1, 2 | ,1,2, 3 | ,1,2,3,

A coluna path é a mesma da atividade 03, agora com um segundo emprego: guardar quem já foi visitado. As vírgulas em volta de cada id não são enfeite — sem elas, ,12, daria falso positivo ao procurar por 1.

A alternativa mais simples

sql
WITH RECURSIVE walk(id) AS (
    SELECT 1
    UNION           -- em vez de UNION ALL
    SELECT l.next_id FROM loopy l JOIN walk w ON l.id = w.id
) SELECT id FROM walk ORDER BY id;
Saída realid -- 1 2 3

UNION sem ALL deduplica a cada iteração; quando o passo só produz linhas já vistas, a fila esvazia e acaba. Funciona, é mais curto — e tem dois custos: você perde o caminho, e a deduplicação exige comparar contra tudo que já saiu, o que é mais caro quando o conjunto cresce.

GuardaPreserva o caminhoCustoDetecta ciclo
path NOT LIKEsimstring crescente por linhasim, e diz onde
UNIONnãodeduplicação a cada passosó evita, não reporta
WHERE depth < nsimnenhumnão — só limita o estrago
Em PostgreSQL há sintaxe para isso

CYCLE id SET is_cycle USING path monta a guarda automaticamente e ainda marca a linha onde o ciclo fechou. Se o seu banco é Postgres 14+, use — é mais rápido e não erra a comparação de string.

Ponha um limite de profundidade de qualquer jeito

Mesmo com guarda de ciclo, WHERE depth < 50 custa nada e transforma "a query travou" em "a query devolveu 50 níveis, o que é suspeito". Um cinto de segurança para o caso que você não previu.

Para saber maisAula 14 · Atividade 07

Quando não usar recursão

04 min

CTE recursiva é elegante e é a construção mais cara do SQL. Vale conhecer as alternativas.

Profundidade fixa e conhecida

"Categoria e subcategoria", dois níveis, sempre. Um LEFT JOIN resolve, é mais rápido e mais legível. Recursão só quando a profundidade é desconhecida.

A hierarquia muda pouco e é lida muito

Materialize. Uma coluna path na própria tabela — /1/2/4/ — transforma "toda a subárvore de X" num WHERE path LIKE '/1/2/%' que usa índice. É o padrão materialized path, e é o que a maioria dos sistemas de categoria usa.

Você vai percorrer a mesma árvore várias vezes por execução

Rode a recursão uma vez, guarde numa tabela temporária, e faça os JOIN contra ela. Repetir a CTE em cinco queries é pagar cinco vezes.

O grafo é grande e denso

Alcançabilidade em grafo com milhões de arestas não é trabalho para SQL recursivo — o conjunto intermediário explode. É o momento de um banco de grafo, ou de processar fora com uma busca em largura.

Como decidir, na prática

Rode a recursão com EXPLAIN QUERY PLAN e olhe quantas linhas o passo produz por iteração. Se o número cresce a cada volta em vez de encolher, você está multiplicando caminhos — e provavelmente falta uma condição no JOIN ou uma guarda de ciclo.

A aula 15 é sobre exatamente isso: ler o plano antes de aceitar que a query é rápida.

ReferênciaAula 14 · Atividade 08

Referência rápida

03 min
sql — o esqueleto, com tudo que costuma faltar
WITH RECURSIVE nome(col1, col2, depth, path) AS (

    -- ÂNCORA: de onde parte. Sem referência à própria CTE.
    SELECT c1, c2, 0, ',' || c1 || ','
      FROM tabela
     WHERE <condição da raiz>

    UNION ALL           -- ALL: mais rápido. Sem ALL: deduplica e evita ciclo.

    -- PASSO: usa apenas o que a iteração anterior produziu.
    SELECT t.c1, t.c2, r.depth + 1, r.path || t.c1 || ','
      FROM tabela t
      JOIN nome r ON t.pai = r.col1
     WHERE r.depth < 50                                  -- cinto de segurança
       AND r.path NOT LIKE '%,' || t.c1 || ',%'          -- guarda de ciclo
)
SELECT * FROM nome;
SintomaCausa provável
a query não terminaciclo nos dados, ou o passo sempre produz linha
volta só a âncorao JOIN do passo não casa — confira a direção
linhas duplicadasvários caminhos até o mesmo nó; use UNION ou DISTINCT
"recursive reference in a subquery"a CTE só pode ser referenciada uma vez, e não dentro de subquery ou OUTER JOIN
resultado explodefalta condição no JOIN; virou produto cartesiano por iteração
A restrição que pega todo mundo uma vez

O passo recursivo pode citar a CTE uma vez só, e não pode fazer isso dentro de subquery, LEFT JOIN do lado direito, agregação ou ORDER BY. Se a sua ideia exige duas referências, ela precisa virar duas CTEs ou um JOIN extra fora da recursão.

Recursão contra caminho materializado

medição

Gere uma hierarquia de 10.000 nós com 6 níveis. Responda "toda a subárvore do nó X" de duas formas: com CTE recursiva, e com uma coluna path materializada mais LIKE '/1/2/%' com índice.

14.6

Desafio: explodir a nota fiscal

desafio

Uma tabela bom(parent_sku, child_sku, qty) descreve produtos compostos: um kit contém peças, que podem conter outras peças. Escreva a query que, dado um SKU, devolve todas as peças elementares e a quantidade total de cada uma.

A parte difícil é a multiplicação

A quantidade não soma ao descer, ela multiplica: r.qty * b.qty. E uma mesma peça pode ser alcançada por dois caminhos, então o total exige um GROUP BY child_sku depois da recursão. Peça elementar é a que não aparece como parent_sku em nenhuma linha.

Inclua um caso com peça compartilhada por dois ramos, e prove que a soma está correta.

Checklist antes de commitar
  • Toda CTE recursiva tem condição de parada dentro do passo?
  • Toda travessia de grafo tem guarda de ciclo?
