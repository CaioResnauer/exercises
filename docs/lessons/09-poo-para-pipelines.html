Apresentação

03 min · pré-requisito: aulas 01 a 08

Oito aulas escrevendo funções. Esta é sobre o momento em que uma função deixa de bastar — e sobre a armadilha de achar que esse momento chegou antes da hora.

A pergunta não é "usar classe ou função?". É "isto tem estado e configuração que várias operações compartilham?". Um conector de banco tem: credencial, conexão aberta, tamanho de lote. Uma função de arredondar não tem nada.

O que a aula constrói

  • Um conector como classe: o que ele guarda e por quê;
  • Um contrato explícito com Protocol, e quando ABC é melhor;
  • Composição de estágios em vez de hierarquia de classes;
  • Injeção de dependência — a única razão pela qual o seu pipeline vai ser testável na aula 10.
O aviso que abre a aula

Metade do código orientado a objetos que se vê em pipelines existe porque alguém achou que "profissional" significa "tem classe". A atividade 10 é a régua do contrário: quando a classe está sobrando, e como reconhecer.

Tempo estimado

45 min de leitura, 1 h 30 de exercícios.

ConteúdoAula 09 · Atividade 02

Quando a função deixa de bastar

06 min

O sintoma é sempre o mesmo: a lista de parâmetros cresce, e os mesmos valores são repassados de função em função.

python — o sintoma
def fetch_page(base_url, token, timeout, retries, page): ...
def fetch_all(base_url, token, timeout, retries): ...
def extract(base_url, token, timeout, retries, since): ...

rows = extract("https://api.x", token, 30, 3, "2026-01-01")

Quatro parâmetros que nunca mudam durante a execução, escritos em toda assinatura e repassados em toda chamada. Na quinta função alguém troca a ordem de timeout e retries e o bug só aparece sob carga.

Esses quatro valores são uma coisa só: a configuração de um conector. Dar um nome a essa coisa é o que a classe faz.

python — o mesmo, com o estado nomeado
@dataclass(frozen=True, slots=True)
class ApiConfig:
    base_url: str
    token: str
    timeout: float = 30.0
    retries: int = 3


class OrdersApi:
    """Read-only connector for the orders endpoint."""

    def __init__(self, config: ApiConfig, session) -> None:
        self._config = config
        self._session = session

    def fetch_page(self, page: int) -> dict: ...

    def read(self, since: str) -> Iterator[dict]:
        page = 1
        while True:
            payload = self.fetch_page(page)
            yield from payload["items"]
            if not payload["has_next"]:
                return
            page += 1

Repare no que mudou de verdade: as assinaturas ficaram curtas, o read() devolve um generator (aulas 02 e 05 continuam valendo), e a configuração virou um objeto imutável — frozen=True garante que ninguém altere o timeout no meio do pipeline.

O teste que decide

PerguntaSimNão
Há estado que sobrevive entre chamadas?classefunção
Os mesmos parâmetros aparecem em 3+ funções?classefunção
Há um recurso a abrir e fechar?classe (com __enter__)função
Vão existir várias implementações do mesmo papel?Protocolfunção
É uma transformação sem memória?função—
Um caso que engana

"Preciso agrupar funções relacionadas" não é motivo para classe. Isso é um módulo. Uma classe só com @staticmethod é um módulo com sintaxe pior.

ConteúdoAula 09 · Atividade 03

O contrato: Protocol e ABC

07 min

Um pipeline vai ter mais de uma fonte: API, CSV, banco, um dublê nos testes. Escrever o que todas precisam saber fazer é o que impede o resto do código de se importar com qual delas é.

ABC: o contrato por herança

python
from abc import ABC, abstractmethod

class Source(ABC):
    @abstractmethod
    def read(self) -> Iterator[dict]: ...

class Incompleta(Source):
    pass

Incompleta()
Saída realTypeError: Can't instantiate abstract class Incompleta without an implementation for abstract method 'read'

O erro chega cedo — na construção, não na primeira chamada. Bom. Mas exige herdar, e isso significa que uma classe de terceiros nunca vai satisfazer o seu contrato.

Protocol: o contrato por formato

python
from typing import Protocol, runtime_checkable

@runtime_checkable
class Readable(Protocol):
    def read(self) -> Iterator[dict]: ...

class CsvSource:                 # não herda de nada
    def read(self): return iter([{"id": 1}])

class Barulhenta:
    def leia(self): return iter([])

isinstance(CsvSource(), Readable), isinstance(Barulhenta(), Readable)
Saída realCsvSource isinstance(_, Readable) = True Barulhenta isinstance(_, Readable) = False

Isto é duck typing verificável: o CsvSource satisfaz o contrato por ter o método certo, sem saber que Readable existe. E o mypy cobra o contrato em tempo de checagem, então o erro continua chegando antes de rodar.

O limite do runtime_checkable
python
class Mentirosa:
    read = 42        # nem função é

isinstance(Mentirosa(), Readable)
Saída realTrue

O isinstance sobre um Protocol só confere se o atributo existe — não o tipo, não a assinatura, não o retorno. Ele serve para uma triagem barata; a verificação de verdade é o mypy, que compara a assinatura inteira.

Qual dos dois

UseQuando
Protocolo contrato descreve o que o consumidor precisa; as implementações podem ser de fora
ABChá comportamento compartilhado de verdade para herdar, e você controla todas as implementações
nenhum dos doisexiste uma implementação só, e não há previsão de outra
A regra de bolso

Defina o Protocol do lado de quem consome, não do lado de quem implementa. Quem escreve o Loader declara o que ele precisa de uma fonte; quem escreve o CsvSource não precisa nem saber que o Loader existe. É a mesma inversão do protocolo de iteração da aula 01: o for declara o que precisa, e qualquer objeto que atenda funciona.

Mão na massaAula 09 · Atividade 04

Qual contrato quebra

05 min

Um Protocol declarado, quatro classes candidatas. Decida quais passam no isinstance e quais passam no mypy — as respostas são diferentes.

python
@runtime_checkable
class Sink(Protocol):
    def write(self, rows: list[dict]) -> int: ...

class A:
    def write(self, rows): return len(rows)

class B:
    def write(self, rows: list[dict], flush: bool) -> int: return 0

class C:
    write = None

class D:
    def __init__(self): self.write = lambda rows: 0
Prever antes de rodar
Sua resposta fica salva neste navegador.
isinstancemypyPor quê
Apassapassasem anotação, o mypy assume compatível
Bpassafalhaexige um argumento que o contrato não prevê
CpassafalhaNone não é chamável — o isinstance só viu o nome
Dpassafalhaatributo de instância, não método de classe

Três das quatro passam no isinstance e quebrariam na primeira chamada. Esse é o ponto: runtime_checkable não é validação, é uma triagem por nome de atributo.

O B é o mais perigoso dos três, porque parece razoável. Uma implementação que exige um parâmetro a mais não é substituível pela original — quem chama pelo contrato vai passar só rows e receber TypeError. O contrário é permitido: um parâmetro opcional a mais está tudo bem.

Como pegar isso de verdade

Uma linha no código de produção resolve a checagem estática inteira:

python
_: Sink = B()   # o mypy reclama aqui, no arquivo certo, antes de rodar
ConteúdoAula 09 · Atividade 05

Injeção de dependência

07 min · o núcleo da aula

O nome é pomposo e a ideia cabe numa frase: um objeto recebe o que precisa em vez de construir por conta própria. É a diferença entre um pipeline testável e um que só roda em produção.

python — constrói a própria dependência
class Loader:
    def __init__(self):
        self._warehouse = Warehouse(os.environ["DB_URL"])   # decidiu sozinho

Para testar essa classe você precisa de um banco de verdade, da variável de ambiente certa e de limpar a tabela depois. Na prática, ninguém testa — e o teste que existe é lento e intermitente.

python — recebe a dependência
class Loader:
    """Load records in fixed-size batches into any warehouse-shaped sink."""

    def __init__(self, warehouse: Sink, batch_size: int = 1000) -> None:
        self._warehouse = warehouse
        self._batch_size = batch_size

    def run(self, records: Iterable[dict]) -> LoadReport: ...

Quem decide qual armazém é quem monta o pipeline, num lugar só, geralmente no main(). E o teste passa outro:

python
class FakeWarehouse:
    def __init__(self): self.rows = []
    def insert_many(self, rows): self.rows.extend(rows)

fake = FakeWarehouse()
print(Loader(fake, batch_size=2).run([{"id": i} for i in range(5)]),
      "| gravadas no dublê:", len(fake.rows))
Saída realLoadReport(inserted=5) | gravadas no dublê: 5 sem injeção, o teste bateria no banco: iria falar com o banco de verdade

Sem rede, sem credencial, em microssegundos — e o dublê ainda deixa você inspecionar o que foi gravado, que é a metade do teste que um banco de verdade dificulta.

O que injetar

Tudo que fala com o mundo

Banco, HTTP, sistema de arquivos, fila. São as fronteiras — e são exatamente o que um teste precisa substituir.

Tudo que é não-determinístico

datetime.now, random, uuid4. Injete como parâmetro com valor padrão: def __init__(self, now=datetime.now). Um teste que depende do relógio falha sozinho às 23:59.

Configuração

Ler os.environ no meio de uma classe amarra o objeto ao ambiente. Leia uma vez, na borda, monte um @dataclass(frozen=True) e passe adiante.

O que não injetar

Não injete o que é puro e determinístico. Um round(), um parser de JSON, uma função de validação — passar isso como parâmetro só acrescenta indireção. A régua é a mesma da aula 08: se substituir aquilo não muda nada num teste, não precisa ser injetável.

Não precisa de framework

Em Python, injeção de dependência é passar argumento no __init__. Contêiner de DI é solução para linguagens onde isso é caro. Se você se pegar instalando uma biblioteca para isto, releia esta atividade.

ConteúdoAula 09 · Atividade 06

Composição em vez de hierarquia

06 min

A tentação de modelar transformações como uma árvore de classes é forte, e quase sempre errada. Transformação não tem estado — é função.

python — a hierarquia que não precisa existir
class Transformer(ABC):
    @abstractmethod
    def transform(self, records): ...

class FilterTransformer(Transformer): ...
class RoundingTransformer(FilterTransformer): ...
class RoundingAndCityTransformer(RoundingTransformer): ...

Na quarta classe você já não sabe qual transform roda sem abrir as quatro. E o dia em que precisar de "arredondar sem filtrar" não existe nessa árvore — é preciso reorganizar tudo.

python — estágios que se compõem
def only_valid(records):  return (r for r in records if r.get("amount", 0) > 0)
def round_amount(records): return ({**r, "amount": round(r["amount"], 2)} for r in records)
def add_city(records):     return ({**r, "city": r.get("city", "?").lower()} for r in records)

def pipeline(*stages):
    """Compose stages left to right; nothing runs until you consume it."""
    def run(records):
        for stage in stages:
            records = stage(records)
        return records
    return run

dados = [{"amount": 10.005, "city": "SP"}, {"amount": -1}, {"amount": 3.14159, "city": "RJ"}]
print(list(pipeline(only_valid, round_amount, add_city)(dados)))
Saída real[{'amount': 10.01, 'city': 'sp'}, {'amount': 3.14, 'city': 'rj'}]

Cada estágio é testável isolado, a ordem é visível numa linha, e acrescentar um é acrescentar uma função. É o pipeline de generators da aula 03, agora com o nome do padrão.

Repare que continua lazy

Cada estágio devolve um generator expression, então pipeline(...)(dados) não faz trabalho nenhum até alguém consumir. As três transformações acontecem por registro, numa passada só, com memória O(1) — exatamente o que a aula 05 mediu.

E quando o estágio tem estado?

Aí ele vira uma classe — mas uma classe que se comporta como função:

python
class Dedupe:
    """Drop repeats of `key`, keeping the first. Stateful, so it is a class."""

    def __init__(self, key) -> None:
        self._key = key
        self._seen: set = set()

    def __call__(self, records):
        for record in records:
            k = self._key(record)
            if k in self._seen:
                continue
            self._seen.add(k)
            yield record


pipeline(only_valid, Dedupe(key=lambda r: r["id"]), round_amount)

O __call__ é o que deixa a classe entrar na mesma composição das funções. Quem monta o pipeline não precisa saber quais estágios têm estado — e o set ali é o da aula 07, com o custo O(1) que ele tem.

Estado no estágio tem preço

O Dedupe é O(chaves distintas) de memória e não é reutilizável: o segundo for sobre o mesmo objeto já vem com o _seen cheio. É o anti-padrão da aula 01 de novo. Se precisar reutilizar, o contrato é criar um objeto novo por execução — e isso vai no docstring.

ConteúdoAula 09 · Atividade 07

O conector como context manager

05 min

Um conector abre alguma coisa. Junte o que a aula 08 ensinou e ele fecha sozinho.

python
class SqliteSink:
    """Batch-insert rows, committing once per batch."""

    def __init__(self, path: str, batch_size: int = 1000) -> None:
        self._path = path
        self._batch_size = batch_size
        self._connection = None

    def __enter__(self) -> "SqliteSink":
        self._connection = sqlite3.connect(self._path)
        return self

    def __exit__(self, exc_type, exc, tb) -> bool:
        try:
            if exc_type is None:
                self._connection.commit()
            else:
                self._connection.rollback()
        finally:
            self._connection.close()
        return False

    def write(self, rows: list[dict]) -> int:
        self._connection.executemany(INSERT, [tuple(r.values()) for r in rows])
        return len(rows)

Três coisas que valem reparar:

O close() está num finally

Se o commit() levantar — disco cheio, constraint violada —, a conexão ainda fecha. Sem o finally, o erro no commit vaza a conexão, e é o vazamento de descritores da aula 08 com outra roupa.

A conexão nasce no __enter__, não no __init__

Construir o objeto passa a ser barato e sem efeito colateral. Você pode montar o pipeline inteiro, ler a configuração, validar — e só então abrir conexões. Um __init__ que conecta torna a classe impossível de instanciar num teste.

return False no __exit__

Faz o rollback e deixa a exceção subir. Devolver True ali desfaz a transação e engole o erro: o job termina com código de saída zero, sem dados, e o log não menciona nada.

python — montando tudo num lugar só
def main() -> None:
    config = ApiConfig(base_url=os.environ["API_URL"], token=os.environ["API_TOKEN"])
    stages = pipeline(only_valid, Dedupe(key=itemgetter("id")), round_amount)

    with SqliteSink("warehouse.db") as sink:
        source = OrdersApi(config, session=requests.Session())
        report = Loader(sink, batch_size=1000).run(stages(source.read(since="2026-01-01")))
    log.info("carregadas %d linhas", report.inserted)

Essa função é a única do programa que sabe que existe uma API, um SQLite e variáveis de ambiente. Todo o resto recebe o que precisa — e é por isso que todo o resto é testável.

Para saber maisAula 09 · Atividade 08

dataclass para configuração

04 min

Configuração em dict é o jeito mais rápido de adiar um erro para o pior momento possível.

python — erra tarde
config = {"base_url": ..., "timeout": "30", "retires": 3}   # typo, e timeout é str
...
time.sleep(config["retries"])    # KeyError, três horas depois

O typo em retires não é apontado por nada. O timeout string funciona em alguns lugares e falha em outros. E o KeyError chega no meio do carregamento, não no início.

python — erra na borda
@dataclass(frozen=True, slots=True)
class ApiConfig:
    base_url: str
    token: str
    timeout: float = 30.0
    retries: int = 3

    def __post_init__(self) -> None:
        if not self.base_url.startswith("https://"):
            raise ValueError(f"base_url must be https, got {self.base_url!r}")
        if self.retries < 0:
            raise ValueError("retries must be >= 0")

Agora o typo vira TypeError: unexpected keyword argument 'retires' na construção, o __post_init__ valida as regras que o tipo não expressa, e o frozen=True garante que ninguém mude a configuração no meio da execução.

ArgumentoO que dá
frozen=Trueimutável, e hasheável — pode ser chave de cache
slots=Truea economia de memória da aula 07, e typo em atributo vira erro
kw_only=Trueobriga nomear os argumentos: acaba a troca de posição
field(repr=False)mantém o token fora do repr() — e fora dos logs
O segredo que vaza pelo log

Um @dataclass gera um __repr__ com todos os campos. Um log.info("config: %s", config) despeja o token inteiro no log estruturado — e de lá para o agregador de logs, onde fica indexado e pesquisável. Use field(repr=False) em tudo que for credencial. É a mesma lição do .env na aula 06: o segredo vazado não volta.

CritérioAula 09 · Atividade 09

Quando a classe está sobrando

04 min

A régua do contrário, prometida na apresentação. Quatro sinais de que aquilo devia ser uma função.

Só tem __init__ e um método

Validator(config).validate(rows) é validate(rows, config) com passos a mais. Se a classe é construída, usada uma vez e descartada, ela é uma chamada de função escrita em duas linhas.

Todos os métodos são @staticmethod

Isso é um módulo. Utils.parse_date(x) não é melhor que from dates import parse_date — é pior, porque não dá para importar só o que se usa.

O estado nunca muda depois do __init__

Se os atributos são só configuração lida, o que você tem é uma @dataclass(frozen=True) mais funções que a recebem. A classe com métodos só esconde de onde os valores vêm.

A herança existe para reaproveitar duas linhas

Herdar para não repetir um self.log = ... amarra as duas classes para sempre. Composição — receber o logger — custa um parâmetro e não cria hierarquia.

A pergunta que decide, de novo

"O que este objeto lembra entre uma chamada e a próxima?" Se a resposta for "nada", é função. Se for "a conexão", "o que já vi", "o lote acumulado", é classe — e o que ele lembra é a razão de existir.

Vale dizer o outro lado com a mesma clareza: quando há estado de verdade, resistir à classe também é erro. Um Dedupe implementado como função com set global é pior que a classe — o estado continua existindo, só que escondido e compartilhado por todo mundo.

Desafio: a classe que devia ser função

desafio

Este código é de verdade — variações dele aparecem em muito repositório. Reescreva eliminando o que sobra, e justifique cada remoção com um dos quatro sinais da atividade 09:

python
class BaseProcessor:
    def __init__(self, config):
        self.config = config
        self.logger = logging.getLogger(__name__)

class DateUtils:
    @staticmethod
    def parse(s): return datetime.fromisoformat(s)
    @staticmethod
    def format(d): return d.isoformat()

class RecordProcessor(BaseProcessor):
    def __init__(self, config):
        super().__init__(config)
        self.processed = 0

    def process(self, records):
        out = []
        for r in records:
            r["date"] = DateUtils.parse(r["date"])
            out.append(r)
            self.processed += 1
        return out

São pelo menos quatro problemas, e um deles não está na lista da atividade 09 — tem a ver com laziness e com o fato de process alterar os registros que recebeu. Ache os dois também.
