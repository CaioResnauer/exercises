Para começarAula 16 · Atividade 01

Apresentação

03 min · pré-requisito: aula 06

A aula 06 mostrou o que o git guarda e como um commit se escreve. Esta é sobre o que muda quando existe outra pessoa — ou quando você quer que o seu repositório pareça que existe.

Três coisas: trabalhar em branch em vez de empurrar direto na main, abrir um pull request que alguém consiga revisar, e resolver o conflito — que não é acidente nem sinal de que alguém errou.

Conflito é uma pergunta, não um erro

O git resolve sozinho quase tudo. Quando ele para e pede ajuda, é porque duas pessoas mudaram as mesmas linhas e não existe forma automática de saber qual das duas intenções vale. A atividade 05 mostra um conflito real e a resolução que parece certa e desfaz uma correção.

E se eu trabalho sozinho?

Vale igual, por dois motivos. Um pull request no seu próprio repositório dá um lugar para o CI rodar e para você reler o diff inteiro antes de mesclar — e reler o próprio diff pega mais bug do que se imagina. O outro é que o histórico do seu portfólio é lido por quem avalia, e um repositório com PRs conta uma história diferente de trinta commits direto na main.

Tempo estimado

40 min de leitura, 1 h 20 de exercícios. Todos os comandos e saídas foram executados.

ConteúdoAula 16 · Atividade 02

Por que não commitar na main

05 min

Não é cerimônia. A main tem um papel: ela é a versão que funciona. Todo commit direto nela é uma aposta de que você não quebrou nada.

Com branchDireto na main
o CI roda antes de entraro CI roda depois; se quebrou, já está lá
o trabalho pela metade fica isoladoou você segura o commit por dias, ou empurra incompleto
desfazer é apagar o branchdesfazer é revert no histórico público
o diff da mudança inteira existea mudança está espalhada em N commits misturados
dá para pedir revisãonão há o que revisar antes

O ciclo

bash
git switch main && git pull --rebase          # parta do que está publicado
git switch -c feat/lesson13-window-functions   # um branch por unidade de trabalho

# ... commits pequenos, um por ideia, como na aula 06 ...

git push -u origin feat/lesson13-window-functions
gh pr create --fill                            # ou pelo site
O nome do branch é a primeira comunicação

tipo/escopo-curto, no mesmo vocabulário dos Conventional Commits: feat/, fix/, docs/, chore/. feat/window-functions diz o que é numa lista de vinte branches; teste, novo e caio2 não dizem nada — e são os que ficam esquecidos no remoto por um ano.

Branch curto

Um branch que vive duas semanas acumula divergência, e cada dia a mais aumenta a chance de conflito. Se o trabalho é grande, quebre em pedaços que entrem sozinhos — três PRs de um dia são muito mais fáceis de revisar e mesclar que um de duas semanas.

E a main tem que ser protegida no servidor, não pela sua disciplina. No GitHub: Settings → Branches → Add rule, exigindo pull request e o CI verde. Depois disso, git push origin main é recusado — inclusive por você, num dia de pressa.

ConteúdoAula 16 · Atividade 03

O pull request

06 min

Um PR é um pedido: "puxe estes commits para a main". O que o torna útil não é o mecanismo — é a descrição.

markdown — o formato que funciona
## O que muda
Deduplicação da staging passa a usar ROW_NUMBER com desempate por id.

## Por quê
Dois registros com o mesmo updated_at faziam o resultado variar entre
execuções — a carga da noite 03/09 trouxe 4 pedidos diferentes da anterior
com os mesmos dados de entrada.

## Como revisar
Comece por transform.sql; o resto é teste. O EXPLAIN antes e depois está
no comentário do commit 3c2a1f9.

## O que ficou de fora
O índice (order_id, updated_at) que faria o SORT sumir do plano — está
medido e vai em PR separado.

O que muda — uma frase

O revisor lê isso antes do diff. Se você não consegue resumir numa frase, o PR está fazendo mais de uma coisa.

Por quê — a parte que o diff não mostra

O diff mostra o que mudou; ele nunca mostra a razão. É aqui que entra o número, o incidente, o ticket. Daqui a um ano, esta é a única fonte.

Como revisar — respeite o tempo de quem lê

Por onde começar, o que é ruído, o que merece atenção. Um PR de 400 linhas em que 350 são teste gerado deveria dizer isso na primeira linha.

O que ficou de fora — evita metade dos comentários

Diga o que você viu e decidiu não fazer agora. Isso transforma "você esqueceu X" em "concordo, deixa para depois".

Do terminal
bash
gh pr create --fill              # usa os commits como título e corpo
gh pr create --draft             # abre como rascunho: CI roda, ninguém é notificado
gh pr view --web                 # abre no navegador
gh pr checks                     # o estado do CI
gh pr diff                       # o diff completo no terminal
Tamanho é a variável que mais importa

A pesquisa sobre revisão de código é consistente: acima de ~400 linhas, a taxa de defeitos encontrados despenca — o revisor cansa e passa a aprovar. Um PR de 2.000 linhas recebe "LGTM" em dois minutos, e isso é pior que não ter revisão, porque cria a impressão de que houve.

ConteúdoAula 16 · Atividade 04

Anatomia de um conflito

07 min

Duas pessoas mexeram na mesma função. Uma trocou o arredondamento por centavos inteiros; a outra acrescentou um campo. Rodando de verdade:

bash
git merge feat/city
Saída realAuto-merging transform.py CONFLICT (content): Merge conflict in transform.py Automatic merge failed; fix conflicts and then commit the result.
transform.py — o que o git escreveu
def normalize(record):
    return {
        "id": int(record["id"]),
<<<<<<< HEAD
        "amount": to_cents(record["amount"]),
=======
        "amount": round(float(record["amount"]), 2),
        "city": record["city"].strip().lower(),
>>>>>>> feat/city
    }

Entre <<<<<<< e ======= está o que existe em HEAD — onde você está. Entre ======= e >>>>>>>, o que vem do branch que você está trazendo. Fora dos marcadores, o git já resolveu.

O git guardou as três versões

bash
git status --short
git ls-files -u
Saída realUU transform.py 100644 af5f801c... 1 transform.py 100644 a06c7de7... 2 transform.py 100644 d0ada785... 3 transform.py

UU significa unmerged, both modified. E os três estágios no index são o que faz o merge funcionar:

EstágioÉComo ver
1a base comum: o último ancestral dos doisgit show :1:transform.py
2a sua versão (HEAD)git show :2:transform.py
3a do outro branchgit show :3:transform.py
bash — a base é o que resolve a dúvida
git show :1:transform.py
Saída realdef normalize(record): return { "id": int(record["id"]), "amount": round(float(record["amount"]), 2), }

Comparando com a base fica óbvio quem mudou o quê: o lado 2 trocou a linha do amount; o lado 3 manteve aquela linha e acrescentou o city. É por isso que o git não conseguiu decidir — as duas edições encostam na mesma linha.

Ligue o diff3 e nunca mais desligue
bash
git config --global merge.conflictStyle zdiff3

Com isso, o git inclui a base comum dentro dos marcadores, num terceiro bloco. Você passa a ver as três versões no próprio arquivo, sem precisar do git show :1: — e a decisão vira quase automática.

Mão na massaAula 16 · Atividade 05

A resolução que parece certa

06 min

O conflito da atividade anterior, e alguém resolvendo com pressa: apaga os marcadores, fica com o lado que tem o campo novo.

transform.py — depois da resolução
def normalize(record):
    return {
        "id": int(record["id"]),
        "amount": round(float(record["amount"]), 2),
        "city": record["city"].strip().lower(),
    }
Prever antes de continuar
Sua resposta fica salva neste navegador.

O arquivo compila, passa no lint e não tem marcador de conflito. E a correção de centavos inteiros — o to_cents, que estava na main — foi silenciosamente desfeita.

É o pior formato de falha da aula 04, agora no git: nada reclama, e o bug que alguém já tinha corrigido volta. O CI só pega se houver um teste que cubra o arredondamento — o que a aula 10 pediu no exercício 10.6.

Por que isso acontece tanto

Porque a resolução parece uma escolha entre dois blocos de texto, e não é. Os dois lados mudaram coisas diferentes que por acaso ficaram perto. A resposta certa quase nunca é "um dos dois" — é combinar as duas intenções:

python — as duas intenções
        "amount": to_cents(record["amount"]),
        "city": record["city"].strip().lower(),
O método, em quatro passos
  1. Leia a base (git show :1: ou o bloco do zdiff3). O que cada lado mudou em relação a ela?
  2. Nomeie as duas intenções em voz alta. "Um trocou float por centavos; o outro acrescentou cidade."
  3. Escreva o código que atende as duas. Frequentemente não é nenhum dos dois blocos literalmente.
  4. Rode os testes antes do git add. Um merge é uma mudança de código como qualquer outra.

E o passo zero: se você não entende o que o outro lado estava fazendo, pergunte a quem escreveu. Resolver conflito adivinhando a intenção alheia é como o merge acima acontece.

ConteúdoAula 16 · Atividade 06

Resolvendo na prática

06 min

Com o método da atividade anterior, o mesmo conflito resolvido direito — e o resultado no histórico.

bash
> editar transform.py combinando as duas intenções
python -m pytest -q
git add transform.py
git commit -m "merge: keep integer cents and add city"

git log --oneline --graph --all
Saída real* feb131c merge: keep integer cents and add city |\ | * d17bd78 feat(transform): add the city field * | acbfac3 fix(transform): use integer cents instead of float |/ * 110568c feat(transform): add normalize

O commit de merge tem dois pais — é o único tipo de commit que tem — e o grafo mostra as duas linhas que se separaram e voltaram. E o blame continua apontando para quem escreveu cada linha, não para o merge:

bash
git blame --date=short -- transform.py
Saída real^110568c (Caio 2026-09-06 1) def normalize(record): ^110568c (Caio 2026-09-06 2) return { ^110568c (Caio 2026-09-06 3) "id": int(record["id"]), acbfac3a (Caio 2026-09-06 4) "amount": to_cents(record["amount"]), d17bd78b (Caio 2026-09-06 5) "city": record["city"].strip().lower(), ^110568c (Caio 2026-09-06 6) }

Os comandos de escape

ComandoFaz
git merge --abortvolta ao estado anterior ao merge, sem perder nada
git checkout --ours <f>fica com a sua versão inteira do arquivo
git checkout --theirs <f>fica com a versão do outro branch
git checkout -m <f>recria os marcadores, se você bagunçou o arquivo
git diff --name-only --diff-filter=Ulista só os arquivos em conflito
git mergetoolabre a ferramenta visual configurada
--ours e --theirs invertem no rebase

Num merge, ours é o seu branch. Num rebase, o git reaplica os seus commits sobre o outro — então ours passa a ser o branch de destino e theirs é o seu trabalho. É a confusão mais comum de quem resolve conflito no rebase, e leva a descartar o próprio código.

rerere: resolva uma vez
bash
git config --global rerere.enabled true

Com isso ligado, o git grava como você resolveu — Recorded resolution for 'transform.py' — e reaplica sozinho se o mesmo conflito reaparecer. Num rebase longo, o mesmo conflito volta a cada commit reaplicado; sem rerere, você resolve o mesmo trecho oito vezes.

Para saber maisAula 16 · Atividade 07

Como evitar conflito

04 min

Conflito é função de duas variáveis: quanto tempo o branch vive, e quanta gente mexe no mesmo arquivo. Dá para atacar as duas.

Integre todo dia

git switch main && git pull --rebase && git switch - && git rebase main. Um conflito de um dia é pequeno e você lembra do contexto; um de duas semanas é arqueologia.

PR pequeno

Menos linhas tocadas, menos superfície de colisão. É o mesmo argumento do tamanho da atividade 03, por outro motivo.

Combine antes quem mexe onde

Trinta segundos de conversa evitam duas pessoas reescrevendo a mesma função. É a solução mais eficaz e a menos técnica.

Formatação automática, e num commit separado

Um black ou ruff format rodando em todo mundo elimina o conflito de estilo. Mas nunca misture reformatação com mudança de comportamento no mesmo commit: o diff fica ilegível e o conflito, garantido. Reformate em commit próprio, e registre o hash em .git-blame-ignore-revs.

Os arquivos que sempre conflitam

Lockfiles (poetry.lock, uv.lock), migrações numeradas sequencialmente, e qualquer arquivo gerado que esteja versionado. Para lockfile, a resolução não é editar à mão — é pegar a versão da main e regerar: git checkout --theirs uv.lock && uv lock.

O conflito que o git não vê

Você renomeia normalize para clean_record num branch; no outro, alguém acrescenta três chamadas a normalize. Arquivos diferentes, zero conflito no merge, e o código quebra na hora de rodar.

Isso é um conflito semântico, e nenhuma ferramenta de merge pega. Quem pega é o CI da aula 11 rodando a suíte da aula 10 — que é o argumento mais forte a favor de exigir CI verde antes de mesclar.

ConteúdoAula 16 · Atividade 08

Revisar código

05 min

Você já recebeu uma revisão nesta trilha — a da aula 04. Vale saber escrever uma.

A ordem em que se lê um PR

  1. A descrição. O que muda e por quê. Se não dá para entender, o primeiro comentário é sobre isso.
  2. Os testes. Eles dizem o que o autor acha que o código faz, e revelam os casos que ele não pensou.
  3. A mudança principal. Aquilo que a descrição prometeu.
  4. O resto, procurando o que não foi prometido — a mudança que entrou de carona.

O que procurar, em ordem de valor

ProcureExemplo desta trilha
Está correto no caso vazio e no limite?o manual_batched em loop infinito com entrada vazia
O contrato mudou sem aviso?o chunked que deixou de ser reutilizável
Escala?um in sobre lista dentro de laço; um list() no meio do pipeline
Falha direito?except Exception: continue engolindo linha ruim
Vaza segredo ou recurso?token no repr; arquivo sem with
Estilodeixe para o formatador — não gaste revisão com isso
Como escrever o comentário

Sobre o código, não sobre a pessoa: "esta função retorna None quando a lista é vazia" em vez de "você esqueceu de tratar". Diga o porquê, não só o quê. E marque o que é opcional — um nit: na frente deixa claro que não bloqueia.

Quando for elogio, seja específico: "o CountingSink isola bem a medição" ensina mais que um "ficou bom".

Aprovar sem ler é pior que não revisar

Um "LGTM" registra que alguém olhou. Se ninguém olhou, o registro é falso e a próxima pessoa confia nele. Se você não tem tempo, diga isso — é uma resposta legítima e honesta.

Hora da práticaAula 16 · Atividade 09

Exercícios 16.1 a 16.4

50 min
Os três primeiros num repositório descartável

mkdir /tmp/git-team && cd /tmp/git-team && git init. Só o 16.4 é no seu repositório de verdade.

16.1

Provoque o conflito

experimento

Reproduza exatamente o cenário da atividade 04: um arquivo, dois branches, edições vizinhas na mesma função. Mostre a saída do git merge, o git status --short, o git ls-files -u e as três versões com git show :1:, :2: e :3:.

Depois ligue merge.conflictStyle=zdiff3, refaça, e compare os marcadores. Diga qual dos dois formatos você quer para sempre.

16.2

Resolva errado e prove com teste

experimento

Escreva um teste que cubra o comportamento de cada lado do conflito. Resolva ficando só com um dos blocos, rode a suíte, e mostre o teste vermelho. Depois resolva combinando as duas intenções e mostre a suíte verde.

O ponto do exercício

É o argumento concreto para exigir CI verde no PR. Sem o teste, a resolução errada da atividade 05 entra na main e ninguém percebe por semanas.

16.3

O conflito semântico

experimento

Num branch, renomeie uma função. No outro, acrescente chamadas a ela em outro arquivo. Faça o merge e mostre que o git não reclama de nada. Depois rode a suíte e mostre o erro.

Escreva em duas frases o que isso implica sobre confiar num merge limpo.

16.4

rerere

experimento

Ligue o rerere, provoque um conflito, resolva, e desfaça o merge com git reset --hard. Refaça o merge e mostre a linha Resolved 'arquivo' using previous resolution.

Diga em que situação isso economiza tempo de verdade — e por que ele é uma faca de dois gumes se você resolveu errado da primeira vez.

Entrega: o seu primeiro pull request

30 min
16.5

Proteja a main e abra um PR

entrega

No repositório exercises:

  • Ative a proteção da main exigindo pull request e o CI da aula 11 verde;
  • Faça o trabalho pendente da aula 06 — o lesson03.py vazio — num branch fix/lesson03;
  • Abra o PR com as quatro seções da atividade 03;
  • Espere o CI, revise o seu próprio diff linha a linha, e mescle.
Revisar o próprio PR não é teatro

Ler o diff inteiro numa tela de review, fora do editor onde você escreveu, pega debug esquecido, arquivo que entrou sem querer e comentário desatualizado. É o mesmo efeito de reler um texto impresso.

16.6

Desafio: revise a si mesmo, por escrito

desafio

Pegue o seu lesson04.py — o que foi revisado na aula 04 — e escreva a revisão que você faria hoje, sem reler a minha. Use a tabela da atividade 08 como roteiro.

Depois compare com a revisão publicada. O que você achou que eu não achei? O que eu achei que você não achou? Escreva as duas listas — a segunda é a mais útil.

Como entregar

Mande o link do PR mesclado e as saídas dos exercícios 16.1 a 16.4.

Checklist antes de mesclar
  • A main está protegida no servidor?
  • O PR tem descrição com o que e por quê?
  • O CI está verde?
  • Você leu o próprio diff inteiro?
  • Nenhum arquivo entrou sem querer — .venv, dado, __pycache__?
  • O branch foi apagado depois?
