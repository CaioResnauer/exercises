Para começarAula 11 · Atividade 01

Apresentação

03 min · pré-requisito: aulas 01 a 10

"Na minha máquina funciona" quase nunca é problema de código. É problema de ambiente — versões diferentes, pacote instalado por acidente, dependência que ninguém declarou.

A aula 10 deixou você com uma suíte de testes. Ela só tem valor se rodar igual na sua máquina, na do colega e no CI. Esta aula é sobre garantir isso.

O que você vai sair sabendo

  • O que um ambiente virtual realmente faz — são três linhas de configuração, não mágica;
  • Por que pip freeze > requirements.txt é a resposta errada para a pergunta certa;
  • A diferença entre declarar uma dependência e travar uma versão;
  • pyproject.toml, e quando poetry ou uv valem a pena.
A aula mais curta da fase

São 35 minutos de leitura, e você provavelmente já usa metade disso. O que muda é entender por que, porque é isso que te salva quando o ambiente quebra de um jeito que o tutorial não previu.

ConteúdoAula 11 · Atividade 02

O problema, concretamente

05 min

Sem ambiente virtual, todo projeto seu compartilha a mesma pilha de pacotes — inclusive os que o sistema operacional instalou.

bash — nesta máquina, fora de qualquer venv
python3 -c "import sys, site; print(sys.executable); print(site.getusersitepackages())"
pip list | wc -l
Saída real/usr/bin/python3 /home/caio/.local/lib/python3.14/site-packages 81 pacotes visíveis

Oitenta e um pacotes que ninguém deste projeto pediu. Três coisas ruins acontecem por causa disso:

A dependência fantasma

O seu código faz import requests e funciona — porque outra coisa instalou requests um dia. Ele não está no seu requirements.txt, e o colega que clonar recebe ModuleNotFoundError. O teste da aula 10 passa aqui e falha lá.

O conflito de versões

Projeto A precisa de pandas 1.5, projeto B de pandas 2.2. Sem isolamento, um dos dois está quebrado a qualquer momento, e instalar um conserta e quebra alternadamente.

O Python do sistema

Em Debian e Ubuntu, o python3 do sistema é usado por ferramentas do próprio sistema. Instalar pacote nele é como editar arquivo em /usr — por isso as distribuições recentes recusam com externally-managed-environment.

O sinal de que você está nesse buraco

Se você já digitou pip install --break-system-packages ou --user para fazer alguma coisa funcionar, era isto. A flag resolve o sintoma e piora a causa — o pacote foi para um lugar compartilhado por todos os seus projetos.

ConteúdoAula 11 · Atividade 03

O que um venv realmente é

05 min

Menos do que parece, e é bom que seja: um diretório, um arquivo de configuração de quatro linhas e um sys.prefix diferente.

bash
python3 -m venv .venv
cat .venv/pyvenv.cfg
Saída realhome = /usr/bin include-system-site-packages = false version = 3.14.4 executable = /usr/bin/python3.14

É isso. O python dentro do venv é um link para o interpretador do sistema; o que muda é que, ao subir, ele encontra esse pyvenv.cfg e reconfigura onde procurar pacotes:

bash
.venv/bin/python -c "import sys; print(sys.prefix); print(sys.base_prefix); [print(p) for p in sys.path if p]"
Saída realsys.prefix : .../p1 base_prefix : /usr isolado? : True caminhos de import: /usr/lib/python314.zip /usr/lib/python3.14 /usr/lib/python3.14/lib-dynload .../p1/lib/python3.14/site-packages

A biblioteca padrão continua vindo de /usr — ela é a mesma. O que mudou é a última linha: o site-packages agora é o do projeto, e o ~/.local com os 81 pacotes sumiu do caminho.

Você não precisa ativar

source .venv/bin/activate só coloca .venv/bin na frente do PATH. Chamar .venv/bin/python ou .venv/bin/pytest pelo caminho completo tem exatamente o mesmo efeito — e é o que você escreve num Makefile ou numa etapa de CI, onde não há shell interativo.

O venv não vai para o git

.venv/ entra no .gitignore. Ele tem centenas de MB, é específico do seu sistema operacional e é derivado — regenerável a partir do que está versionado. É a regra da aula 06: versione a fonte, não o derivado.

ConteúdoAula 11 · Atividade 04

Declarar não é travar

07 min · o núcleo da aula

São duas perguntas diferentes, e quase todo requirements.txt por aí tenta responder as duas com o mesmo arquivo.

DeclararTravar
Respondede que este projeto depende?o que exatamente instalar hoje?
Contémo que você importa, com faixa de versãotudo, inclusive dependência de dependência, com versão exata
Escrito porvocê, à mãoa ferramenta
Arquivopyproject.toml*.lock, requirements.lock

Por que pip freeze é a resposta errada

bash — o que quase todo mundo faz
pip install requests pandas
pip freeze > requirements.txt
requirements.txt — o resultado
certifi==2025.8.3
charset-normalizer==3.4.1
idna==3.10
numpy==2.3.2
pandas==2.2.3
python-dateutil==2.9.0
pytz==2025.2
requests==2.32.4
six==1.17.0
tzdata==2025.2
urllib3==2.5.0

Onze linhas para duas dependências. O arquivo agora mistura tudo:

Não dá para saber o que é seu

six está aí porque você precisa dele ou porque o python-dateutil precisa? Daqui a um ano, ninguém sabe se pode remover.

Ele congela o que não devia

urllib3==2.5.0 impede uma correção de segurança do requests de chegar. Você trava a árvore inteira quando só queria travar o topo.

Ele leva junto o lixo do ambiente

Se o venv tinha pytest, ipython e aquele pacote que você instalou para testar uma ideia, tudo entra — e vira dependência de produção.

O jeito certo, com dois arquivos

pyproject.toml — o que você declara
[project]
name = "sales-pipeline"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = [
  "requests>=2.32,<3",
  "pandas>=2.2,<3",
]

[project.optional-dependencies]
dev = ["pytest>=8", "pytest-cov", "mypy"]
bash — o lock, gerado
pip install pip-tools
pip-compile pyproject.toml -o requirements.lock      # resolve e trava tudo
pip-sync requirements.lock                            # instala exatamente aquilo

Os dois vão para o git. O pyproject.toml diz a intenção e é editado por gente; o .lock diz o fato e é editado por ferramenta. Quando você quiser atualizar, roda o pip-compile de novo e o diff mostra exatamente o que mudou.

A faixa de versão que faz sentido

>=2.32,<3: aceita correção e recurso novo, recusa a próxima versão maior. É o contrato do semantic versioning. Fixar == no arquivo de declaração é abrir mão de qualquer correção de segurança; não pôr limite nenhum é aceitar que a versão 3.0 quebre o seu build sem aviso.

Mão na massaAula 11 · Atividade 05

O que quebra o colega

05 min

Um repositório com este conteúdo. Três coisas nele vão fazer o clone de outra pessoa falhar — ou, pior, funcionar diferente.

repositório
sales-pipeline/
├── .venv/                 # versionado
├── requirements.txt       # gerado com pip freeze, 47 linhas
├── src/pipeline.py        # importa requests, pandas e dateutil
└── tests/test_pipeline.py # importa pytest e freezegun
Prever antes de rodar
Sua resposta fica salva neste navegador.

.venv/ versionado

Centenas de MB no repositório para sempre — e a lição da aula 06 vale: apagar depois não tira do histórico. Pior, ele contém caminhos absolutos e binários compilados para o seu sistema. No macOS do colega, o .venv clonado simplesmente não roda.

freezegun e pytest misturados com produção

Se estão no requirements.txt, vão para a imagem de produção — mais superfície, mais tempo de build, mais CVE para acompanhar. Se não estão, a suíte de testes não roda no CI. Um requirements.txt só não consegue separar os dois casos; é para isso que existe optional-dependencies.

Nenhum requires-python

O código usa batched, da aula 04, que só existe no 3.12+. Quem tiver 3.11 recebe ImportError: cannot import name 'batched' — e vai procurar o erro no código, não na versão. Uma linha no pyproject.toml faz o pip recusar a instalação com a mensagem certa.

E um quarto, que não estava na pergunta

dateutil é importado pelo código mas provavelmente não está declarado — ele veio junto do pandas. Funciona hoje; no dia em que o pandas trocar de dependência, some. Toda coisa que você import tem que estar declarada, mesmo que já venha por tabela.

pip, poetry ou uv

05 min

As três resolvem o mesmo problema com quantidades diferentes de opinião. Nenhuma é errada.

venv + pip-toolsPoetryuv
Cria o ambientevocê (python -m venv)a ferramentaa ferramenta
Resolve e travapip-compilepoetry.lockuv.lock
Velocidade de instalaçãobaselineparecidaordens de grandeza mais rápida
Peças a instalar antesnenhuma além do pipo Poetryo uv (binário único)
Padrão do arquivopyproject.toml padrãopyproject.toml, seção própriapyproject.toml padrão

O que escolher agora

Para o seu primeiro repositório de portfólio: venv + pyproject.toml. Sem ferramenta extra, todo mundo consegue rodar, e o arquivo é o padrão da linguagem — o que você aprende aí vale para as outras duas.

O uv vale a pena assim que o projeto crescer: ele lê o mesmo pyproject.toml, resolve muito mais rápido e substitui venv, pip e pip-tools de uma vez. A migração é trocar comandos, não arquivos.

bash — os mesmos passos, nas três
# venv + pip
python -m venv .venv && . .venv/bin/activate
pip install -e ".[dev]"

# poetry
poetry install --with dev
poetry run pytest

# uv
uv sync --extra dev
uv run pytest
O -e do pip install -e .

Instala o próprio projeto em modo editável: o src/ passa a ser importável de qualquer lugar sem gambiarra de sys.path, e as edições valem na hora. É o que faz from sales_pipeline.transform import clean funcionar tanto no teste quanto no script — e resolve o ModuleNotFoundError mais comum de quem organiza o projeto em src/.

Não misture as três

Um poetry.lock e um requirements.txt no mesmo repositório é a garantia de que os dois vão divergir, e de que metade das pessoas vai instalar o conjunto errado. Escolha uma e apague o resto.

Para saber maisAula 11 · Atividade 07

O ambiente além do Python

04 min

Um lockfile perfeito ainda deixa três coisas variando entre a sua máquina e o servidor.

A versão do interpretador

requires-python declara a faixa aceita, mas não instala nada. Dentro da faixa, 3.12 e 3.14 têm comportamentos diferentes — dict ordenado, mensagens de erro, desempenho. Fixe a versão exata no Dockerfile e no CI, e anote no README.

Bibliotecas do sistema

Pacotes com extensão em C dependem de bibliotecas nativas — libpq para psycopg, libssl, drivers ODBC. O lock não as cobre. Foi exatamente o que aconteceu com o Chromium do check.py deste site: o pacote Python instalou, e o binário não subia porque faltavam quatro bibliotecas do sistema.

Variáveis de ambiente e locale

LANG muda o encoding padrão de open(), TZ muda o que datetime.now() devolve. Um pipeline que roda certo aqui e erra três horas em produção quase sempre é TZ. Passe encoding="utf-8" sempre, e trabalhe em UTC.

É por isso que o contêiner ganhou

Um Dockerfile fixa o sistema operacional, as bibliotecas nativas, a versão do Python e o lock, tudo num arquivo versionado. Não é assunto da fase 1, mas é para onde isto aponta — e por isso vale aprender a separar declaração de trava agora, porque a imagem se constrói em cima disso.

O teste que revela ambiente escondido

Crie um venv limpo, instale só o que está declarado, e rode a suíte. É o mesmo que o CI faz, e é a única forma honesta de descobrir a dependência fantasma. Fazer isso uma vez antes de cada entrega vale mais que qualquer ferramenta.

Hora da práticaAula 11 · Atividade 08

Exercícios 11.1 a 11.4

50 min · diretório exercises/python/lesson11/
11.1

Abra o venv por dentro

experimento

Crie um venv e reproduza a atividade 03: mostre o pyvenv.cfg, o sys.prefix, o sys.base_prefix e o sys.path, dentro e fora dele. Aponte exatamente qual entrada do sys.path mudou.

Depois crie um com --system-site-packages e mostre a diferença no sys.path. Diga em que situação essa flag é útil e por que ela normalmente não é.

11.2

A dependência fantasma

experimento

Num venv limpo, instale só pytest. Escreva um módulo que importe algo que você usa hoje sem declarar — requests, dateutil, o que for — e rode. Mostre o erro.

Depois liste, para o seu lesson10.py, todo import de terceiros e confira contra o que você declararia. Quantos faltavam?

11.3

Declarar e travar, separados

implementação

Escreva um pyproject.toml para um projeto pequeno com requests e pytest, separando produção de dev em optional-dependencies, com requires-python. Gere o lock com pip-compile (ou uv lock) e commite os dois.

Compare o número de linhas dos dois arquivos e explique a diferença. Depois abra o lock e ache uma dependência que você não pediu — diga de quem ela veio.

11.4

O clone limpo

verificação

Clone o seu próprio repositório num diretório novo, crie um venv do zero, instale só o que está declarado, e rode a suíte da aula 10. Reporte tudo que faltou.

O jeito rápido de simular outra máquina

git clone . /tmp/clone-teste && cd /tmp/clone-teste. O clone só traz o que está versionado — se o teste precisa de um arquivo que só existe no seu diretório, ele vai falhar aqui, que é exatamente o que você quer descobrir.

EntregaAula 11 · Atividade 09

Entrega

30 min
11.5

Arrume o ambiente deste repositório

entrega

O repositório exercises hoje não declara nada. Acrescente:

  • Um pyproject.toml na raiz com requires-python e as dependências de dev que as aulas usaram (pytest, pytest-cov, mypy);
  • .venv/ no .gitignore, se ainda não estiver;
  • Uma seção no README dizendo, em três comandos, como clonar e rodar os exercícios.
Cuidado com o batched

Os exercícios da aula 04 usam itertools.batched, que é 3.12+. Se você declarar requires-python = ">=3.10", estará mentindo. Declare o que o código realmente exige — e, se quiser aceitar 3.10, inclua a receita alternativa da aula 04 no código.

11.6

Desafio: o CI mínimo

desafio

Escreva um workflow do GitHub Actions que, a cada push, crie um ambiente limpo, instale o que está declarado e rode a suíte. Vinte linhas bastam.

Isso fecha o assunto da aula: o CI é a máquina do colega, rodando a cada commit e sem paciência para "aqui funciona". E prepara a aula 16, onde o resultado dele vira parte do pull request.

Como entregar

Mande o pyproject.toml, o lock e a saída do exercício 11.4 — a lista do que faltou no clone limpo. Se não faltou nada, diga isso; é um bom resultado.

Checklist antes de commitar
  • Todo módulo de terceiros que você importa está declarado?
  • Dependência de teste está separada da de produção?
  • .venv/ está no .gitignore?
  • O requires-python reflete o que o código realmente exige?
  • Você rodou a suíte num clone limpo?
