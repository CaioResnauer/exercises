Para começarAula 08 · Atividade 01

Apresentação

03 min · pré-requisito: aulas 01 a 07

Duas construções que envolvem o seu código em vez de alterá-lo. Uma acrescenta comportamento a uma função sem tocar no corpo dela; a outra garante que a limpeza aconteça mesmo quando dá errado.

Você já usou as duas sem chamá-las pelo nome. @dataclass, da aula 07, é um decorator. with open(...) é um context manager. E o @contextmanager que você escreveu no measure_peak da aula 04 é os dois assuntos ao mesmo tempo.

Por que isso importa num pipeline

Porque quase todo requisito não-funcional de ETL é transversal: medir tempo, tentar de novo, registrar em log, abrir e fechar conexão, controlar transação. Escrever isso dentro de cada função significa repetir e esquecer. Decorator e context manager são as duas formas do Python de escrever uma vez e aplicar em muitos lugares.

O risco de gostar demais

Decorator é fácil de abusar. Um empilhamento de cinco decorators torna impossível saber o que a função faz sem ler os cinco. A aula termina com a régua de quando não usar — porque o custo real deles não é desempenho, é rastreabilidade.

Tempo estimado

50 min de leitura, 1 h 30 de exercícios. Todas as saídas foram executadas.

ConteúdoAula 08 · Atividade 02

Função é objeto, e por isso existe decorator

06 min

Antes da sintaxe com @, o fato que a torna possível: em Python, uma função é um valor como qualquer outro. Pode ser guardada, passada, devolvida.

python
def extract(path):
    return f"lendo {path}"

f = extract                 # sem parênteses: o objeto função, não a chamada
print(f, f("orders.jsonl"))
print(extract.__name__, extract.__doc__)
Saída real<function extract at 0x7f...> lendo orders.jsonl extract None

Uma função que devolve outra

Aqui está a peça que falta. Uma função interna pode lembrar das variáveis onde foi criada, mesmo depois que a externa terminou:

python
def prefixer(prefix):
    def add(text):
        return prefix + text     # `prefix` vem de fora, e sobrevive
    return add

warn = prefixer("[WARN] ")
print(warn("linha 12 malformada"))
print(warn.__closure__[0].cell_contents)
Saída real[WARN] linha 12 malformada [WARN]

Isso é uma closure: a função add carrega consigo uma célula com o valor de prefix. O __closure__ mostra que não é mágica — é um atributo do objeto função.

Você já viu isso na aula 01

Um generator também é um objeto que carrega estado entre chamadas. Closure e generator resolvem o mesmo problema — "lembrar de algo entre invocações" — por caminhos diferentes: a closure lembra de variáveis, o generator lembra de onde parou.

Do padrão à sintaxe

Um decorator é exatamente isso: uma função que recebe uma função e devolve outra. A sintaxe com @ é açúcar puro:

python
def logged(fn):
    def wrapper(*args, **kwargs):
        print(f"chamando {fn.__name__}")
        return fn(*args, **kwargs)
    return wrapper

# estas duas formas são a MESMA coisa
@logged
def extract(path): ...

def extract(path): ...
extract = logged(extract)

Guarde a segunda forma. Quando um decorator se comportar de um jeito estranho, reescrevê-lo assim costuma tornar o problema óbvio — porque o @ esconde que o nome extract passou a apontar para outra função.

ConteúdoAula 08 · Atividade 03

O decorator que apaga a função

06 min

Aquela última frase tem consequência. Se o nome agora aponta para o wrapper, tudo que descrevia a função original se perdeu.

python
@timing_sem_wraps
def extract_orders(path: str) -> list:
    """Read every order from `path`."""
    return []

print(extract_orders.__name__, extract_orders.__doc__, inspect.signature(extract_orders))
Saída realsem @wraps: __name__='wrapper' __doc__=None sig=(*a, **k) com @wraps: __name__='extract_orders_ok' __doc__='Read every order from `path`.' sig=(path: str) -> list

Sem @wraps, a função virou wrapper: perdeu o nome, a docstring e a assinatura. Isso não é cosmético. Quebra, em ordem de dor crescente:

O traceback

Todo erro passa a apontar para wrapper. Com três funções decoradas, os três tracebacks ficam idênticos e não dizem qual estágio do pipeline falhou.

O help() e o editor

A docstring some e o autocomplete passa a sugerir (*a, **k). Quem usa a função perde a única documentação que existia.

Qualquer coisa que leia a assinatura

Frameworks que fazem injeção por tipo, o pytest resolvendo fixtures por nome de parâmetro, dataclasses, serializadores. Todos leem inspect.signature, e todos passam a ver (*a, **k).

python — a correção é uma linha
import functools

def timing(fn):
    @functools.wraps(fn)          # copia __name__, __doc__, __wrapped__, __module__...
    def wrapper(*args, **kwargs):
        return fn(*args, **kwargs)
    return wrapper
O atributo que salva depois

@wraps também grava wrapper.__wrapped__ = fn. É por ele que inspect.signature consegue devolver a assinatura verdadeira, e é como você chega na função original quando precisa testá-la sem o decorator: extract_orders.__wrapped__(path).

Quanto custa a camada

timeit
função pura        157 ns
com 1 decorator    471 ns   -> +314 ns por chamada (3.0x)

Três vezes parece muito e quase nunca é: 314 ns só importa se a função for chamada milhões de vezes e ela própria custar pouco. Decorar read_jsonl, que faz I/O, é irrelevante. Decorar uma função de validação chamada por registro, num pipeline de dez milhões de linhas, são três segundos que ninguém pediu.

ConteúdoAula 08 · Atividade 04

Decorator com argumentos

06 min

O @retry(times=3) tem uma camada a mais que o @logged, e essa camada confunde todo mundo na primeira vez. Vale abrir devagar.

Quando você escreve @retry(times=3), o Python primeiro chama retry(times=3) e usa o resultado como decorator. Ou seja: retry não é o decorator — é uma função que fabrica um.

python
def retry(times: int, delay: float = 0):
    """Retry `fn` up to `times` times, re-raising the last error."""
    def deco(fn):                                  # 2. isto é o decorator
        @functools.wraps(fn)
        def wrapper(*args, **kwargs):              # 3. isto substitui a função
            last = None
            for attempt in range(1, times + 1):
                try:
                    return fn(*args, **kwargs)
                except Exception as error:
                    last = error
                    log.warning("tentativa %d/%d falhou: %s", attempt, times, error)
                    time.sleep(delay)
            raise last
        return wrapper
    return deco                                    # 1. retry() devolve deco

Três níveis, três papéis: retry guarda a configuração, deco recebe a função, wrapper roda no lugar dela. As desdobradas ajudam:

python
@retry(times=3)
def fetch_page(url): ...

# é exatamente
def fetch_page(url): ...
fetch_page = retry(times=3)(fetch_page)
python
@retry(times=3)
def fetch_page(url):
    tentativas["n"] += 1
    if tentativas["n"] < 3:
        raise ConnectionError("502 Bad Gateway")
    return {"url": url, "rows": 120}

print(fetch_page("https://api.exemplo/orders?page=1"))
Saída realtentativa 1/3 falhou: 502 Bad Gateway tentativa 2/3 falhou: 502 Bad Gateway {'url': 'https://api.exemplo/orders?page=1', 'rows': 120}
Três erros clássicos de retry

Capturar Exception. Você vai repetir um KeyError no seu próprio código três vezes antes de falhar. Capture o que é de fato transitório: ConnectionError, TimeoutError, HTTP 5xx.

Não ter backoff. Três tentativas imediatas contra um serviço sobrecarregado só somam carga. O padrão é exponencial com jitter: delay * 2**attempt + random().

Repetir operação não idempotente. Se o INSERT chegou ao banco e a resposta é que se perdeu, tentar de novo duplica a linha. Retry só é seguro sobre operações idempotentes — ou com chave de deduplicação.

O decorator que já existe

functools.lru_cache é o decorator com argumentos mais útil da biblioteca padrão: @lru_cache(maxsize=1024) memoiza a função por argumentos. Num pipeline, ele resolve o "consultar a mesma tabela de-para mil vezes" — mas exige argumentos hasheáveis, o que exclui dict e list, exatamente como o set da aula 07.

Mão na massaAula 08 · Atividade 05

A ordem da pilha

05 min

Dois decorators empilhados. A ordem em que rodam não é a que a maioria chuta.

python
def um(fn):
    @functools.wraps(fn)
    def wrapper(*a, **k):
        print("um: antes"); r = fn(*a, **k); print("um: depois"); return r
    return wrapper

def dois(fn):
    @functools.wraps(fn)
    def wrapper(*a, **k):
        print("dois: antes"); r = fn(*a, **k); print("dois: depois"); return r
    return wrapper

@um
@dois
def trabalho():
    print("  trabalho")

trabalho()
Prever antes de rodar
Sua resposta fica salva neste navegador.
saída real
um: antes
dois: antes
  trabalho
dois: depois
um: depois

A aplicação é de baixo para cima; a execução é de cima para baixo. Desdobrando, fica evidente:

python
trabalho = um(dois(trabalho))

O dois é aplicado primeiro, então fica mais perto da função original. O um envolve o resultado, então é o primeiro a rodar. É uma cebola: quem foi aplicado por último é a casca de fora.

Onde isso muda o comportamento

@retry acima de @timing mede cada tentativa separadamente. @timing acima de @retry mede o total das três. As duas leituras são úteis — mas você precisa saber qual escreveu. O mesmo vale para @cache e @retry: cache por fora nunca chega a tentar de novo em um acerto.

ConteúdoAula 08 · Atividade 06

O with e o arquivo que fica aberto

07 min

Segunda metade da aula. Um context manager garante que a saída aconteça — pela porta da frente ou pela exceção.

python
def parse_sem(path):
    fh = open(path)
    fh.read()
    raise ValueError("linha 12 malformada")     # o close() nunca roda

def parse_com(path):
    with open(path) as fh:
        fh.read()
        raise ValueError("linha 12 malformada")

Num pipeline real, o erro por arquivo é capturado e guardado para o relatório — e é aí que a diferença aparece:

python
erros = []
for _ in range(200):
    try:
        parse(path)
    except ValueError as error:
        erros.append(error)      # guardar o erro é o padrão normal de ETL
Saída realsem with: 200 arquivos, 200 erros guardados -> 200 descritores abertos com with: 200 arquivos, 200 erros guardados -> 0 descritores abertos

Por que 200, e por que isso engana

O objeto de exceção guarda o __traceback__, que guarda o frame onde o erro nasceu, que guarda a variável local fh. Enquanto a lista de erros existir, os 200 arquivos continuam abertos.

O que engana é que, sem guardar o erro, o CPython fecha tudo sozinho: quando o frame morre, o contador de referências do arquivo chega a zero e o close() acontece no ato. O bug fica invisível — até alguém acrescentar um erros.append(e), ou um logger com exc_info=True, ou o código rodar em PyPy, que não usa contagem de referências.

Como isso quebra em produção

OSError: [Errno 24] Too many open files, depois de horas rodando, num job que passou em todos os testes. O limite típico de um contêiner é 1.024 descritores — 200 arquivos ruins bastam para chegar perto, e o erro aparece em um lugar que não tem relação nenhuma com a causa.

O protocolo

with não é sintaxe especial para arquivos. É um protocolo de dois métodos, como o de iteração da aula 01:

python — o with sem açúcar sintático
gerenciador = open(path)
recurso = gerenciador.__enter__()          # 1. entra, devolve o que vai para o `as`
try:
    ...                                     # 2. o corpo do with
finally:
    gerenciador.__exit__(*sys.exc_info())   # 3. sai, SEMPRE

Dois métodos, e o finally é a garantia inteira. __exit__ recebe a exceção que estiver em curso — e, se devolver um valor verdadeiro, engole essa exceção. É assim que contextlib.suppress funciona; e é por isso que devolver True por acidente de um __exit__ esconde erros.

ConteúdoAula 08 · Atividade 07

Escrevendo um context manager

06 min

Duas formas: a classe com __enter__/__exit__ e o generator decorado com @contextmanager. A segunda é a que você vai escrever quase sempre.

python — a forma curta
from contextlib import contextmanager

@contextmanager
def stage(name: str):
    """Time a pipeline stage, reporting even when it fails."""
    start = time.perf_counter()
    log.info("-> entra %s", name)
    try:
        yield                                  # aqui roda o corpo do with
    finally:
        log.info("<- sai %s em %.1f ms", name, (time.perf_counter() - start) * 1000)
python
with stage("transform"):
    time.sleep(0.01)
    raise RuntimeError("schema inesperado")
Saída real-> entra transform <- sai transform em 10.4 ms excecao propagou: schema inesperado

O finally rodou, o tempo foi reportado, e a exceção seguiu subindo. É o comportamento certo: o context manager observa a falha, não a esconde.

O try/finally não é opcional

Sem ele, uma exceção no corpo do with nunca volta ao generator, e o código depois do yield não roda. Um @contextmanager sem try/finally é um context manager que só limpa quando não precisa. É a mesma lição do gen_with_finally da aula 02, agora com outro nome.

A forma com classe

Vale quando o gerenciador precisa guardar estado ou ser reusável:

python
class Transaction:
    """Commit on success, roll back on any exception."""

    def __init__(self, connection) -> None:
        self._connection = connection

    def __enter__(self) -> "Transaction":
        self._connection.execute("BEGIN")
        return self

    def __exit__(self, exc_type, exc, tb) -> bool:
        if exc_type is None:
            self._connection.execute("COMMIT")
        else:
            self._connection.execute("ROLLBACK")
        return False          # False: não engole a exceção

O return False é o detalhe que mais importa. Devolver True ali faria o ROLLBACK acontecer e a exceção desaparecer — o pipeline seguiria como se tivesse dado certo, com a transação desfeita. Silencioso e com evidência apontando para o lado errado, de novo.

Um __exit__ sem return está correto

Uma função sem return devolve None, que é falso, então a exceção propaga. Escrever return False explícito é para o leitor, não para o interpretador.

Para saber maisAula 08 · Atividade 08

suppress e ExitStack

04 min

Dois utilitários do contextlib que resolvem problemas específicos de pipeline e quase ninguém conhece.

suppress: o try/except que cabe numa linha

python
from contextlib import suppress

# em vez de
try:
    os.remove(temp_path)
except FileNotFoundError:
    pass

# escreva
with suppress(FileNotFoundError):
    os.remove(temp_path)

Mesma semântica, e a intenção fica na primeira linha em vez da última. Só use com exceções nomeadas: with suppress(Exception) é o mesmo except Exception: pass que a revisão da aula 04 apontou como o pior formato de falha.

ExitStack: N recursos, quantidade decidida em tempo de execução

O with a, b, c: resolve quando você sabe quantos são. Quando o número vem dos dados — "abra todos os arquivos do diretório" — é o ExitStack:

python
from contextlib import ExitStack

with ExitStack() as stack:
    handles = [stack.enter_context(open(p)) for p in paths]
    print("dentro do bloco, fechados =", [h.closed for h in handles])
print("depois do bloco, fechados =", [h.closed for h in handles])
Saída realdentro do bloco, fechados = [False, False, False] depois do bloco, fechados = [True, True, True]

E a propriedade que faz ele valer: se o quinto open falhar, os quatro já abertos são fechados na ordem inversa. Escrever isso à mão com try/finally aninhado é onde os vazamentos moram.

Onde isso aparece

Escrever saída particionada — um arquivo por região, com o número de regiões vindo dos dados — é exatamente o caso. Sem ExitStack, ou você abre e fecha a cada linha (lento), ou acumula descritores e torce.

ConteúdoAula 08 · Atividade 09

Os dois juntos

05 min

Um objeto pode ser as duas coisas ao mesmo tempo. O contextlib.ContextDecorator deixa você escrever a lógica uma vez e usá-la como with ou como @.

python
@contextmanager
def measure(label: str):
    """Report wall time and peak allocation for a block or a function."""
    tracemalloc.start()
    start = time.perf_counter()
    try:
        yield
    finally:
        elapsed = time.perf_counter() - start
        _, peak = tracemalloc.get_traced_memory()
        tracemalloc.stop()
        log.info("%s: %.2f s, pico %.1f MB", label, elapsed, peak / 1024**2)

Um @contextmanager já serve como decorator de graça — a implementação dele herda de ContextDecorator:

python
# como bloco
with measure("transform"):
    rows = list(transform(read_jsonl(path)))

# e a MESMA função como decorator
@measure("extract")
def extract(path):
    return list(read_jsonl(path))

É o measure do exercício 5.1, agora com as duas caras. A do bloco é melhor para medir um trecho; a do decorator é melhor para instrumentar um estágio inteiro sem mexer no corpo dele.

Um detalhe do @contextmanager como decorator

Cada chamada da função decorada re-executa o generator do começo — é isso que faz funcionar. Mas um @contextmanager usado como with não pode ser reutilizado: cm = measure("x") e depois dois with cm: levanta RuntimeError: generator didn't yield. É a mesma propriedade de esgotamento da aula 01, num objeto que não parece um iterador.

CritérioAula 08 · Atividade 10

Quando não usar

04 min

Decorator é a construção do Python que mais vira vício. Vale ter a régua antes da vontade.

Quando muda o que a função faz

Decorator é para o que envolve: medir, tentar de novo, registrar, autorizar, cachear. Se ele altera o resultado — converte tipo, filtra registros, muda a regra de negócio —, esse comportamento tem que estar visível no corpo da função. Ninguém procura regra de negócio numa linha com @.

Quando é usado uma vez só

Um decorator aplicado a uma única função é uma indireção sem retorno. Escreva o try/finally dentro dela e siga.

Quando empilha mais de dois

Três ou mais e a ordem passa a importar de formas que ninguém consegue prever lendo. Se você precisa de quatro, provavelmente o que falta é um objeto — que é o assunto da aula 09.

Quando esconde estado global

Um decorator que lê configuração de módulo, escreve num cache global ou depende de ordem de importação transforma a função em algo intestável. O teste passa a depender de o que mais foi importado antes — e você descobre isso na aula 10.

A pergunta que decide

"Se eu apagar esta linha com @, a função continua fazendo a coisa certa, só que sem a instrumentação?"

Se sim, o decorator está no lugar certo. Se não — se apagar quebra o resultado — aquilo não era instrumentação, era o programa, e está escondido.

Com context manager o risco é menor, porque o with deixa o escopo visível no código. O único abuso comum é engolir exceção no __exit__ sem que quem lê perceba.
