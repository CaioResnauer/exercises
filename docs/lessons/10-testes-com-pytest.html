Apresentação

03 min · pré-requisito: aulas 01 a 09

Quase ninguém que vem de analytics escreve teste automatizado. É a lacuna mais visível quando um analista tenta virar engenheiro — e é das mais baratas de fechar, porque o pytest exige aprender pouca coisa.

A aula 09 preparou o terreno: sem injeção de dependência não há o que testar sem banco. Agora os dublês que você escreveu à mão viram fixtures, e o relógio injetado vira um teste determinístico.

O que você vai levar

  • assert puro e a mensagem que o pytest constrói sozinho;
  • parametrize — um teste, N casos, N linhas de resultado;
  • fixture, tmp_path e monkeypatch;
  • o que testar num pipeline — e o que não vale a pena;
  • cobertura: para que serve e por que 100% não quer dizer nada.
Um teste desta aula achou um bug de verdade

Enquanto eu escrevia os exemplos, um parametrize falhou: round(10.005, 2) não devolve 10.00. A atividade 05 é sobre esse resultado, porque é exatamente para isso que teste existe — descobrir que a sua ideia do comportamento estava errada.

Tempo estimado

50 min de leitura, 2 h de exercícios. Instale antes: pip install pytest pytest-cov.

ConteúdoAula 10 · Atividade 02

O primeiro teste

06 min

Não há classe para herdar, nem assertEqual, nem setUp. Uma função que começa com test_ e um assert.

pipeline.py — o código sob teste
def parse_lines(lines: Iterable[str]) -> Iterator[dict]:
    """Yield one record per non-blank line, naming the line that fails."""
    for number, line in enumerate(lines, start=1):
        line = line.strip()
        if not line:
            continue
        try:
            yield json.loads(line)
        except json.JSONDecodeError as error:
            raise ValueError(f"line {number}: {error.msg}") from error
test_pipeline.py
from pipeline import parse_lines

def test_parse_skips_blank_lines():
    assert list(parse_lines(['{"id":1}', "", "  ", '{"id":2}'])) == [{"id": 1}, {"id": 2}]
bash
python -m pytest -q
Saída real. [100%] 1 passed in 0.01s

A mágica do assert

Um assert comum de Python só diz AssertionError. O pytest reescreve o bytecode dos arquivos de teste para reconstruir a comparação quando ela falha:

pytest — um teste falhando
>       assert normalize(raw) == esperado
E       AssertionError: assert {'id': 1, 'am... 'city': 'sp'} == {'id': 1, 'am... 'city': 'sp'}
E         Omitting 2 identical items, use -vv to show
E         Differing items:
E         {'amount': 10.01} != {'amount': 10.0}
E         Use -v to get more diff

Ele omitiu os dois campos iguais e apontou exatamente o que difere. Isso vem de graça — você não escreveu mensagem nenhuma.

Onde a reescrita não chega

O pytest só reescreve assert em arquivos que ele reconhece como teste (test_*.py) e em módulos registrados com pytest.register_assert_rewrite. Um assert dentro de um helper em utils.py não ganha a explicação — vira o AssertionError pelado.

As três convenções que bastam

O quêConvenção
arquivotest_*.py ou *_test.py
funçãocomeça com test_
classe (opcional)Test*, sem __init__
O nome do teste é documentação

test_parse_skips_blank_lines diz o comportamento esperado numa linha, e é o que aparece quando falha. test_parse_2 não diz nada — e é o nome que você vai ler às duas da manhã.

ConteúdoAula 10 · Atividade 03

parametrize: um teste, N casos

06 min

A tentação é escrever um teste com cinco assert. O problema é que o primeiro que falha esconde os outros quatro.

python — cinco asserts, um resultado
def test_normalize():
    assert normalize({"id": "1", "amount": "10.005"}) == {...}
    assert normalize({"id": 2, "amount": 3}) == {...}          # nunca roda se o de cima falhar
    assert normalize({"id": 3, "amount": 1.239}) == {...}
python — um teste por caso
@pytest.mark.parametrize("raw,esperado", [
    ({"id": "1", "amount": "10.005", "city": " SP "}, {"id": 1, "amount": 10.01, "city": "sp"}),
    ({"id": 2, "amount": 3, "city": "Rio"},           {"id": 2, "amount": 3.0,  "city": "rio"}),
    ({"id": 3, "amount": 1.239},                      {"id": 3, "amount": 1.24, "city": ""}),
])
def test_normalize(raw, esperado):
    assert normalize(raw) == esperado

São três testes independentes. Todos rodam, e o relatório nomeia qual caso quebrou:

pytest
FAILED test_pipeline.py::test_normalize[raw0-esperado0] - AssertionError: ass...
1 failed, 7 passed in 0.05s

[raw0-esperado0] é o identificador do caso. Você pode rodar só ele: pytest "test_pipeline.py::test_normalize[raw0-esperado0]".

Dando nome aos casos

python
@pytest.mark.parametrize("raw,esperado", [
    pytest.param({"amount": "10.005"}, 10.01, id="string-com-3-decimais"),
    pytest.param({"amount": 3},         3.0,  id="inteiro-vira-float"),
    pytest.param({"amount": None},      None, id="nulo",
                 marks=pytest.mark.xfail(reason="ainda não tratamos nulo")),
])
def test_normalize_amount(raw, esperado): ...

O id= troca [raw0-esperado0] por [string-com-3-decimais]. E o xfail registra um caso conhecido e ainda não resolvido — ele roda, é esperado falhar, e avisa se um dia passar.

Onde ele brilha em dados

Validação e parsing são tabelas de casos por natureza: formato de data, moeda, encoding, campo ausente, campo nulo, campo vazio, valor negativo. parametrize transforma essa tabela em testes sem repetição — e a tabela vira a especificação do que o parser aceita.

Não parametrize o que não é o mesmo teste

Se os casos precisam de if dentro do teste para funcionar, eles não são o mesmo teste. Dois testes separados são mais claros que um parametrizado com ramificação.

ConteúdoAula 10 · Atividade 04

Fixtures: o preparo que se compartilha

07 min

Uma fixture é uma função que produz o que o teste precisa. O teste pede pelo nome do parâmetro, e o pytest resolve.

python
@pytest.fixture
def arquivo(tmp_path):
    """A small JSONL file on real disk, thrown away after the test."""
    p = tmp_path / "orders.jsonl"
    p.write_text('{"id":1,"amount":10}\n{"id":2,"amount":20}\n', encoding="utf-8")
    return p


def test_le_do_disco(arquivo):          # o nome do parâmetro é o nome da fixture
    with arquivo.open(encoding="utf-8") as fh:
        assert total(normalize(r) for r in parse_lines(fh)) == 30.0

Repare que a fixture arquivo usa outra fixture, tmp_path, que vem pronta do pytest: um diretório temporário exclusivo daquele teste, apagado depois. Fixtures compõem.

As que já vêm prontas

caplogos registros de log emitidosgarantir que o aviso foi emitido

Limpeza: yield em vez de return

python
@pytest.fixture
def banco(tmp_path):
    connection = sqlite3.connect(tmp_path / "test.db")
    connection.execute("CREATE TABLE orders(id INTEGER, amount REAL)")
    yield connection                     # o teste roda aqui
    connection.close()                   # e isto roda depois, mesmo se ele falhar

É o mesmo @contextmanager da aula 08 com outro decorator. E vale o mesmo cuidado: se a limpeza precisa acontecer mesmo quando o setup falha no meio, use try/finally.

Escopo: quantas vezes ela roda

python
@pytest.fixture(scope="session")     # uma vez para a suíte inteira
def dataset_grande(tmp_path_factory):
    path = tmp_path_factory.mktemp("data") / "big.jsonl"
    gerar(path, linhas=1_000_000)
    return path
A fixture de escopo largo que vaza estado

Uma fixture scope="session" que devolve algo mutável é compartilhada por todos os testes. Um teste que altera a lista faz o próximo falhar — e a falha depende da ordem de execução, que é o pior tipo de teste intermitente. Escopo largo só para coisa imutável ou cara e somente-leitura.

conftest.py

Fixtures usadas por mais de um arquivo vão para um conftest.py no diretório — sem importar nada, o pytest acha sozinho. Um conftest.py na raiz de tests/ vale para toda a suíte; um dentro de uma pasta vale só ali.

Mão na massaAula 10 · Atividade 05

O teste que estava certo

06 min

Este é o caso real prometido na apresentação. A função arredonda para duas casas; o teste diz o que você esperaria.

python
def normalize(record: dict) -> dict:
    return {"id": int(record["id"]),
            "amount": round(float(record["amount"]), 2),
            "city": record.get("city", "").strip().lower()}


@pytest.mark.parametrize("raw,esperado", [
    ({"id": "1", "amount": "10.005", "city": " SP "}, {"id": 1, "amount": 10.00, "city": "sp"}),
])
def test_normalize(raw, esperado):
    assert normalize(raw) == esperado
Prever antes de rodar
Sua resposta fica salva neste navegador.
saída real
Differing items:
{'amount': 10.01} != {'amount': 10.0}

round(10.005, 2) devolve 10.01, não 10.00. E o bug não está nem na função nem no teste — está na sua ideia de o que 10.005 é.

python
from decimal import Decimal
for v in ("10.005", "2.675", "0.125", "1.005"):
    print(f"round({v}, 2) = {round(float(v), 2):<6} | o float real é {Decimal(float(v))}")
Saída realround(10.005, 2) = 10.01 | o float real é 10.0050000000000007815970093361102044582366943359375 round(2.675, 2) = 2.67 | o float real é 2.67499999999999982236431605997495353221893310546875 round(0.125, 2) = 0.12 | o float real é 0.125 round(1.005, 2) = 1.0 | o float real é 1.00499999999999989341858963598497211933135986328125

Nenhum desses números existe em binário. 10.005 vira um float ligeiramente acima, então sobe; 2.675 e 1.005 viram floats ligeiramente abaixo, então descem. Não há regra a decorar: depende de para que lado o valor caiu.

O 0.125 é o único exato dos quatro — e ele desce, porque aí sim vale a regra do round: empate vai para o par. Duas regras diferentes, dependendo de o número ser representável ou não.

O que fazer com dinheiro

Não usar float. Use Decimal a partir de string — Decimal("10.005"), nunca Decimal(10.005) — e arredonde com quantize(Decimal("0.01"), ROUND_HALF_UP). Um centavo por linha, em dez milhões de linhas, é uma diferença que a área financeira encontra.

E para comparar float em teste

assert x == pytest.approx(0.3). Ele compara com tolerância relativa e é a única forma honesta de testar aritmética de ponto flutuante — 0.1 + 0.2 == 0.3 é False.

ConteúdoAula 10 · Atividade 06

Testando o que dá errado

06 min

Metade do valor de um pipeline está em falhar direito. Isso também é testável, e é o teste que quase ninguém escreve.

python
def test_parse_reports_the_line_number():
    with pytest.raises(ValueError, match="line 2"):
        list(parse_lines(['{"id":1}', "{nao e json}"]))

Duas coisas verificadas de uma vez: que levanta ValueError, e que a mensagem diz qual linha. O match é uma regex contra o texto da exceção — é o que impede o teste de passar com uma mensagem inútil.

O pytest.raises que não testa nada
python — dois erros comuns
with pytest.raises(Exception):        # 1. qualquer erro passa, inclusive typo seu
    parse_lines(linhas)               # 2. generator: não roda nada!

O primeiro erro é capturar Exception: um NameError no seu próprio teste faria ele passar. O segundo é a lição da aula 01 — parse_lines é generator, então a linha não executa corpo nenhum. Sem o list(...), o teste passa por acidente sempre que a função não levanta, e falha sempre que levanta.

Inspecionar a exceção

python
def test_erro_preserva_a_causa():
    with pytest.raises(ValueError) as info:
        list(parse_lines(["{nao e json}"]))
    assert isinstance(info.value.__cause__, json.JSONDecodeError)

O raise ... from error do parse_lines preenche o __cause__. Testar isso garante que a causa original não se perdeu — é o que faz o traceback em produção dizer por que o JSON era inválido, e não só que era.

Testar que o log saiu

python
def test_avisa_linha_ruim(caplog):
    with caplog.at_level(logging.WARNING):
        list(read_jsonl_tolerante(["{ruim}", '{"id":1}']))
    assert "skipped" in caplog.text
    assert caplog.records[0].levelname == "WARNING"

Esse é o teste que impede a regressão da revisão da aula 04: um except que engole a linha ruim em silêncio. Se alguém remover o aviso, o teste cai.

ConteúdoAula 10 · Atividade 07

monkeypatch e os dublês

06 min

A aula 09 resolveu metade do problema: o que é injetado, você substitui passando outro objeto. Esta atividade é sobre a outra metade — o que não é injetável.

python
def test_usa_a_url_do_ambiente(monkeypatch):
    monkeypatch.setenv("API_URL", "https://exemplo.test")
    monkeypatch.delenv("API_TOKEN", raising=False)
    assert load_config().base_url == "https://exemplo.test"
    # tudo desfeito ao fim do teste, sem você escrever nada

O monkeypatch reverte tudo ao final — inclusive se o teste falhar no meio. Escrever os.environ["API_URL"] = ... à mão contamina os testes seguintes, e o efeito depende da ordem de execução.

MétodoSubstitui
monkeypatch.setenv / delenvvariável de ambiente
monkeypatch.setattratributo de módulo, classe ou objeto
monkeypatch.chdirdiretório de trabalho
monkeypatch.syspath_prependsys.path

A regra que evita o erro clássico

python
# em pipeline.py:  from requests import get

monkeypatch.setattr("requests.get", fake)     # NÃO funciona
monkeypatch.setattr("pipeline.get", fake)     # funciona

Substitua onde o nome é usado, não onde é definido. O from requests import get copiou a referência para dentro de pipeline; trocar em requests não alcança essa cópia.

Quando você precisa de monkeypatch, pergunte por quê

Substituir requests.get é sinal de que o cliente HTTP não foi injetado. A aula 09 já dizia: injete e o teste passa um dublê, sem mágica. Guarde o monkeypatch para o que não dá para injetar — ambiente, diretório de trabalho, código de terceiros.

Dublê escrito à mão contra unittest.mock

python
class FakeSink:
    """Records what it was given, so the test can inspect it."""
    def __init__(self): self.batches = []
    def write(self, rows): self.batches.append(list(rows)); return len(rows)

Doze palavras, e o teste consegue afirmar o que foi gravado e em quantos lotes. Um MagicMock daria o mesmo com menos digitação e um problema: ele aceita qualquer método, com qualquer assinatura. Se você renomear write para write_batch, o dublê de verdade quebra o teste — que é o que você quer — e o mock continua passando.

Se usar mock, ancore no real

mock.create_autospec(Sink) ou autospec=True no patch fazem o dublê copiar a assinatura verdadeira. É a diferença entre um mock que protege e um que apenas concorda com tudo.

ConteúdoAula 10 · Atividade 08

O que testar num pipeline

06 min

Testar tudo é caro e testar nada é o que quase todo mundo faz. O critério é o valor de cada teste dividido pelo custo de mantê-lo.

CamadaTestarComo
Transformação purasempreentrada e saída, parametrize
Parsing e validaçãosempretabela de casos, inclusive os ruins
Regra de negóciosempreo exemplo que motivou a regra
Composição de estágiosvale a penafonte em memória, sink dublê
Conector real (API, banco)um só, marcado@pytest.mark.integration
Biblioteca de terceirosnãoo pandas já tem testes

Os testes que valem mais em dados

A entrada vazia

Arquivo sem linhas, resposta sem itens, tabela sem registros. É o caso que nunca é testado à mão e o que mais quebra — foi a StopIteration da aula 01 e o max() sem default da aula 04.

A linha malformada no meio

Não no começo — no meio. Ela testa se o pipeline processa o que veio antes, reporta, e decide conscientemente entre parar e continuar.

O campo nulo contra o campo ausente

{"city": null} e {} são coisas diferentes e o código quase sempre trata uma só. Dois casos de parametrize.

A laziness que você prometeu

Um teste que prova que nada foi lido antes do primeiro next(). Sem ele, um list() acrescentado no meio do pipeline passa despercebido — e é o teste da atividade 09 da aula 05, agora dentro da suíte.

python — testando laziness
def test_parse_e_lazy(arquivo):
    """Nada é lido antes do primeiro next()."""
    lidas = []
    def contando():
        with arquivo.open(encoding="utf-8") as fh:
            for line in fh:
                lidas.append(line)
                yield line

    gen = parse_lines(contando())
    assert lidas == []          # construir não lê
    next(gen)
    assert len(lidas) == 1      # uma linha por vez
Marcadores para separar o que é lento

Registre markers = integration: toca a rede ou o banco no pyproject.toml e rode o dia a dia com pytest -m "not integration". A suíte rápida tem que caber em segundos, ou você para de rodá-la.

Para saber maisAula 10 · Atividade 09

Cobertura, e o que ela não mede

04 min

Útil como mapa do que nunca foi executado. Perigosa como meta.

bash
python -m pytest -q --cov=pipeline --cov-report=term-missing
Saída real.......... [100%] Name Stmts Miss Cover Missing ------------------------------------------- pipeline.py 15 0 100% ------------------------------------------- TOTAL 15 0 100% 10 passed in 0.05s

A coluna que importa é Missing: ela lista as linhas nunca executadas por teste nenhum. Costuma apontar exatamente os ramos de erro — o except que ninguém exercitou.

Por que 100% não quer dizer correto

python
def taxa(valor, aliquota):
    return valor * aliquota      # e se aliquota vier em porcentagem? e negativa?

def test_taxa():
    assert taxa(100, 0.1) == 10  # 100% de cobertura desta função

Uma linha, um teste, 100%. E a função aceita alíquota negativa, string, None. Cobertura mede execução, não verificação: um teste sem nenhum assert cobre igual.

A meta que produz teste ruim

"90% de cobertura" como regra de CI faz as pessoas escreverem testes que executam código sem afirmar nada, só para subir o número. O sinal útil é o oposto: olhar o Missing e perguntar "por que ninguém passa por aqui?". Às vezes a resposta é que aquele código não precisa existir.

Cobertura de ramo

--cov-branch conta cada saída de if separadamente. Um if sem else testado só pelo caminho verdadeiro aparece como ramo faltando — é um sinal bem mais honesto que a cobertura de linha.

Organizando a suíte

04 min

Onde os arquivos ficam e o que configurar para o pytest rodar do jeito que você quer.

estrutura
projeto/
├── pyproject.toml
├── src/
│   └── sales_pipeline/
│       ├── extract.py
│       └── transform.py
└── tests/
    ├── conftest.py           # fixtures compartilhadas
    ├── test_transform.py     # espelha o módulo que testa
    └── data/
        └── sample.jsonl      # amostra pequena, versionada
pyproject.toml
[tool.pytest.ini_options]
testpaths = ["tests"]
addopts = "-q --strict-markers"
markers = [
  "integration: toca a rede ou o banco",
  "slow: leva mais de um segundo",
]

--strict-markers é o detalhe que vale: sem ele, @pytest.mark.integraton (com typo) é silenciosamente ignorado, e aquele teste nunca roda nem é excluído. Com ele, o typo vira erro.

Os comandos do dia a dia

ComandoFaz
pytest -qroda tudo, saída curta
pytest -xpara no primeiro erro
pytest --lfsó os que falharam na última vez
pytest -k "parse and not lazy"filtra por nome
pytest -m "not integration"filtra por marcador
pytest --durations=5os cinco testes mais lentos
pytest -p no:randomlydesliga a ordem aleatória, se instalada
--lf muda o ritmo de trabalho

Corrigiu, roda pytest --lf: só os que falharam, em milissegundos. Quando passarem, roda tudo. É a diferença entre um ciclo de dois segundos e um de dois minutos — e é o que faz você rodar os testes com frequência.
