ConteúdoAula 17 · Atividade 02

Escolhendo a fonte

05 min

A API decide metade da qualidade do projeto. Uma que devolve trinta registros num JSON só não exercita nada do que a fase 1 ensinou.

Precisa ser paginada

Sem paginação não há streaming, não há generator, não há motivo para o batched. É o requisito que mais importa.

Precisa devolver volume

Alguns milhares de registros no mínimo. Com duzentos, todo argumento de memória vira teoria.

Não precisa de cadastro

Quem for avaliar o repositório precisa conseguir rodar. Se exigir chave, o projeto tem que funcionar com dados de amostra versionados — e isso é trabalho extra.

Melhor se tiver sujeira

Campo nulo, formato de data inconsistente, registro duplicado. É o que dá material para a validação — e o que existe em dados de verdade.

FontePor que serve
GitHub APIpaginação com Link header, rate limit de verdade, volume ilimitado
Open-Meteosérie temporal longa, sem chave, ótima para janelas e gaps
Banco Centralséries diárias com buracos em feriado — o calendário da aula 14
IBGEhierarquia UF → município, e nomes com acento para testar encoding
dados.gov.brCSV grande e sujo de verdade; o mais realista dos cinco
Antes de decidir, faça uma requisição

Chame uma página no curl e olhe. Quantos registros por página? Como se pede a próxima — cursor, offset, Link header? O que vem quando acaba: lista vazia, 404, campo has_next? Isso muda a estrutura do seu extrator, e é melhor descobrir agora.

Rate limit é parte do projeto

A GitHub API dá 60 requisições por hora sem autenticação. Bater no limite e tratar direito — ler o Retry-After, esperar, registrar em log — é exatamente o retry da aula 08 num caso real. Não é obstáculo, é conteúdo.

def main() -> int:
    config = Config.from_env()
    setup_logging(config.log_level, config.log_format)
    log = logging.getLogger("pipeline")

    run_id = uuid4().hex[:8]
    log.info("job started", extra={"context": {"run_id": run_id, "since": config.since}})

    source = WeatherApi(config.api, session=requests.Session())
    stages = pipeline(drop_invalid, normalize, Dedupe(key=itemgetter("station", "ts")))

    with JsonlSink(config.out_dir, batch_size=config.batch_size) as sink:
        report = Loader(sink).run(stages(source.read(since=config.since)))

    log.info("job finished", extra={"context": {
        "run_id": run_id, "rows_in": report.seen, "rows_out": report.written,
        "rejected": report.rejected, "seconds": round(report.seconds, 1)}})
    return 0 if report.written else 1

Quinze linhas, e todas as aulas estão ali: o generator do read, os estágios compostos da 09, o context manager da 08, o lote da 04, o log estruturado da 12. E o código de saída no fim — um job que não gravou nada precisa falhar, ou o agendador vai achar que deu certo.

O teste de fogo da arquitetura

Consigo trocar a API por um arquivo local mexendo em uma linha do cli.py? Se sim, as camadas estão certas. Se for preciso mexer em transform.py, elas vazaram uma na outra.

ConteúdoAula 17 · Atividade 04

extract: paginar sem materializar

06 min

O conector é onde a aula 09 encontra a 02: uma classe que guarda configuração e um método que devolve generator.

extract.py
class WeatherApi:
    """Read-only connector. `read` yields one record at a time, lazily."""

    def __init__(self, config: ApiConfig, session) -> None:
        self._config = config
        self._session = session

    @retry(times=3, exceptions=(ConnectionError, TimeoutError), base_delay=1)
    def _fetch(self, page: int) -> dict:
        response = self._session.get(
            f"{self._config.base_url}/observations",
            params={"page": page, "per_page": self._config.page_size},
            timeout=self._config.timeout,
        )
        response.raise_for_status()
        return response.json()

    def read(self, since: str) -> Iterator[dict]:
        page = 1
        while True:
            payload = self._fetch(page)
            items = payload["items"]
            if not items:
                return
            log.debug("page fetched", extra={"context": {"page": page, "rows": len(items)}})
            yield from items
            if not payload.get("has_next"):
                return
            page += 1

Cinco decisões nesse trecho, e cada uma vem de uma aula:

yield from items, não yield items

A assinatura diz Iterator[dict]: cada item é um registro. Devolver a lista da página faria o consumidor iterar páginas — que foi exatamente o bug do exercício 4.5.

Duas condições de parada

Página vazia e has_next falso. APIs mentem: algumas devolvem has_next: true na última página. Sem a primeira condição, o laço é infinito.

timeout sempre

Sem timeout, o requests espera para sempre. Um job travado sem erro é pior que um job que falha — o agendador não sabe que tem problema.

raise_for_status()

Sem ele, um HTTP 500 vira um response.json() que estoura com uma mensagem que não menciona HTTP nenhum.

A sessão é injetada

É o que permite o teste passar uma FakeSession e rodar sem rede. Sem isso, não há teste de extração — só teste de integração lento e intermitente.

Guarde o bruto antes de transformar

Vale muito gravar a resposta crua da API em data/raw/ antes de qualquer transformação. Quando a validação rejeitar um registro, você vai querer olhar o que veio — e refazer a chamada pode não ser possível (rate limit, dado que mudou). É a diferença entre depurar em cinco minutos e não conseguir depurar.

ConteúdoAula 17 · Atividade 05

transform: validar é decidir

06 min

Funções puras, sem I/O, cada uma com uma responsabilidade. É a camada mais fácil de testar e a que carrega as regras do negócio.

transform.py
@dataclass(frozen=True, slots=True)
class Observation:
    station: str
    ts: datetime
    temperature: float


class Invalid(Exception):
    """A record that cannot be turned into an Observation."""


def parse(record: dict) -> Observation:
    """Turn one raw record into an Observation, or say precisely why not."""
    try:
        return Observation(
            station=record["station_id"].strip().upper(),
            ts=datetime.fromisoformat(record["timestamp"]),
            temperature=float(record["temp_c"]),
        )
    except KeyError as error:
        raise Invalid(f"missing field {error.args[0]!r}") from error
    except (TypeError, ValueError) as error:
        raise Invalid(f"bad value: {error}") from error

O Invalid com a razão específica é o que torna o log útil: missing field 'temp_c' diz o que consertar; ValueError não diz nada.

A decisão que o projeto tem que tomar

Registro inválido: parar tudo, ou pular e contar? Não há resposta universal — há uma escolha, que precisa estar explícita no código e no README.

transform.py
def drop_invalid(records: Iterable[dict], report: Report,
                 max_rejected: float = 0.05) -> Iterator[Observation]:
    """Skip records that fail to parse, aborting if too many do."""
    for raw in records:
        report.seen += 1
        try:
            yield parse(raw)
        except Invalid as error:
            report.rejected += 1
            if report.rejected <= 5:
                log.warning("rejected", extra={"context": {
                    "row": report.seen, "reason": str(error)}})
            if report.seen >= 100 and report.rejected / report.seen > max_rejected:
                raise RuntimeError(
                    f"{report.rejected}/{report.seen} rejeitados, acima de "
                    f"{max_rejected:.0%} — abortando") from error

Um limiar, não "sempre pula"

except: continue responde "infinitos registros ruins são aceitáveis" sem ninguém ter decidido isso. Um limiar torna a decisão explícita — e pega o dia em que a API mudou o schema e 100% falha.

Registre as primeiras, conte todas

Cinco avisos bastam para diagnosticar; o total vai no relatório final. É a regra de contadores em vez de eventos da aula 12.

O report é injetado

Contador dentro do laço, não uma passada extra sobre o iterador — o log que mente da aula 12.

O nível acima: dead-letter

Em vez de descartar, grave os rejeitados num rejected.jsonl com o motivo. Custa cinco linhas, e transforma "3% falharam" em "aqui estão as 412 linhas e o porquê de cada uma". É o que um time de dados faria.

ConteúdoAula 17 · Atividade 06

load: lote, atômico, particionado

05 min

A saída em disco parece a parte trivial e tem três armadilhas.

load.py
class JsonlSink:
    """Write records as JSONL, one file per day, atomically."""

    def __init__(self, out_dir: Path, batch_size: int = 1000) -> None:
        self._out_dir = out_dir
        self._batch_size = batch_size
        self._stack: ExitStack | None = None
        self._handles: dict[str, TextIO] = {}
        self._tmp: dict[str, Path] = {}

    def __enter__(self) -> "JsonlSink":
        self._stack = ExitStack()
        return self

    def __exit__(self, exc_type, exc, tb) -> bool:
        self._stack.close()                  # fecha todos os arquivos
        if exc_type is None:
            for key, tmp in self._tmp.items():
                tmp.replace(self._out_dir / f"date={key}" / "part-00000.jsonl")
        else:
            for tmp in self._tmp.values():
                tmp.unlink(missing_ok=True)  # não deixa saída pela metade
        return False

Escreva em temporário e renomeie

Path.replace é atômico no mesmo sistema de arquivos. Sem isso, um job que morre no meio deixa um arquivo parcial — e o processo seguinte lê metade dos dados achando que leu tudo. É o pior tipo de erro: silencioso e plausível.

ExitStack para N arquivos

Uma partição por dia, e o número de dias vem dos dados. É o exercício 8.4 no projeto: abre cada arquivo uma vez, fecha todos no fim, inclusive se der erro no meio.

Particione pelo que vai ser filtrado

date=2026-03-05/ é a convenção que Spark, DuckDB e Athena entendem — e é o partition pruning da aula 15. Se ninguém vai filtrar por data, não particione: mil arquivos pequenos são piores que um grande.

Idempotência

Rodar o job duas vezes com a mesma entrada tem que produzir o mesmo resultado — não o dobro das linhas. Abrir em modo "a" quebra isso; o padrão de temporário mais replace resolve de graça. Escreva isso no README: "o job é idempotente por dia".

Por que JSONL e não CSV

JSONL preserva tipo e aninhamento, não tem problema de vírgula dentro de campo, e é lido em streaming linha a linha. Se quiser ir além, grave Parquet com pyarrow — compressão e leitura por coluna, que é a fase 2 batendo na porta.

def test_erro_nao_deixa_arquivo_parcial(tmp_path):
    """A failed run must leave no output at all, not half of it."""
    with pytest.raises(RuntimeError):
        with JsonlSink(tmp_path, batch_size=2) as sink:
            sink.write([{"station": "A", "ts": "2026-03-01"}])
            raise RuntimeError("falhou no meio")

    assert list(tmp_path.rglob("*.jsonl")) == []

Esse teste é o que separa um pipeline de um script. Ele afirma uma propriedade sobre a falha — e é a que ninguém verifica à mão.

tests/test_pipeline.py — a laziness, defendida
def test_nada_e_lido_antes_do_primeiro_next():
    chamadas = []
    session = FakeSession(pages=[...], on_call=chamadas.append)

    registros = WeatherApi(config, session).read(since="2026-03-01")
    assert chamadas == []          # construir não chama a API
    next(registros)
    assert len(chamadas) == 1      # uma página, não todas
Um teste de integração, marcado

Vale ter um teste que chama a API de verdade, com @pytest.mark.integration. Ele pega a mudança de schema que nenhum dublê pega. Fica fora do pytest -m "not integration" do dia a dia e roda uma vez por dia no CI.

ConteúdoAula 17 · Atividade 08

O README

05 min

É a única parte do repositório que todo mundo lê. Ele decide se a pessoa continua.

README.md — o esqueleto
# weather-pipeline

Extrai observações meteorológicas da API do Open-Meteo, valida e grava
em JSONL particionado por dia. Memória constante: processa qualquer
volume sem carregar tudo.

## Rodar

    git clone ... && cd weather-pipeline
    python -m venv .venv && . .venv/bin/activate
    pip install -e ".[dev]"
    python -m weather_pipeline --since 2026-03-01 --out data/

## Testar

    pytest -m "not integration"

## Arquitetura

    extract  ->  transform  ->  load
    (API)        (puro)         (JSONL)

extract devolve um Iterator[dict] e nunca materializa uma página inteira.
transform são funções puras, sem I/O. load grava em lotes de 1.000,
escrevendo num temporário e renomeando ao final — o job é idempotente por
dia e uma falha não deixa saída parcial.

Todas as dependências são injetadas no cli.py, que é o único módulo que lê
o ambiente. É o que permite a suíte rodar sem rede em menos de 5 s.

## Decisões

- **JSONL, não CSV:** preserva tipo, sem escape de vírgula, lê em streaming.
- **Rejeita até 5% dos registros:** acima disso o job aborta. Um schema que
  mudou falha alto em vez de gravar dados errados em silêncio.
- **Sem banco:** a fase 1 é sobre o pipeline. A carga em warehouse é fase 2.

## Limites conhecidos

- Rate limit da API não é respeitado entre execuções paralelas.
- Deduplicação é O(chaves distintas) em memória; acima de ~10M chaves,
  precisaria de disco.

Sem "este projeto foi desenvolvido com o objetivo de". O que faz, de onde lê, para onde escreve.

O que atravessa para a fase 2

Shuffle é a agregação O(n) da aula 05 — as O(1) resolvem dentro da partição, as O(n) obrigam a mover dados. Você não vai aprender esses conceitos do zero; vai reconhecê-los com outro nome.
