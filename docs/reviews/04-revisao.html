BugAula 04 · Item 02

manual_batched nunca termina

08 min · exercício 4.2

Esse é o bug sério da entrega. O que você escreveu:

lesson04.py — como está
def manual_batched(iterator, size):
    it = iter(iterator)
    batch = islice(it, size)
    while batch:
        yield tuple(batch)
        batch = islice(it, size)

Você acertou a peça mais difícil: o iter() explícito, para que cada islice continue de onde o anterior parou. Sem isso a função reiniciaria a leitura a cada volta. Essa parte está certa.

O problema está na condição de parada. Rodando de verdade:

python
g = manual_batched([1, 2, 3, 4, 5], 2)
print(list(islice(g, 6)))    # só os 6 primeiros, para poder imprimir
list(g)                      # e agora, sem o limite...
Saída real[(1, 2), (3, 4), (5,), (), (), ()] ^C — matei em 6 s; o list(g) nunca retorna

Os três primeiros lotes estão corretos. Depois disso a função entra em regime permanente devolvendo () para sempre. Um for batch in manual_batched(...) em produção nunca sairia do laço, e um list() consumiria toda a memória da máquina.

Por quê

while batch: pergunta "o objeto batch é verdadeiro?". E batch, no seu código, é um objeto islice:

python
from itertools import islice
vazio = islice(iter([]), 3)          # não há absolutamente nada para produzir
print(bool(vazio))
print(bool(tuple(vazio)))
Saída realTrue False

Um objeto islice é verdadeiro sempre — cheio, vazio ou esgotado. Ele não tem como não ser: para responder "estou vazio?" ele teria que olhar adiante no iterador de origem, consumir um item e guardá-lo. É o hasNext() que o Python decidiu não ter, e que a atividade 03 da aula 01 já tinha explicado por outro caminho.

A correção

lesson04.py — corrigido
def manual_batched(iterable, size):
    """Batch data into tuples of length `size`. The last batch may be shorter."""
    if size < 1:
        raise ValueError("size must be at least one")
    it = iter(iterable)
    while batch := tuple(islice(it, size)):
        yield batch

A diferença é onde o tuple() fica. No seu código ele está depois do teste, no yield — materializa para entregar. Na versão correta ele está dentro do teste — materializa para poder testar. É a mesma chamada, mas só uma das duas posições resolve o problema.

Sobre o :=

O walrus não é enfeite aqui: ele permite atribuir e testar na mesma expressão, o que elimina a duplicação do batch = islice(...) antes do laço e no fim dele. A sua versão precisou escrever a mesma linha duas vezes — e é exatamente esse tipo de duplicação que costuma esconder um bug de condição de parada.

Com mais calmaAula 04 · Item 03

Como o Python decide o que é verdadeiro

07 min · a raiz do bug do 4.2

Vale parar aqui, porque esse mecanismo é curto, é usado o tempo todo, e quando você o conhece o bug do 4.2 deixa de ser uma pegadinha e vira uma consequência óbvia.

Quando o Python precisa de um booleano onde você deu um objeto qualquer — if x:, while x:, not x, x and y — ele segue exatamente três passos, nesta ordem:

O objeto tem __bool__?

Se tiver, chama e usa o resultado. Fim. É o que bool, int e float fazem — 0 é falso, o resto é verdadeiro.

Não tem. E __len__?

Se tiver, chama e testa se o comprimento é zero. Comprimento zero é falso. É daqui que vem [] == False, "" == False, {} == False, () == False — todas as coleções seguem esta regra, nenhuma delas define __bool__.

Não tem nenhum dos dois?

Então o objeto é verdadeiro. Sempre. Este é o padrão do Python, e é o passo que morde.

Confira nos objetos do seu código:

python
from itertools import islice

i = islice(iter([]), 3)
print("islice   ", hasattr(i, "__bool__"), hasattr(i, "__len__"), bool(i))

g = (x for x in [])
print("generator", hasattr(g, "__bool__"), hasattr(g, "__len__"), bool(g))
Saída realislice False False True generator False False True

Nenhum dos dois define nada, então os dois caem no passo 3 e são verdadeiros. Não é uma exceção esquisita do islice — é a regra padrão, aplicada a um objeto que não tem como implementar as outras duas.

Por que um iterador não pode ter __len__

Porque ele não sabe. Um islice sobre um arquivo de 40 GB não faz ideia de quantas linhas restam, e descobrir custaria ler o arquivo inteiro — destruindo a única razão de ele existir. O mesmo vale para um cursor de banco, um socket, uma API paginada.

E não pode ter __bool__ pelo mesmo motivo mais um: para dizer "tenho pelo menos um item", ele teria que consumir esse item e guardá-lo num buffer. O ato de perguntar mudaria o estado — que é a pior propriedade possível numa expressão booleana.

As três formas do mesmo erro
python — nenhuma delas funciona
if records:              # sempre True se records for iterador
    process(records)

while batch:             # o seu bug do 4.2
    ...

if not rows:             # sempre False
    log.warning("arquivo vazio")

Todas as três compilam, rodam e mentem em silêncio. Nenhum linter padrão avisa.

next(it, None) tem o mesmo problema que a aula 01 apontou em StopIteration: se None pode aparecer nos dados, ele é ambíguo. Em ETL isso acontece. Quando importar, use um sentinela seu: _MISSING = object(), e teste com is _MISSING.

BugAula 04 · Item 04

O teste do 4.5 lê chaves, não registros

07 min · exercício 4.5

A função está certa. O teste que deveria prová-la é que não prova nada.

lesson04.py — o teste, como está
for records_iterator in read_patitioned(TEST_PATH):
    for record in records_iterator:
        print(record)
        break  # Just test first record
    break  # Just test first file

O nome da variável entrega a intenção: você esperava que cada item fosse um iterador de registros, um por arquivo. Rodando:

saída real
opening .../data/users.jsonl
id

id. Não um registro — a string "id", que é a primeira chave do primeiro dict do arquivo.

O que aconteceu, passo a passo

  1. read_patitioned faz yield from read_jsonl(f). O yield from repassa cada item do gerador interno — não repassa o gerador. Então a função produz dict, um por linha de arquivo.
  2. O for externo, portanto, dá a você um dict, não um iterador. A variável se chama records_iterator, mas contém {"id": 1, "name": "Alice Johnson", ...}.
  3. O for interno itera esse dict. E iterar um dict em Python percorre as chaves: "id", "name", "age", "city".
  4. O break para na primeira. Imprime id.

Nada disso levantou erro, porque cada passo é uma operação perfeitamente legal sobre o tipo que recebeu. O programa fez exatamente o que você mandou — só não era o que você queria.

O teste que o enunciado pedia

lesson04.py — corrigido
for record in take(read_partitioned(TEST_PATH), 2):
    print(record)
Saída realopening .../data/users.jsonl {'id': 1, 'name': 'Alice Johnson', 'age': 29, 'city': 'New York'} {'id': 2, 'name': 'Bob Smith', 'age': 34, 'city': 'Chicago'}

Agora sim são registros. E repare no que a saída prova de quebra: um único opening. Há dois arquivos .jsonl no diretório, e o segundo nunca foi aberto, porque os dois registros pedidos saíram do primeiro. É essa a prova de laziness que o enunciado queria — e ela só aparece quando o teste consome registros de verdade.

O sinal de alerta que estava na frente

Você anotou a assinatura certa: -> Iterator[dict]. Ela diz, em letras grandes, que cada item é um dict. Um for aninhado sobre o resultado contradiz a própria anotação que você escreveu. Quando o type hint e o laço discordam, um dos dois está errado — e vale trinta segundos descobrir qual.

RegressãoAula 04 · Item 05

O chunked perdeu a reusabilidade

08 min · exercício 4.1

Esse é o item mais interessante da entrega, porque o código está certo, os testes passam, e mesmo assim alguma coisa se perdeu no caminho.

python — antes (aula 01) e depois (aula 04)
class Chunked:                        # aula 01 — um ITERABLE
    def __init__(self, iterable, size):
        self.iterable = iterable
        self.size = size
    def __iter__(self):
        return ChunkedIterator(self.iterable, self.size)   # objeto novo a cada for


def chunked(it, size):                # aula 04 — um ITERATOR
    for batch in batched(it, size):
        yield list(batch)

Seu assert passa nos dois casos. Mas o assert só itera uma vez:

python
c = Chunked([1, 2, 3, 4, 5], 2)
print("Chunked  1ª:", list(c), " 2ª:", list(c))

g = chunked([1, 2, 3, 4, 5], 2)
print("chunked  1ª:", list(g), " 2ª:", list(g))
Saída realChunked 1ª: [[1, 2], [3, 4], [5]] 2ª: [[1, 2], [3, 4], [5]] chunked 1ª: [[1, 2], [3, 4], [5]] 2ª: []

É o anti-padrão da atividade 07 da aula 01, só que ao contrário: lá você tinha um iterator disfarçado de iterable por acidente; aqui você trocou um iterable por um iterator e o nome ficou o mesmo. Quem chamar chunked() esperando o comportamento antigo vai receber uma lista vazia na segunda passada, sem erro nenhum.

Mas a versão nova também ganhou alguma coisa

E é importante ser justo, porque o Chunked antigo tinha um defeito pior:

python — alimentando os dois com um generator
fonte = (x for x in range(10))
print(list(islice(Chunked(fonte, 3), 2)))    # o da aula 01
print(list(islice(chunked((x for x in range(10)), 3), 2)))   # o da aula 04
Saída realTypeError: object of type 'generator' has no len() [[0, 1, 2], [3, 4, 5]]

O ChunkedIterator da aula 01 testava self.index >= len(self.iterable) — o que exige que a fonte tenha tamanho conhecido. Ele funcionava com listas e quebrava com exatamente as fontes que o curso inteiro está tratando: arquivos, generators, streams. A sua versão nova conserta isso.

A resposta que o exercício queria

Não é "a nova é mais legível". É esta: você trocou reusabilidade por suporte a fontes infinitas. Nos dois casos, uma propriedade real foi embora e outra chegou, e a escolha depende de quem chama.

Chunked (aula 01)chunked (aula 04)
Iterar duas vezesfunciona2ª vem vazia
Fonte sem len()TypeErrorfunciona
Fonte infinitaTypeErrorfunciona
Linhas de código223

Se você quiser as duas propriedades ao mesmo tempo — e em ETL geralmente quer — o padrão é guardar a fábrica, não o iterador:

python — reusável e sem len()
class Chunked:
    """Reusable iterable of fixed-size chunks over a re-openable source."""

    def __init__(self, source_factory, size: int) -> None:
        self._source_factory = source_factory   # chamável que devolve uma fonte nova
        self._size = size

    def __iter__(self):
        return (list(b) for b in batched(self._source_factory(), self._size))

Repare que a fonte virou um chamável. É a mesma decisão do CsvSource da aula 01: um iterable reutilizável não pode guardar um iterador já aberto — ele precisa saber como abrir um novo a cada for.

A pergunta de review para levar

Depois de todo refactor que troca uma classe por uma função de itertools, rode list(x) duas vezes. Se a segunda vier diferente da primeira, você não fez refactor — mudou o contrato. Pode ser a escolha certa; só precisa ser uma escolha, e estar escrita no comentário.

AnáliseAula 04 · Item 06

A análise do 4.4 está certa, e pela metade

08 min · exercício 4.4 (c)

Começo pela parte boa, porque eu fui medir esperando te corrigir e o número me deu razão a você.

Você escreveu que sorted() + groupby usa mais memória que o defaultdict, porque o sorted() constrói uma cópia completa. Medindo com 300 mil registros desordenados:

tracemalloc — fonte desordenada, 300 grupos
sorted() + groupby : pico   6.86 MB
defaultdict        : pico   2.49 MB

Certo, e pelo motivo que você deu. Ponto para a sua análise.

O que ficou de fora

Você mediu o cenário em que a fonte chega bagunçada. Mas a pergunta era "em que situação cada uma é preferível" — e existe uma segunda situação, muito comum em engenharia de dados, em que a resposta se inverte inteira: a fonte já vem ordenada pela chave.

Acontece o tempo todo: um ORDER BY no banco, arquivos particionados lidos em ordem, um log cronológico, o resultado de um estágio anterior que já agrupou. Nesse caso o sorted() some da conta, e com ele some a única razão de o groupby gastar memória:

tracemalloc — mesma carga, fonte já ordenada
groupby em streaming : pico   0.00 MB
defaultdict          : pico  11.70 MB

De 2,8× a favor do defaultdict para quatro ordens de grandeza a favor do groupby. Não é um ajuste na conclusão; é a conclusão oposta.

Por que a inversão é tão violenta

Porque as duas abordagens respondem a perguntas diferentes sobre quando o primeiro resultado pode sair:

groupby em fonte ordenadadefaultdict
Quando o 1º grupo fica prontoao ver a primeira chave diferentesó no fim do arquivo
O que fica na memóriaum grupotodos os grupos
MemóriaO(maior grupo)O(n)
Cabe em fonte infinitasimnão

O defaultdict não pode emitir nada antes do último registro, porque o próximo registro sempre pode pertencer a um grupo já visto. O groupby sobre fonte ordenada pode: quando a chave muda, ele sabe que aquele grupo acabou. Ordenação é uma promessa, e essa promessa é o que compra a memória constante.

A pergunta que substitui as duas

Não é "groupby ou defaultdict?". É "minha fonte já está ordenada pela chave — e, se não está, consigo pedir para ela vir ordenada?". Empurrar um ORDER BY para o banco transforma uma agregação O(n) em O(1) e não custa nada do seu lado. É o mesmo raciocínio que, na fase 2, decide se uma operação no Spark provoca shuffle.

Reescreva o comentário do 4.4 (c) cobrindo os dois cenários, com os dois números. A resposta completa é "depende de a fonte estar ordenada" — e você já tem metade dela medida.

4.5 — chain.from_iterable

O enunciado dizia "usando chain.from_iterable". Você importou chain, não usou, e resolveu com yield from dentro de um laço. As duas soluções são igualmente lazy e igualmente corretas — não há erro técnico. Mas o exercício existia para você praticar essa função específica, então vale escrever as duas e comparar. Fica assim:

python — a versão que o enunciado pedia
def read_partitioned(directory, pattern: str = "*.jsonl") -> Iterator[dict]:
    """Read every matching file in `directory` as a single stream of records."""
    paths = sorted(Path(directory).glob(pattern))
    return chain.from_iterable(read_jsonl(p) for p in paths)

Duas observações sobre ela. A função deixa de ser generator (não tem yield) e passa a devolver um iterador — o que significa que o corpo roda na chamada, e o glob acontece imediatamente. E note o sorted(): Path.glob não garante ordem, e num pipeline particionado por data ler as partições fora de ordem é um bug que só aparece quando o sistema de arquivos muda.

4.6 — o gap não é localizável

track_variations devolve (delta, houve_gap). Funciona, mas quando ele apontar um gap num arquivo de 2 milhões de leituras, você não terá como saber onde. Devolva o timestamp junto — o custo é zero e transforma a saída em algo que dá para investigar:

python
def track_variations(records, max_gap_minutes: float):
    """Yield (timestamp, delta, gap) for each consecutive pair of readings."""
    for previous, current in pairwise(records):
        minutes = (current["timestamp"] - previous["timestamp"]).total_seconds() / 60
        yield (current["timestamp"],
               current["value"] - previous["value"],
               minutes > max_gap_minutes)

De quebra, max_gap_minutes em vez de N: nome maiúsculo de uma letra é convenção para constante de módulo, não para parâmetro.

Saída real[{'ok': 1}, {'ok': 2}] # 3 linhas no arquivo, 2 registros, zero aviso

É o formato de falha que a aula 01 chamou de pior possível: silencioso, e com evidência apontando na direção errada. Um relatório sai com 2 registros, o arquivo tem 3 linhas, e nada no log liga uma coisa à outra. Num arquivo de milhões de linhas você perde 3% dos dados por meses.

Duas correções, e a escolha entre elas é de produto, não de estilo:

python — pelo menos, deixe rastro
def read_jsonl(path: Path) -> Iterator[dict]:
    """Yield one record per line, logging and skipping malformed ones."""
    with open(path, encoding="utf-8") as handle:
        for line_number, line in enumerate(handle, start=1):
            if not line.strip():
                continue
            try:
                yield json.loads(line)
            except json.JSONDecodeError as error:
                log.warning("%s:%d skipped: %s", path, line_number, error)

Três mudanças que valem por si: json.JSONDecodeError em vez de Exception (um KeyboardInterrupt ou um MemoryError não deveriam virar "linha ruim"); o número da linha, que é o que torna o aviso acionável; e encoding="utf-8" explícito, porque o padrão depende da locale da máquina e um pipeline que funciona no seu WSL pode falhar no container.

E a outra escolha

Em muitos pipelines, pular linha ruim é errado mesmo com log — o certo é falhar alto, ou desviar para uma dead-letter queue e contabilizar. "Quantos registros ruins são aceitáveis antes de abortar?" é uma pergunta de negócio, e o código precisa ter uma resposta explícita para ela. except Exception: continue responde "infinitos", em silêncio, sem que ninguém tenha decidido isso.
